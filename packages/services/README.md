# @repo/services

The service layer: business rules and input validation, on top of the query functions in [`@repo/db`](../db). The web app calls it through tRPC (`apps/web/src/server/trpc/`, where `workspaceProcedure` admits a signed-in user in an allowed workspace). The bearer-authenticated Hono routes (`/mcp`, `/api/proxy`, and the machine, Slack, trigger and file routes) resolve a principal with `createPrincipalResolver` and call services directly. They are the one exception to "the app reaches it only through tRPC". Nothing here knows about tRPC, Hono or Cloudflare, so a script or a test can use a service the same way.

### Events

`append(event)` validates, strips secrets, and writes one row. In a `tool.call` or `tool.result` payload it also redacts credential headers, credential fields and well-known token formats inside the text (`events/scrub.ts`). A payload over 64 KB goes to `blobs.put` under `payloads/<workspaceId>/<eventId>.json`, and the row keeps `{}` as its payload and the key in `payload_ref`. `blobs` is `{ get, put }`: R2 in the app, a `Map` in tests. The reads take the calling principal first and call `authorize`: `transcript(principal, workspaceId, sessionId)` returns the `message.*` and `tool.*` events of a session ordered by id, `query(principal, workspaceId, filters)` filters by agent, run, session, types and an `after` id cursor, `list(principal, filters)` is one page of the workspace log for the Log page, newest first, filtered by agent, types and a `from`/`to` range and paged with `page` and `limit`, each entry holding a short summary in place of its payload (events of a session follow the sessions visibility rules, events outside any session show to the whole workspace), and `readPayload(principal, event)` fetches an overflowed payload. The event types and actor kinds are in `@repo/db/shared`. The helpers in `src/events/` (ids, payload cap, redaction) are copies from control-plane, except `scrub.ts`.

### Runs

`startRun(principal, input)` takes no actor: the actor and `on_behalf_of_user_id` come from the principal. A user acts for themselves, a run principal acts as its agent for the user its parent run was for (`parent_run_id` and `depth` follow, and depth above 3 is refused), a trigger acts for nobody, and only the `system` principal (the tick) may start a run for any agent. The session is found or created on `(agent, origin, externalKey)`; without a key the session's own id is its key, so the UI sends the next message with the id it got back. The run is inserted with its session in one `atomic` write. A third argument, `{ alongside?, pendingFiles? }`, is for trusted callers inside the Worker (the Slack service): `alongside({ runId, sessionId })` returns more statements for the same atomic write, and `pendingFiles` stores file descriptors, which keep the run from being claimed or offered until `fetchPendingFiles` has stored them. A duplicate `requestId` fails the unique index and the first run is returned. Then `run.queued` and `message.user` are appended and the agent's `RuntimeAdapter` (`adapters`, keyed by `agents.runtime`) gets the run in `dispatch`. `FakeRuntime`, which echoes the input, is registered only when `devFakeRuntime` is true, and is the one adapter that finishes the run inside `dispatch`.

`ingestRunEvents` and `completeRun` answer 409 (`ServiceError` `conflict`) unless the run is `running`, so a late call from an execution whose lease expired writes nothing. The one exception is `completeRun({ status: "aborted" })`. On a `running` run it makes the run `interrupted` with `process_ended_at` set and appends `run.interrupted`; on an `interrupted` run it records `process_ended_at`. A repeat gets 409. Only the `system` principal and the machine that claimed the run may call them. `completeRun` hands the reply target to the `Gateway` for its kind with the trusted `{ runId, agentId, onBehalfOfUserId }`; the `none` gateway is always registered. A gateway error reaches the caller after the run is saved as `done`.

The tick calls `sweepQueuedRuns(SYSTEM_PRINCIPAL)`, which offers again every run that has been `queued` or `offered` for over 60 seconds (after the reply gateway's `downloadPendingFiles` fetched leftover `pending_files`; the third failed download of a run fails it with a `run.failed` event, and `fetchPendingFiles(SYSTEM_PRINCIPAL, runId)` is the same step for one run),. It first fails every run still `queued` or `offered` an hour after `created_at` with "Never claimed" (`UNCLAIMED_EXPIRY_MS`; a run queued behind a `running` or `waiting` run of its agent is spared, and the hour restarts when that run ends, a `run.failed` event, a write guarded on the starting statuses so a claim that wins is kept; routine settlement counts it as an error). `reapExpiredLeases(SYSTEM_PRINCIPAL)` makes a run with an expired lease `interrupted`. An interrupted run is never queued again. A machine run's lease is 90 seconds (`LEASE_MS`). A cloud run's is `CLOUD_LEASE_MS` (10 minutes, `@repo/services/cloud/lease`): `claimRun` and `heartbeatRun` take `{ leaseMs }` from the system principal, and the run's Durable Object heartbeats from an alarm every 20 seconds. The longer lease keeps the run token valid and the reaper away through an outage of the object, and an outage over 10 minutes still ends the run `interrupted`.

`bun scripts/dev/seed-fake-agent.ts` seeds the local D1 database with a fake-runtime agent in the dev workspace and prints its id.

### Routines

A routine is a `triggers` row of kind `routine` with a cron, a timezone (the workspace's unless given), a prompt and `next_run_at`, the next slot as an ISO instant. `fireDue(SYSTEM_PRINCIPAL)` takes every enabled routine whose slot has passed, oldest first, and calls `runs.startRun` with `requestId = trigger:<id>:<slot>` and one `alongside` statement, `UPDATE triggers SET next_run_at = <next> WHERE id = ? AND next_run_at = <slot>`. The run and the update land in one `atomic` write, and the run is dispatched afterwards. An overlapping tick hits the unique `request_id`, so its whole write is undone and it reads the first run back without dispatching. A write that fails leaves `next_run_at` at the slot, so the next tick fires it, and counts one error. A run left `queued` by a crash after the write is offered by `sweepQueuedRuns`. Slots missed while the tick was down collapse into one run, and the next slot is the first one after now.

`consecutive_errors` counts failed writes and runs that ended `failed` or `interrupted` (`settleRuns` reads each routine's runs, `runs.actor_id` being the routine id, in order from `settled_run_id`, up to the first one that has not ended, so every run is counted once). The fifth in a row sets `disabled_at`, and a `done` run resets the count. `setEnabled(true)` clears the count and picks the next slot after now.

`nextFireTime` runs a job whose hour field is `*` in real time. Any other job runs on the wall clock: in the repeated hour of a fall-back it fires once, in the first pass, and a wall time inside a spring-forward gap fires once when the gap ends. The upstream bruce-next copy skipped the gap and fired twice in the repeat.

### Inbox

Threads and posts belong to a workspace and every user in it reads and posts to all of them. A post's `@slug` mentions (`inbox/mentions.ts`, at most 10 distinct per post) wake the named active agents, except the agent that wrote the post. A person's post starts each run with the person's principal (`origin: "inbox"`, `externalKey` = the thread id, reply target the thread). `completeRun` hands an agent's reply to `gateway`, which loads the run row, writes the reply post with that `run_id`, and wakes its mentions with a run principal for that run, so `on_behalf_of_user_id`, `parent_run_id` and `depth` come from the run table. Nothing in a post's text can change them.

The loop guard (`inbox/loop-guard.ts`, borrowed from Agentum) has two rules. When the newest 3 posts of a thread are all from agents, no mention wakes anyone until a person posts. An agent also has a budget of 10 wakes per hour, counted from its `inbox` runs. A stopped wake appends `inbox.loop_stopped` with `reason` `streak` or `budget`. A wake that `startRun` refuses (a busy ancestor, the depth limit) is recorded the same way with `reason` `refused`, so the reply post is kept and the other mentions still run. An error from a wake that is not a `ServiceError` reaches the caller, after the run is saved as `done`.

### Workspaces and principals

A workspace is one Clerk organisation, created on its first request by `forOrg`. An org outside `allowedOrgIds` has no workspace. `sessionPrincipal({ orgId, userId })` turns a Clerk session into a `user` principal (`via: "session"`).

`createPrincipalResolver({ db, runTokenKey, verifyClerkOAuthToken, isOrgMember, allowedOrgIds })` has one method, `resolve(authorization)`, which returns a `Principal` or null (answer 401). The token prefix picks the check: `hm_run_` run token, `hm_mach_` machine credential (`machines.credential_hash`, not revoked), `hm_trg_` trigger token (`triggers.token_hash`; routines have no token), `hm_key_` API key (`api_keys.key_hash`, a stub table that M2.1 builds on), and a token with no `hm_` prefix goes to `verifyClerkOAuthToken`. Any other `hm_` token is refused. Every accepted token must belong to a workspace whose org is in `allowedOrgIds`. The `api_key` and `oauth` principals also pass `isOrgMember(userId, clerkOrgId)`, whose answer, true or false, is reused for 60 seconds per user and org. A throw from `isOrgMember` or `verifyClerkOAuthToken` is not caught, so a Clerk outage is a 5xx, not a 401. `SYSTEM_PRINCIPAL` is for the minute tick; nothing resolves to it from a request.

### Agent connections

`a2a/connections.ts` does no HTTP. The invite `join` goes through an injected `PairingTransport`, and anything that may be retried is an `a2a_outbox` row for AA.5. Only a person on a browser session creates, approves or widens a connection (an org admin or the agent's owner), and any session member revokes or narrows one. A `peer` principal passes `authz.can` only for `a2a.*` and `runs.start`. `authenticate` is not part of `createPrincipalResolver`, so an `hm_a2a_` token works only on the `/a2a` routes.

Tokens are stored as SHA-256 hashes. The credential we present to a peer is sealed with the secrets key, bound to its row. The token an approval sends to the joiner waits in the outbox sealed under `body.token`, and its headers under `headers`, both bound to the outbox row: AA.5 unseals them, delivers, then calls `activationDelivered`. An invite token is `hm_inv_<connectionId>.<secret>` so a wrong secret counts against its own invite. Archiving an agent revokes its connections through `events.onAppend`.

### Skills store

A skill is a named file tree with a history, kept in D1 (`skills`, `skill_versions`, `skill_version_files`, `skill_assignments`) and R2 (`skill-blobs/<sha256>`, written once and shared by every version and skill). Every commit makes a new version that holds the whole tree, never a delta. The library's `skills/` folders are moved into the store and are not the source any more: the runtimes read through `@repo/services/run-skills`, and the library no longer checks a SKILL.md under `skills/`. The first call of any method in a workspace moves them into the store (`migrateLibrary`, recorded in `skill_library_migrations`, so it runs once).

Every method takes the calling principal first and a plain input object (the zod schemas are in `skills-store/records`). Errors are `ServiceError` (`invalid`, `conflict`, `not_found`) or `ForbiddenError`.

| Method | What it does |
| --- | --- |
| `create({ name, files, message })` | A new skill with version 1. A person's skill is people-owned, a run's is owned by its agent |
| `commit({ skillId, baseVersion, writes, deletes, message })` | One new version from the base's tree. `writes` are `{ path, content, executable? }` (text or bytes), `deletes` are `{ path }`. The base must be the latest version that is not rejected, approved or proposed, else `conflict` (a git non-fast-forward). A commit that changes nothing is `invalid` |
| `list()`, `log({ skillId })`, `show({ skillId, version, withContents? })` | Skills with their latest and latest approved number, a skill's versions newest first, one version's tree (with bytes on request) |
| `diff({ skillId, from, to })` | Added, removed and changed paths, and a unified diff of each text file |
| `revert({ skillId, toVersion, message? })` | A new version whose tree equals an older one, made on the latest version |
| `approve`, `reject({ skillId, version })` | People only, for a `proposed` version. Approving needs the version's base to be the latest approved version, else `conflict`: a stale proposal is redone, not merged |
| `assign`, `unassign({ agentId, skillId })`, `pin({ agentId, skillId, version })` | People only. An assignment follows the latest approved version, or the pinned approved one (`version: null` unpins). An agent carries one assigned skill per name |
| `forAgent(agentId, { withContents?, paths? })` | The agent's resolved skills by name, `{ skillId, name, version, pinned, files }`, each file `{ path, hash, size, executable, content? }`. A skill with no approved version yet is left out. A run may ask only for its own agent. `paths` (each `<name>/<file>`) limits the files, so reading one file does not load the rest |
| `importSkillArchive(zip)`, `exportSkillArchive({ skillId, version })` | A `.skill` file is a zip with one top-level folder (the skill name) holding SKILL.md and the other files; the executable flag is the unix mode in the zip. Import makes a new skill, or a new version holding exactly the archive's tree when the caller already owns one of that name. `fflate` does the zip work; the unpacked size is capped while inflating, so a zip bomb is refused before it is expanded |
| `readFile({ skillId, version, path })` | One file of a version with its bytes, `not_found` when the path is not in it (SK.4) |
| `assignments()`, `proposals()` | Every assignment in the workspace (`{ agentId, skillId, pinnedVersion }`) and every version waiting for a decision, for the Skills page (SK.4). A run sees only its own agent's |
| `migrateLibrary()` | The one-off library move. Own folders become skills owned by that agent and assigned to it, `_shared` folders become people-owned skills assigned to every agent that has no own folder of the same name. Folders that break a rule are returned in `skipped` |

Who may do what. A person with workspace access may do everything and their versions are `approved` at once. A run may create skills (owned by its agent), commit, revert and import into skills its agent owns, and read the skills assigned to or owned by its agent, but its versions are `proposed`, and it can never approve, reject, assign, unassign or pin. The proposing agent reads its own proposed versions by number (`show`, `log`, `exportSkillArchive`), so it can test a change before a person approves it. Another agent, and `forAgent`, see approved versions only. A skill a run cannot see is `not_found`; a skill it can see but does not own is `ForbiddenError` for writes.

Every write checks SKILL.md the way the library did (frontmatter `name` equals the skill name, a description of up to 1,024 characters, UTF-8), the caps of `@repo/protocol/skills` (`SKILLS_MAX_FILES`, `SKILLS_MAX_BYTES`, applied to each version's tree; the total over an agent's assigned skills is the loader's to check), and refuses unsafe paths (absolute, `..` or `.` segments, backslashes, empty segments, control characters, over 512 bytes or 20 segments). Events (`skill.created`, `skill.committed`, `skill.approved`, `skill.rejected`, `skill.reverted`, `skill.assigned`, `skill.unassigned`, `skill.pinned`, `skill.imported`) name the principal, the skill and the version, never file contents. Rejecting a proposal also rejects the proposals built on it, with one `skill.rejected` event each, the later ones carrying `rejectedWith`.

Names are unique among one owner's skills, not workspace wide: the people's skills are one scope and each agent's own skills another. The library allowed an agent's skill and a shared one to share a name, and the migration has to keep that.

## Using it

A service is a factory that takes one object, `{ db, atomic, ... }`, and never `env`. `db` is a drizzle instance. A service that writes more than one row also takes `atomic` from `@repo/db/atomic`, and the others take what they need from the caller, such as `blobs`, `clock` or `adapters`. A new module would be used like this (`createXService` is a placeholder):

```ts
import { d1Atomic } from "@repo/db/atomic";
import { createXService } from "@repo/services/x";
import { drizzle } from "drizzle-orm/d1";

const db = drizzle(env.DB);
const x = createXService({ atomic: d1Atomic(db), db });
await x.list(principal);
```

In the app, `compose` in `apps/web/src/server/compose.ts` builds the services from the Worker's bindings, once per request and once per minute tick. `apps/web/src/server/trpc/context.ts` puts them on `ctx.services`, and the bearer routes read them from the same composed object.

## Writing a service

Add a module as `src/x.ts` and an entry for it in `exports`. Then follow these rules:

- Export the input schema (zod). The tRPC router passes it to `.input()`, and the service parses with it again, so a caller that skips tRPC still gets validated input.
- Methods are `async`, so a validation error rejects the promise rather than throwing synchronously.
- Take `{ db, ... }` with `db` typed as `Database` from `@repo/db`. Never read `env`, bindings or the request; the caller passes in what the service needs, including the user id when a rule depends on it.
- Rows that must land together go through the `atomic` parameter, never `db.batch` or `db.transaction`.
- Return the plain JSON shapes from `@repo/db/shared`.

A new service also needs a factory call in `composeWith` and a field on `Services` in `apps/web/src/server/compose.ts`.
