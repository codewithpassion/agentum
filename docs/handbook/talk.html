Anthropic Managed Agents

Why we do not run the agent loop ourselves.

Managed Agents

What Anthropic hosts, and what we keep

Anthropic's side

  • The agent loop. A session runs until end_turn, a budget, or a stop.
  • A sandbox with a shell and filesystem.
  • Subagents. Ours is "Worker", a Haiku agent for mechanical tasks.
  • A memory store per agent, with instructions on what to keep there.
  • Connectors and skills, attached at registration.

Our side

  • The workspace: channels, wiki, computer, browser, secrets, routines.
  • One MCP server per agent, reachable at /mcp/:token. 34 tools.
  • The router: who wakes, when, with which session.
  • The event pump: every 4 seconds, read session events, turn them into messages and status.
The MCP server is the whole contract. Anthropic never sees our database.4

Managed Agents

One message, end to end

1. Registeragents.create with the system prompt, the workspace MCP server, skills, vault ids, model. Re-synced on change.
2. MentionA message with @Bruce lands. The workspace's router Durable Object sees it.
3. Sessionsessions.create with the effective model and a $10 budget. Reuse for a thread, fresh for a channel mention.
4. Wakesessions.events.send with the wake text: the message, its thread, who else is in the channel.
5. WorkThe agent calls our tools over MCP: read_thread, wiki_write, computer_exec, post_message.
6. Pumpsessions.events.list every 4 s. Status to the UI, replies as messages, stop reason carried through.

The system prompt is assembled per agent: name, soul, instructions, the workspace rules, a subagents section, a skills section, and the roster of other agents it can mention.

The API calls we actually make

Agents and sessions

  • environments.create / list
  • agents.create / update
  • sessions.create / retrieve / delete
  • sessions.events.send / list

Skills

  • skills.create / delete
  • skills.versions.create / list / delete
  • R2 stays the source of truth. The download endpoint was unusable with workspace keys.

Vaults

  • vaults.create / delete
  • vaults.credentials.create / update / archive
  • One vault per connector for OAuth tokens. One vault per workspace for secrets, header injection only.

Every new API surface got a spike script first (bun scripts/anthropic-spike.ts) so the plan was written against observed behaviour, not the docs.

Managed Agents

Things we learned the hard way

The silent death

A Slack mention produced browser activity and then nothing. No reply, no error, no log.

  • Read the session transcript with sessions.events.list: stop_reason: budget_reached at 105 cents of a 100 cent cap.
  • The session had carried 66 cents from an earlier task. Reuse was shrinking every later budget.
  • Fix: $10 budget, fresh session per channel mention, and an abnormal stop posts a death notice into every thread still showing "Thinking…".

Smaller surprises

  • status_idle is not "finished". Its stop reason is the whole story.
  • A session fixes its connectors and vaults at creation. Changes reach the next session, so resync is settled right before sessions.create.
  • A sandbox secret is a placeholder, 61 characters against a 40 character key. Anthropic substitutes at egress, so even the agent's own shell cannot read it.
  • Anthropic accepts duplicate agent names. No prefixing needed.

Managed Agents

And when you do not want Managed Agents

The Cloudflare runtime

  • Chosen per agent at creation. A Durable Object holds the transcript and advances it from alarms.
  • Model through the AI binding: Workers AI, or any provider through AI Gateway. No Anthropic key involved.
  • Same MCP server, connected in memory. The two runtimes cannot drift in what an agent can do.
  • 40 model calls per wake instead of a dollar budget.

What you give up

  • No sandbox, no subagents, no connectors, no memory store.
  • No per-conversation model overrides. The agent's model is the model.

Both runtimes sit behind one SessionGateway interface, so the router, the status badges and the death notices are shared.

Slack

Every agent is a real Slack identity.

Slack

One Slack app per agent, not one bot for the deployment

Why

  • An agent should show up in Slack under its own name and avatar, not as "Agentum bot".
  • Two agents in one Slack channel is a real topology. Events are claimed by bridge ownership, or every message ingests twice.
  • A workspace owner can add an agent to Slack without touching deployment secrets.

The manifest is generated

  • Scopes are exactly the calls the client makes: channels:history, channels:read, channels:join, groups:*, chat:write, files:read, files:write, users:read.
  • Bot events: message.channels, message.groups.
  • Interactivity for question buttons.
  • Events URL carries the app's row id, so a draft can answer Slack's URL verification before any secret exists.

Slack

Connecting an agent, in the agent's own settings

1. DraftOpen the Slack tab. One click creates a draft row and shows the manifest and the events URL.
2. Create the appPaste the manifest into api.slack.com. Slack pings the events URL; the draft answers the handshake.
3. TokensPaste the bot token and signing secret. We call auth.test, store team and bot user, encrypt the secrets.
4. BridgeChannel settings: pick a connected agent and a Slack channel. Messages now mirror both ways.

Rules that fell out of it

  • No response ever returns a stored token. Verify server-side, report status only.
  • The wizard step is derived from the persisted row. Abandon mid-flow and you resume, not restart.

Operational

  • Adding a capability to the manifest means every connected app must re-apply it. That is surfaced in the UI, not just in docs.
  • Disconnecting the app takes its bridges with it.

Slack

What a bridged channel feels like

Mirroring

  • A Slack message becomes an Agentum message with an external author.
  • An Agentum message goes out as the agent's app, so it carries the agent's name.
  • Threads map to threads. Attachments cross over.

Thinking

  • The moment an agent wakes, a "Thinking…" placeholder posts into the Slack thread. That placeholder is what creates the thread.
  • It is rewritten into the reply when the reply lands. A small model writes the one-line status.

Questions

  • ask_user renders as Slack blocks with buttons.
  • Slack gives 3 seconds to ack. The handler acks, does the real work in waitUntil, and reports back through response_url.
  • First answer wins, decided by the database. Approving wakes the agent in that thread.

Connecting a computer

An agent's shell on hardware you own.

Computer

Where an agent's computer can live

Cloudflare default

  • A Durable Object with a SQLite filesystem.
  • A shell only in dev. Deployed Workers refuse the Worker Loader, so production has files but no exec.

Self-hosted verified live

  • A Docker or Podman container on your laptop, a NAS, an office box.
  • It dials out. No inbound port, no tunnel, no public IP.

Fly.io unverified

  • A Fly Machine plus volume per agent, provisioned through the Machines API.
  • Built against fakes. Nobody has run it on a real account yet.

Fixed at agent creation. Five tools on every backend: read, write, edit, list, exec. The Files tab in the rail browses whichever backend the agent has.

Computer

Connecting one: a token and a run command

docker run -d --name agentum-computer \
  --restart unless-stopped \
  --memory 2g --cpus 2 \
  -v agentum-computer:/home/agent \
  -e AGENTUM_URL=https://agentum.rockyshoreslabs.io \
  -e AGENTUM_COMPUTER_TOKEN=<token> \
  ghcr.io/codewithpassion/agentum-computerd

The Computers page shows this once, with the token filled in. Podman is the same plus --userns=keep-id.

What is in the box

  • Debian slim with bash, git, curl, python3, node, bun, sqlite3, ripgrep.
  • An unprivileged agent user. /home/agent is the volume, and the volume is the computer.
  • A Bun daemon speaking one JSON protocol: hello, heartbeat, then read, write, edit, list, exec.
  • Reconnects forever with backoff. Stopping Agentum is a pause, not a failure.

Computer

How a tool call reaches the container

AgentCalls computer_exec over MCP with a command and a timeout up to ten minutes.
WorkerAgentComputerClient looks up the agent's backend and picks the remote transport.
ComputerRelayOne Durable Object per host holds the daemon's WebSocket with the hibernation API. Pending map, one exec in flight.
Containercomputerd runs it as agent, streams back exit code and output, capped.
ActivityEvery command lands in the agent's Activity tab with its exit code.

Who presents the credential decides how it is stored

  • Self-hosted: the daemon dials in with the token, so we store a hash.
  • Fly: Agentum is the client, so we store it encrypted.

Offline is a sentence, not a stack trace

"The computer host "office-box" is offline (less than a minute ago). Start the container and try again." The agent relays that verbatim.

Computer

The acceptance run, on this laptop

  1. Created a host in Computers, got the token, ran docker run --network host against the dev server. Ready in seconds.
  2. Test connection answered "computerd 0.1.0 on Morosini".
  3. Created an agent on that host and asked it to run uname -a, write a file, read it back. Every command in the activity feed.
  4. Stopped the container. The agent reported the host offline with the last-seen time.
  5. docker start. The file was still there.
The container runs whatever the agent decides to run, with the network the container has. The container boundary is the safety. Cap its memory and CPU, and put it on a machine you are willing to hand to a program.

Path mapping bit us once: file tools are rooted at the home directory, a real shell sees the real filesystem. The tool description now says so.

What to take away

Managed Agents

Hand the loop to Anthropic and put all your effort into the MCP server and the router. Read session transcripts when something goes quiet.

Slack

One app per agent, generated manifest, tokens verified and never returned. The placeholder message is what creates the thread.

Computer

A container that dials out is the simplest way to give an agent a real shell on your own hardware. The volume is the computer.
