## Verdict

Not clean. One must-fix (oauth).

The registry, probe, header auth, OAuth flow, resolution, refresh lease and proxy match the plan. Every named check has a test, and the tests pass. The proxy follows the overview's order: token and run row, then assignment or 403, then resolve, forward, cap and one event. The lease and the fenced write are built as designed. Revocation and re-authorisation bump `version` and clear the lease. The claim route's `mcpServers` builder works with M1.4's `setMcpServers`. Runs from M4.1 triggers and from the system tick carry `on_behalf_of_user_id = null`, so they get the agent's credential, and a run started by another run keeps its parent's person. That is the chain case, and it is tested through the real runs service. M2.2's OAuth clients produce user principals and resolve as that person.

The one gap is a guarantee the overview states and the server does not enforce: a Connect link that writes an agent-owned credential works from anywhere, not only from the agent's page.

I did not count three items that wait by decision or on someone else. The Slack needs-auth ephemeral moved to M5.2. The staging `--sleep 240` call waits for O.1. The real-provider refresh waits for Dom.

Checks run in `/home/roboto/devel/harbourmaster-wt/review-M3-0d04585`: `bun install --frozen-lockfile`, `bun run check`, `bun run test` and `bun run build` all passed. Grepping `apps/web/dist/client` for `drizzle` found nothing. Neither migration 0006 nor 0007 touches `events`. No new binding was added, so the three-places rule for `wrangler.jsonc` does not come up.

## Must-fix scope

### 1. Agent-owned Connect only from inside Harbourmaster

Scope: in `packages/services/src/connector-oauth.ts` `start`, or in the `/connect/:connectorId` route in `apps/web/src/server/routes/connectors-oauth.ts`, refuse to start a flow for `as=agent:<id>` unless the navigation came from Harbourmaster itself. Take the smaller of these two fixes:

- Require `Sec-Fetch-Site: same-origin`, or, when that header is missing, a `Referer` whose origin matches the request. Any other request is redirected to `/agents/<id>?tab=connectors` and inserts no `oauth_states` row and registers no client.
- Have a GET with `as=agent:<id>` render a confirmation page that names the agent and the connector. Only a same-origin POST from that page starts the flow.

`as=user` stays as it is, because it can only ever bind the clicker's own row. The proxy's needs-auth text and `connectPath` may keep the `/connect` path, since the redirect now lands on the agent page. Pointing the agent case at `/agents/<id>?tab=connectors` directly is also acceptable. Update the agent tab's "Connect as this agent" link if the POST variant is chosen.

Check: in `apps/web/src/server/routes/oauth-callback.test.ts`:

- `GET /connect/:id?as=agent:<id>` from a signed-in member without same-origin fetch metadata redirects to the agent page, and `oauth_states` stays empty with no registration call at the stub.
- The same GET with `Sec-Fetch-Site: same-origin` (or the confirmation POST) redirects to the provider with a state row whose `owner_kind` is `agent`.
- `?as=user` without fetch metadata still redirects to the provider.
- The existing tests (a different initiator gets 403, an off-site `return_to` gets 400, a non-member's `?as=agent` is refused) still pass.

`bun run check && bun run test && bun run build` pass.
