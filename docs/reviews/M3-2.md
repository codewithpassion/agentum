## Verdict

Clean. Nothing is must-fix.

Round 1's must-fix is resolved. `GET /connect/:id?as=agent:<id>` now starts a flow only when `Sec-Fetch-Site` is `same-origin`, or, when that header is missing, when the `Referer` origin matches the request. Any other request is redirected to `/agents/<id>?tab=connectors` before the service runs, so no `oauth_states` row is written and no client is registered. `?as=user` is unchanged. The route is the only caller of `connectorOAuth.start`, and the route and the service both match the `agent:` prefix exactly, so no other spelling of `as` reaches the agent branch without passing the gate. The agent tab's "Connect as this agent" control is a plain `<a href>`, so a click on it sends `Sec-Fetch-Site: same-origin`. The redirect target names a real tab id (`connectors`).

Every check in the M3.4 task has a test in `apps/web/src/server/routes/oauth-callback.test.ts`. A request without fetch metadata goes to the agent page with no state row and no registration call. `Sec-Fetch-Site: same-origin` starts the flow with `owner_kind = agent`. A same-origin `Referer` starts it. A foreign `Referer` or `cross-site` is refused. `?as=user` works without metadata. The existing tests (other initiator, off-site `return_to`, non-member) now send `same-origin` and still pass.

Since round 1, M5.1 and M6.1 landed. Neither changes M3 code apart from `compose.ts`, which now passes `connectorFetch` and `PUBLIC_BASE_URL` to the new Slack services. The new inbox page renders post text as plain text, so a needs-auth path quoted in an inbox post is not a clickable same-origin link. No round 1 nit got worse.
