# M7 gate review at 40929cd

Scope: M7.1 (files service, routes, composer upload) and how M1.6 and M1.9 use it in the daemon. Checked against docs/architecture/build-plan.html#m7, the three task files, CLAUDE.md in the checkout, and "Rules that are easy to break" in docs/HANDOVER.md.

## Verdict

Not clean. One must-fix. The files service, routes and daemon side are sound. The service takes `{ db, blobs, clock }` and reads no `env`. It is built in `composeWith`. Every refusal on `GET /files/:id` is 404. Run tokens only work while the run is `running`. Cross-workspace and cross-user attachment is refused in `startRun` through `requireFiles`. The daemon vets paths lexically and by realpath, and on multi-user machines it does every file step as `hm-agent`. The must-fix is in the chat. A file the agent hands back shows as a chip only for the latest run, and the raw `[ATTACHMENT:path]` marker stays in the assistant bubble. So "file chips on messages" holds for the user's own uploads but not for the agent's output.

## Must-fix 1: agent output files as chips on their messages

Scope: in the chat, show each run's output files as chips on that run's reply, for every run in the session, not only the latest. Remove the `[ATTACHMENT:...]` markers from the assistant text the chat shows. One way is for `sessions.transcript` to return `outputFileIds` per run (or include `run.finished` entries, whose payload already carries `outputFileIds`). `toChatItems` then attaches them to the last assistant item of that run and strips markers from assistant text. The marker regex moves from `apps/daemon/src/attachments.ts` into `@repo/protocol`, which the daemon already imports, so the daemon and the chat share one copy and it cannot drift. The separate "Files from the agent" block goes away, or stays only for a run without an assistant message. The changes go in `packages/protocol`, `packages/services/src/sessions.ts` and `apps/web/src/components/agent/chat/`. In the daemon, only the import of the regex changes. (Confirmed: the bubble text comes from the streamed `message.assistant` events, and the `none` reply gateway the chat uses writes nothing from the stripped completion text.)

Check: a `chat-logic.test.ts` case with two runs in one session, each with an output file. Both chips appear under their own assistant items, and an assistant text `"Here [ATTACHMENT:/w/report.md]"` renders as `"Here"`. A `sessions.test.ts` case shows the transcript carries both runs' output ids. Browser (dev login, `fake` runtime, or a completion posted with `fileIds`): after a second message, the first run's output chip is still visible and opens the file.
