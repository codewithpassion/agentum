## Findings

### Must-fix

1. must-fix. `apps/web/src/server/pi-run-mcp.ts:58-99` and `:249-259`. The MCP bridge assumes every server is stateless ("The servers are stateless, so no session id is kept", line 86). It never reads `Mcp-Session-Id` from the `initialize` reply, never resends it, never sends `notifications/initialized`, and `tools/call` goes out with no `initialize` at all. That holds for the platform's own `/mcp`, but not for connectors. The proxy forwards `mcp-session-id` both ways (`apps/web/src/server/routes/proxy.ts:38-49`), and the platform's own connector client tracks it (`packages/services/src/connectors/mcp.ts:141-174`), so stateful upstreams are an expected shape. A Streamable HTTP server built with the official SDK in stateful mode answers 400 to `tools/list` and `tools/call` without a session id. `syncMcpTools` then logs a warning and drops the connector (`pi-run-mcp.ts:139-146`), so the connector's tools silently vanish from cloud runs. The staging check (`staging-cloud-check.md` step 5) used `scripts/dev/stub-mcp.ts`, which has no session handling, so it could not catch this. Fix: keep the session id per server from `initialize`, send `notifications/initialized`, send the id on later calls, and re-initialize on a 404 or 400 for a lost session. Add a test with a fake server that requires the session id.

2. must-fix. C.3 scope "steer for a second message in a busy session" isn't delivered, and the second message waits for the sweep. `packages/services/src/runs.ts:604-616` allows one running run per agent, across all its sessions. `packages/services/src/cloud/runtime.ts:103-105` returns quietly on the claim conflict. Nothing offers the next waiting run when a cloud run ends (`apps/web/src/server/pi-run-core.ts:240-250`, `:394`). Managed has `offerNext` for this (`packages/services/src/managed/service.ts:619-635`). So the steer path in `pi-run-core.ts:461-475` never runs in the normal flow. A follow-up message, or a message in any other session of the same cloud agent, waits until the minute sweep picks it up (`runs.ts:1219`, only runs older than 60 s, plus the tick), which is 60 to 120 s. Known and deferred: C.2 nits 6 and 10 (`docs/reviews/tasks/C.2.md:22,26`), C.3 (`docs/reviews/tasks/C.3.md:46`, "If Dom wants real steering..."). Neither the task log nor HANDOVER records a decision from Dom, so taken at face value the C.3 scope is open. Fix: either offer the next waiting run of the agent after a cloud run completes (as managed does), and make the busy rule per session if steering is wanted, or get Dom's decision recorded and C.3's scope amended.

### Nits

3. nit. `docs/reviews/tasks/C.1.md:9,35`, `docs/reviews/staging-cloud-check.md`. The C.1 check "Worker startup under 1 s on staging" and the spike's step 3 (CPU time per turn from `wrangler tail`) aren't recorded anywhere. Staging deployed, and Cloudflare refuses a deploy over the startup limit, so the limit holds. The figure is still missing.
4. nit. `packages/services/src/runs.ts:654-675`. `releaseRun` writes no event, so a released and re-claimed run logs `run.started` twice (C.2 nit 1, still open).
5. nit. `apps/web/src/server/pi-run.ts:124`. The Durable Object calls `managedKeys.resolve(workspaceId)` with no principal and no `authorize()`. CLAUDE.md says a service method that reads workspace data takes the calling principal. This follows M8.1's API (`packages/services/src/managed/keys.ts:231-252`). Record it as a decision next to the `SYSTEM_PRINCIPAL` one, or pass a principal.
6. nit. `apps/web/src/server/pi-run-mcp.ts:65-74`. No timeout on the bridge's fetches. The proxy caps connector calls, but a stuck `/mcp` (initialize or tools/list during `installTools`) keeps the `startRun` RPC and the dispatch waiting with no limit. Add `AbortSignal.timeout`, combined with the tool's abort signal.
7. nit. `apps/web/src/server/pi-run-mcp.ts:226-231`. Connector image or resource content becomes the text `[image]`, so the model never sees it, although Pi tool results can carry image blocks. The cloud form text (`apps/web/src/components/agent/agent-form.tsx:186-195`) doesn't say so. The managed text does.
8. nit. `apps/web/src/server/pi-run-mcp.ts:209-224`, `:244`. Tool names are de-duplicated within one server only. If a connector's `<slug>_<tool>` equals a built-in tool (`read`, `write`, `edit`, `read_input_file`, `activate_skill`, `read_skill_resource`), or two names collide after the 64-character cut, the registry refuses the repeat. Then `installTools` throws, the start throws, and the run is released and re-offered every minute until the 1 h expiry. Rare, but nothing guards it.
9. nit. `apps/web/src/server/pi-run-core.ts:540`. After 12 h (`RUN_TOKEN_MAX_AGE_MS`) the object stops heartbeating. The reaper then marks the run `interrupted` about 10 minutes later, and nothing says why. Same cap as machine runs, but a cloud run can actually live that long.
10. nit. `apps/web/src/components/agent/agent-form.tsx:1`. A React component imports `@repo/services/cloud/models`. CLAUDE.md says components get shared constants from `@repo/db/shared`, and the app reaches services through tRPC. The module imports nothing, and boundary-lint and the drizzle grep pass, so this is a layering nit only.
11. nit. `apps/web/src/components/agent/agent-form.tsx:186-195`. The text says the agent has "no local files" but doesn't mention that Pi's `read`, `write` and `edit` work on `/library` (C.8). The cloud option also shows on PR previews, where `compose` never registers the cloud adapter (`PUBLIC_BASE_URL` is `""`, `apps/web/src/server/compose.ts` cloud runtime guard). There, a first message fails with "No runtime is registered for cloud agents".
12. nit. `apps/web/src/routes/_app/settings.managed-agents.tsx:98`. The page describes the Anthropic key as the managed agents' key. Cloud agents depend on it too, and `apps/web/src/server/pi-run-credentials.ts:3-4` sends users there. Removing the key there silently stops every cloud agent as well. Say so on the page.
13. nit. Spike section 2 suggested a unique index on `events(run_id, seq)`. It wasn't added (`events_run_idx` stays non-unique). Correctness rests on the serial flush inside one object (`pi-run-core.ts:335-365`) and on one object per session. Fine today, but a concurrent writer would duplicate rows silently.
14. nit. `packages/services/src/cloud/runtime.ts:45-55` copies the connector query from `managed/service.ts`. The busy and older-run conditions now exist in `runs.ts`, `runs/machine-claim.ts` and `managed/service.ts` (C.2 nits 4 and 5, still open).
15. nit. `apps/web/src/server/pi-run.ts:466-468`. `RUN_KEY` (library principal for Pi's file tools) and `SKILLS_KEY` are written before `runCore().start()` and are never cleared. A late duplicate start of an older run moves attribution back to it (C.8 review note, still open). Authz checks only the workspace, so only the run id on library events is affected.
16. nit. Release path. `apps/web/package.json` `deploy` doesn't apply D1 migrations, and `0001_faithful_kulan_gath.sql` (M8.1) must go out first. `PiRun` and `ManagedPoller` are new DO classes, so the first production release must use `wrangler deploy`, not `versions upload`. Both follow existing rules. They belong in Dom's production release steps, which no file in the range lists.

## Things checked and found sound

- Exact pins in `apps/web/package.json` and HANDOVER's rule to run `e2e:pi-durability` on every bump. `pi-tool-result.test.ts` pins the `output` result shape (C.1).
- `PI_RUN` binding in all three places. Migration tags `v1`, `v2` (`PiRun`), `v3` (`ManagedPoller`) at the top level only. No shipped tag was edited.
- `claimRun` older-run and busy conditions, `releaseRun` limited to `running` + `system`, and the release on a failed start (C.2). Tests cover dispatch, claim race, failed start and cancel.
- Event translation is sliced per run by user entry, seq comes from position in the slice so a replay is a no-op, flushes are serial, completion is retried and outputs are uploaded once (C.3).
- Lease: 10 min cloud lease, a 20 s alarm heartbeat owned by a Lifecycle job that survives eviction, a failed beat re-arms. The run token stays valid through an outage shorter than the lease (C.4).
- Self-fetch to the public origin, confirmed on staging. A down connector keeps its last tools or drops out without failing the start (C.5).
- The model key is resolved per request through a read-only `CredentialStore`, never stored in the object, and the Worker's env vars are kept out of auth (C.6).
- Skills, input images under a 1.2 MB cap, `read_input_file`, output markers through library upload (C.7). The library `ExecutionEnv` has no shell, and paths clamp to `/library` (C.8).
- Dev-only `faux` and `dev_slow_read` sit behind `import.meta.env.DEV`. `check-dev-only.ts` runs in `build` and `staging:build`, and passed here (C.10). `/api/dev/cloud/*` is mounted only in dev.
- Unknown model fails with a message that names the model and the valid list. Instructions are set through `root.configure` before an idle submit (C.11).
