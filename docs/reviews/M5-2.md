# M5 gate review, round 2

Commit 445d6b0 (main). Round 1 was at 05b66b0 (docs/reviews/M5-1.md). M5.4 merged as 61e635c (commits fc85372, 84aa49f, eea11a2).

## Verdict

Clean. Nothing is must-fix.

Round 1's must-fix is resolved. Migration 0014 adds `sessions.private` (boolean, `NOT NULL DEFAULT false`), and its snapshot chains onto 0013. The Slack service sets `private: event.trigger === "dm"` (`packages/services/src/slack.ts:260`), and `startRun` writes it with the session row inside the existing atomic write (`packages/services/src/runs.ts:431`). `visibleSessions` treats a private session like a `ui` one (`packages/services/src/sessions.ts:146-161`). So `sessions.list`, `sessions.transcript`, `sessions.search`, MCP `list_sessions`, `read_session` and `search_sessions`, and the user path of `getRun` and `cancelRun` (`runs.ts:209-232`) all hide another user's DM. The task review also caught a write path that the round 1 scope missed. `findSession` now refuses another actor's private session (`packages/services/src/runs/queries.ts:75`), so `runs.start` cannot join someone else's DM by its key. A test covers it in `runs.test.ts`.

Every check in the task file has a test. `sessions.test.ts` covers u2's DM, which is hidden from u1 and from a run on behalf of u1 in both list and transcript, and visible to u2. The same test shows the channel thread visible to both. The old shared-session test now uses a channel thread. `slack-events.test.ts` shows that a DM fixture sets `private = true` and a mention fixture does not. `mcp.test.ts` shows `read_session` returning `not_found` to a run on behalf of another user and the transcript to the owner's run.

Read as a whole against the build plan's M5 section, the Slack work still matches what round 1 found. The only code that changed since round 1 is M5.4 and the unrelated M4.3 sweep-window change. The events service has no user-facing reader of its own. Its only reader is `sessions.transcript`, which applies `visibleSessions` first (`packages/services/src/sessions.ts:253`), so DM events do not leak around the new rule. The four new findings are nits. Three are about where DM privacy stops: at run ids, at delegation, and at private Slack conversations. One is a squat that the new private check makes possible. Each one needs an id or key the caller should not normally have, or matches how `ui` sessions have behaved since M2.4, or is a choice the build plan made on purpose.

Checks run in a fresh worktree at 445d6b0 all passed. `bun install --frozen-lockfile` and `bun run check` passed, with ultracite, typecheck and boundary-lint clean. `bun run test` passed in every package: services 705, web 336, daemon 265, mcp 57, protocol 44, db 12, scripts 90, with 0 failures. `bun run build` in `apps/web` passed, and a grep of `apps/web/dist/client` for `drizzle` found nothing. Staging and the live Slack checks for M5.2 and M5.3 still wait for O.1 and Dom. Migration 0014 must go to remote D1 with the next deploy, as the M5.4 review says.

## Findings

| # | Severity | Finding | Area | Resolution |
|---|---|---|---|---|
| 1 | nit | `requireVisibleSession` applies only to user principals (`packages/services/src/runs.ts:213-215`). Any run of the same agent can therefore `get_run` a run in another user's DM and read its `resultText` (`runs.ts:827-846`). That includes a run started from a public channel on behalf of someone else. It needs the run id. Inbox posts show run ids (`packages/mcp/src/tools/inbox.ts:21`), so a DM run that posts to the inbox exposes its id. M2-1 raised this for user principals and M2.4 fixed that path. M2.4 kept run principals open on purpose, and DMs now add a second kind of private session behind that gap. | sessions | In `requireVisibleSession`, apply `visibleSessions` to run principals as well (it already resolves `onBehalfOfUserId`), unless the run is the parent of the target. Test that a run on behalf of u1 gets `not_found` for a run in u2's DM, and still reads the child run it started. |
| 2 | nit | Privacy does not follow delegation. When a DM run calls `send_message`, the child run gets a new `origin: "mcp"` session with `private = false` (`apps/web/src/server/mcp/ports.ts:193-197`). That session holds the delegated text and the answer, and every user sees it in the target agent's Sessions tab. `ui` sessions have behaved the same way since M2. The content leaves the DM only when the agent sends it on. | sessions | Have `startRun` set `private` on a new child session when the parent run's session is `ui` or private, with the same opener. Or record that delegated runs are shared by design. Test both outcomes. |
| 3 | nit | M5.4 lets a member block a Slack or inbox session in advance. tRPC `runs.start` takes `startRunInputSchema` unchanged (`apps/web/src/server/trpc/runs-router.ts:11-15`), so a browser caller picks any `origin` and can set `private` (`packages/services/src/runs/types.ts:64-67`). A member who knows a future key can create that session as private first. Two such keys are a Slack thread under an existing channel message (`team:channel:parentTs`) and an inbox thread id for an agent that has not been woken in it yet. When the real Slack mention or inbox wake arrives, `findSession` treats it as foreign and answers `not_found` (`runs/queries.ts:75`), and that thread stops reaching the agent. Before M5.4 the same squat created a shared session that the real sender then joined. The M5.4 review recorded only "can hide the caller's own session". | runs | Narrow the router's input to `origin: "ui"` with no `private` field, so only in-process callers (Slack, inbox, triggers) set them. Add a `runs-router` test that `origin: "slack"` and `private` are rejected. |
| 4 | nit | A mention in a private channel or a group DM (`mpim`) starts a shared session (`packages/services/src/slack.ts:260`, `packages/services/src/slack/event-parse.ts:221`). Every workspace user then sees content that Slack shows only to that conversation's members. The build plan keeps channel threads shared, and `app_mention` carries no `channel_type`, so telling these cases apart would take a `conversations.info` call. | slack | A decision for Dom. Either record that channel-thread sessions are workspace-visible whatever the Slack conversation's privacy, or mark sessions from private channels and `mpim` as private after a `conversations.info` lookup at admission. |

Not re-raised: round 1 nits 2 to 7 still stand unchanged. The M5.4 task-review nits also still stand: the always-true `dm.sessionId` assertion, `private` being settable through `runs.start`, and no backfill for DM sessions created before 0014.
