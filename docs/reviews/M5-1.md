# M5 gate review, round 1

Commit 05b66b0 (main). M5 merges since `m5-start`: ab7dcfd (M5.1), 2e75227 (M5.2), aca1c44 (M5.3, whose last commit bcaaf7d is the merge that added the attachment-marker strip).

## Verdict

Not clean. One must-fix.

The M5 work matches the build plan's M5 section. The events route caps the body at 256 KB, looks the app up by `api_app_id`, checks the signature and `team_id`, and writes the dedupe row, the run, its events and any `pending_files` in one atomic write before the 200. Mentions and DMs become `origin: "slack"` runs with session key `team:channel:threadTs` and a `{ kind: "user", via: "slack" }` principal. Unlinked senders, file downloads with the sweep and the three-attempt limit, the gateway's threaded reply with retry, the private Connect link, the paste flow with encrypted secrets and revoke, and `files.uploadV2` uploads are all in place and tested.

The needs-auth ephemeral carried from M3.3 works in production as well as in the test. The proxy records `connector.needs_auth` through `c.get("composed").services.events.append` (`apps/web/src/server/routes/proxy.ts:495`, `:268`). That is the instance `composeWith` registers `notifyNeedsAuth` on (`apps/web/src/server/compose.ts`).

The attachment-marker strip (`packages/services/src/slack/gateway.ts:249-262`, `packages/protocol/src/attachments.ts`) is correct. It runs before the Connect-link search and before the empty-text check. It uses the shared helper the daemon and the chat already use, and it closes M7-2 nit 1 for Slack: the daemon's fallback completion can no longer post an absolute machine path into a thread. Its two gateway tests and the four protocol tests pass. What remains are nits about the fallback path and the empty-text post.

The must-fix comes from how M5 fits the rest. `visibleSessions` keeps only `origin: "ui"` sessions private. Every Slack session is shared, including DMs, so one person's DM with an agent can be read by everyone in the workspace and by any run of that agent.

Checks run in a fresh worktree at 05b66b0: `bun install --frozen-lockfile`, `bun run check` (boundary-lint clean), `bun run test` (all packages pass: services 702, web 334, daemon 265, mcp 57, protocol 44, db 12, scripts 90), and `bun run build` in `apps/web`. A grep of `apps/web/dist/client` for `drizzle` found nothing. The staging and real-Slack checks for M5.2 and M5.3 wait for O.1 and Dom.

### Must-fix 1: Slack DM sessions are private to the sender

Scope: a session opened by a Slack DM is visible only to the user who sent it, the same rule `origin: "ui"` sessions follow. Channel-thread sessions stay shared. The Slack service knows the trigger (`event.trigger === "dm"`, from `channel_type: "im"`). Pass a privacy flag from the Slack service through `startRun`'s session input to the `sessions` row, for example a nullable `private` column, or a `slack_dm` origin if contract C3 may change. Make `visibleSessions` (`packages/services/src/sessions.ts:146-158`) treat that flag like `ui`: visible to `actorId`, and to a run only when the run's `onBehalfOfUserId` is that user. A schema change means `bun run generate` and committed migrations. `getRun` and `cancelRun` already reuse the rule after M2.4, so they follow. Change `sessions.test.ts:234-252` to start the shared session as a channel thread, so it still asserts what it means.

Check: in a `sessions.test.ts` case, user u2's DM session is missing from `sessions.list` and `sessions.transcript` for user u1 and for a run on behalf of u1, and is present for u2. A channel-thread Slack session stays visible to both. A `slack-events.test.ts` case sends a DM fixture and checks that the resulting session carries the privacy marker, and that a mention fixture's session does not. An MCP `read_session` from a run on behalf of another user returns not-found for the DM session. `bun run check && bun run test && bun run build` pass.

The nits in `docs/reviews/tasks/M5.1.md`, `M5.2.md` and `M5.3.md` still stand and are not repeated here: the 30 s `waitUntil` ceiling on large uploads, no re-check of org membership at message time, the unlinked-sender reply without a rate limit, and the needs-auth dedupe keyed on events. None of them rises to must-fix at the gate.
