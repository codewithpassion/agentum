# M1 gate review, round 1, commit cf03abe

## Verdict

Not clean: 1 must-fix, 16 nits.

The milestone mostly does what it set out to do. On this box, with the compiled daemon (`apps/daemon/dist/harbourmaster`, single_user) against `vite dev`:

- `bun scripts/e2e/skeleton.ts` passed (Pelican, heron, heron after resume).
- A browser run of the milestone goal passed: dev login, enrol code from the Machines page, `harbourmaster enroll` and `run`, create agent "Pelican" with machine runtime, send a message, and the transcript showed "Pelican" with status Done about 6 s later.
- CI steps all pass from a clean checkout: `bun install --frozen-lockfile`, `bun run check`, `bun run test` (daemon 188, web 98, services 161, protocol 40, db 12, mcp 6, scripts 50), `bun run build` and the `drizzle` bundle grep.

The must-fix sits where M1.3 meets M1.4. When the daemon stops a run on its own, it posts `complete { status: "aborted" }` while the server still has the run as `running`. That happens on SIGTERM, a 1012 close and every `systemctl restart`. The server refuses the call with 409 and the daemon swallows the 409. I reproduced it live: I sent a message that runs `sleep 60`, sent SIGTERM to the daemon, and saw the following. The daemon logged "completed as aborted". The row stayed `running` until the lease ran out. The reaper then made it `interrupted` with `process_ended_at` empty. The chat showed "Interrupted. The process may still be running." with Retry and Send both disabled for ten minutes. The architecture (`docs/architecture/index.html` around line 1494) says the daemon posts `aborted` once the process has exited after a 1012, and that the UI offers Retry after that, so the intended unlock never happens. The contracts freeze at this gate, so the semantics of `aborted` should be settled now.

## Must-fix 1: an aborted completion from the claiming machine ends a running run

Scope: in `packages/services/src/runs.ts` `completeRun`, when `status` is `aborted`, the run is `running` and the caller passed `authorizeRunWrite`, do one conditional write (`WHERE id = ? AND status = 'running'`). It sets `status = 'interrupted'`, `finished_at`, `process_ended_at` and `error = "Aborted by the machine"`, and then appends `run.interrupted`. An aborted call on an `interrupted` run keeps today's behaviour, and a repeat on either path still gets 409. Remove the wrong comment at `apps/daemon/src/run.ts:134`, or make it true. Update the C4 line in `docs/architecture/index.html` (around 1538) and the matching sentence around 1485 so that they say `aborted` is accepted for a running run from the machine that claimed it, and for an interrupted run. The daemon code stays as it is.

Check:

- A service test: claim a run as machine A, then `complete { status: "aborted" }` makes it `interrupted` with `process_ended_at` set and a `run.interrupted` event. A second aborted call gets 409. The same call from machine B gets 403.
- `runs-machine.test.ts`: after an aborted completion of a running run, the run token is refused by the proxy resolver, and the agent's next queued run can be claimed at once.
- Live: start a run that runs `sleep 60`, send SIGTERM to the daemon, and within a few seconds the row is `interrupted` with `process_ended_at` set, and the chat's Retry and Send are enabled.
