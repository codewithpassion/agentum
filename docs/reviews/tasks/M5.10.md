# M5.10 review: Slack agent view scope and event, and a working status

Branch task/M5.10-slack-agent-view-status. Final head is recorded in the dispatcher report.

## What changed

- The manifest asks for the `assistant:write` scope and subscribes to `app_home_opened`. The events route already answers an event type it does not handle with a 200 and starts nothing, so `app_home_opened` and any unknown type (tests use `team_join`) get a 200, no run, no events row and no Slack call. Tests in `event-parse.test.ts` and `slack-events.test.ts` pin that.
- A run that replies in a Slack thread (mention, DM, thread reply) shows "is thinking…" when it is accepted, a short tool label on each tool call ("is reading files…", "is editing files…", "is running a command…", "is searching Slack…", "is searching the web…", "is working…"), and the status is cleared when the run fails, is cancelled or is interrupted, or when posting the reply fails. A posted reply clears the status by itself.
- Code: `packages/services/src/slack/status.ts` (the tracker and its database ports), `SlackClient.setStatus` in `client.ts`, `onEvent` on the runs service, the wiring in `compose.ts` and `admitRun` in `slack.ts`.
- Migration 0010 adds `slack_status_at`, `slack_status_label` and `slack_status_stopped` to `runs`.

## Why the state is on the run row

The first version kept the 5 second limit and the "stop trying" flag in memory. Review round 1 found that every request builds its own services (`compose()` per request in `server.ts`), so a machine run, whose events arrive in separate HTTP requests, would get a status call per batch and a warning per request. The limit and the flag now live on the `runs` row and are taken with one conditional UPDATE, so they hold across requests and isolates. A tool call or `run.started` of a run that does not reply in Slack costs one UPDATE by primary key that matches nothing.

## Where `setStatus` works

Checked on docs.slack.dev on 19 Oct 2026. `assistant.threads.setStatus` takes `channel_id`, `thread_ts` and `status`, and an empty `status` clears it. It accepts `assistant:write` or, for now, `chat:write`. The page ties the method to assistant threads in the agent messaging experience and does not say whether a thread in an ordinary channel works. It lists the error `method_not_supported_for_channel_type` for conversations it refuses, and it names `agents.sessions.setStatus` as the current method. That newer method takes only the enum statuses `active`, `processing`, `suspended` and `closed`, with no free text, and it does support `thread_ts` in regular channels and DMs.

The app calls the legacy method for every Slack-started run and skips it quietly where Slack refuses: on `method_not_supported_for_channel_type` the run's status stops with no warning. Any other failure (`missing_scope`, `ratelimited`, a network error, no bot token) logs one `console.warn` with the code, per run, stops the status for that run, and never fails the run. Whether channel threads accept the call is unverified. The staging check shows it.

## Existing apps need the manifest regenerated

An app installed before this change has neither the scope nor the event. A workspace owner opens the agent's Slack app in Harbourmaster, copies the regenerated manifest, saves it in Slack's manifest editor, and reinstalls the app. Slack accepts `chat:write` for `setStatus` for now, and the app already has it, so the status may work before the reinstall. If Slack answers `missing_scope`, the app logs one warning per run and the run goes on without a status.

## Verdicts

- Round 1 (2fdfb7f): must-fix. The status state was per request, so the 5 second limit and the stop flag did not hold for machine runs, and the tests used one compose for a whole test.
- Round 2 (defa34d): clean. The state moved to the `runs` row and the tests build a fresh compose per request.

## Nits left

- A `tool.call` ingest in flight while the run completes could win a claim after the reply is posted and leave a status that nothing clears until Slack drops it after 2 minutes. Marking the run stopped on `run.finished` would close it, but then a failed delivery could not clear (the `slack.delivered` handler relies on `finish` flipping the flag).
- After a mid-run send failure (rate limit) the later `run.failed` or `run.cancelled` sends no clear, so the last label stays until Slack times it out.
- Sends run inside the request that wrote the event unless `compose` gets a `defer`. Only the HTTP middleware passes one. The Pi Durable Object, the managed poller, the Linux VM session and the scheduled handler compose without it, so a slow Slack holds that write for up to the 10 second client timeout. Sends are limited to one per 5 seconds per run.
- Deferred sends can arrive out of order, so a clear can reach Slack before an earlier label, and `begin` now runs beside the run offer, which makes that slightly more likely for a run that fails within milliseconds.
- The `.catch` around `status.begin` in `admitRun` cannot run, because `begin` catches its own errors.
- No test claims concurrently. Atomicity rests on the single UPDATE.
- A batch run (M5.9) has reply kind `none` and answers through `slack_send`, so it has no thread to show a status in. The task lists "an M5.9 batch that replies"; there is nowhere to put it, so batch runs show no status.

## Beyond scope

- Refresh "is thinking…" while a run waits a long time with no tool call. Slack drops a status after 2 minutes without a message. `run.started` re-sends it once, but a long model turn can still outlast it.
- Move to `agents.sessions.setStatus` if Slack retires the legacy method, at the price of the free-text labels.
- Pass `waitUntil` into the compose calls in the Durable Objects and the scheduled handler, so listeners never hold a write.

## R.2

R.2 (turn limit, repeat guard, cancel) was built in parallel. The status clears on cancel through the `run.cancelled` event that `cancelRun` writes with the runs service's events instance, which R.2 keeps. R.2's safeguard stops write `run.limit_reached` or `run.repeat_stopped` and then `run.failed`, and the `run.failed` clears the status, so no follow-up hook is needed. If R.2 or a later task ends a run without one of `run.failed`, `run.cancelled` or `run.interrupted` written through the runs service, the status stays until Slack drops it, and that path needs a call to the status tracker. `runs.test.ts` conflicts textually with R.2's branch: both append tests at the end of the file, so the merge keeps both blocks.
