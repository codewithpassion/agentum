# V4.6 review record

Library change announcements: a library write now reaches the running runs whose sync scope covers a changed path, and a `library.prune-versions` job runs on the minute tick.

## Verdicts

Round 1 (d696172): not clean. Two must-fix items. Durable Objects (`PiRun`, `ScriptHost`) composed services without `defer`, so the notifier ran inline inside their library writes, and a session syncing out under the VM library lock could make every write wait 30 seconds on another session's pull. The audience matched only `running` runs, so a run `waiting` on a person kept a stale working copy. Fixed in 98e5a5b: both objects pass `this.ctx.waitUntil` as `defer`, and the audience matches `running` and `waiting`.

Round 2 (98e5a5b, fix commits only): clean.

## Decisions

- The app cannot import `@repo/db/schema/*`, so the run lookup is `createLibraryAudience` in `packages/services/src/library/audience.ts` (export `@repo/services/library/audience`). `library-notifier.ts` takes it as a dependency.
- A machine run is found by `runs.claimed_by`. A cloud run is announced only when it is in a Linux VM and not a dry run, because an isolate reads the library directly. `PiRun.libraryChanged` still does nothing for an isolate, as the task says.
- Paths are merged per machine and per VM session, so a machine with two covered runs gets one frame.
- `CloudRunnerPort.libraryChanged` is optional, like `answered`. `PiRun` stores the agent's `runtimeConfig` under a new key in `#prepareRun` so `libraryChanged` can run the existing full `syncLibraryIn`.
- A daemon's features live in the socket attachment, so they survive Durable Object hibernation.

## Nits left

- `PiRun.libraryChanged` syncs `librarySyncRoots` (home plus legacy `runtimeConfig.libraryPaths`), while the audience picks runs by `librarySyncScope` (home, wiki, grants). A wiki change triggers a full sync that does not cover the wiki, and a legacy path that is not a grant never reaches the VM run. V4.7 removes the legacy roots and should close this.
- Each change starts a full `syncLibraryIn` in every VM session. Sessions of one agent share a VM and repeat the same work, and a burst of writes queues on the 30 second lock wait. V4.7's `only` narrowing reduces this.
- The mid-run sync stores `ready: false` first, so the prompt stops mentioning the VM copy while it runs, and for good if it fails.
- A run already in flight at deploy has no stored `runtimeConfig`, so it gets no mid-run sync until its next start.
- In a request, `defer` is `waitUntil` (about 30 seconds). A long `libraryChanged` RPC may outlive it. Nothing documents whether the object finishes the sync when the caller is cut off.
- The writer's machine still gets the frame when it runs another covered run. This relies on the daemon treating a pull of its own write as a no-op, and no test covers it.
- No test checks that `PiRun` and `ScriptHost` pass `defer`.
- `trpc/context.ts` `createSsrContext` composes without `defer`. SSR loaders do not write to the library.

## Ideas beyond the scope

- Skip the VM sync when none of the announced paths falls under the run's own roots.
- Send the paths to `libraryChanged` as `only` once V4.7 lands, and drop duplicate syncs for sessions that share a VM.
