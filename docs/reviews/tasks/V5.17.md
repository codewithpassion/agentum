# V5.17 review

A failed release after Allow once now keeps the message `failed` with its error, and the approval's settled line says the send failed.

## What changed

`mail_messages.last_error` (migration 0023) holds the release error, capped at 500 characters. In `applyDecision`, a throwing `release` writes `status = failed`, `last_error` and `request_id`, appends a `mail.failed` event in the request's session (payload: `requestId`, `error`, `messageId`, `threadId`, `address`), and rethrows so the event listener still logs it. `mail.failed` joins `STREAM_EVENT_TYPES`, so the task view gets it live and on load.

`requests.answer` returns `sendError` for a mail approval (`mailSendError` in `mail/approval.ts`), which is the services-level settled view. On the web, `Settled` has an optional `sendError`. `settledLine` reads "Allowed once by Dom in the web app, but sending failed: <error>". `requestViews` adds the error from `mail.failed` events, and the task page passes the answer's `sendError` so the line is right before the stream catches up. The desk drops an answered card at once, so its route shows an alert with the error.

The mail was already `failed` in V5.5, so the Failed chip in the Mail sheet is unchanged. There is no per-message Retry in the Mail sheet (only the mailbox provisioning Retry on the profile header), so none was added. The task file's line "The Mail sheet's Retry stays available for it" has nothing to keep.

## Verdict

Round 1 (3e4455b): clean, 9 nits, none must-fix. Zero fix rounds.

## Nits left

- `requests.ts` `sendError` comes from `last_error` without the masker `scrubbedRecord` applies. The error text comes from the Cloudflare send path, so the risk is low.
- If appending `mail.failed` throws, that error replaces the release error in the listener's log.
- The test "a sent or denied mail has no send error" covers the sent case only. The session assertion on `mail.failed` cannot catch a wrong session because the fixture's thread and request share one.
- The desk alert has no dismiss and does not name the mail. It stays until the next successful answer.

## Ideas beyond the scope

- Show `last_error` in the Mail sheet next to the Failed chip (`approvalNote` in `sheets/mail-logic.ts`).
- Mark the receipt step of the approval `failed` on `mail.failed` (`tasks/receipt.ts`).
- The map page and Slack answer paths ignore `sendError`. A Slack card still settles as allowed.
- A per-message Retry for a `failed` held mail would need a re-hold or re-send path in the mailbox port. Decide whether wanted.
