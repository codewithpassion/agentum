# M5.3 review

## Verdicts

Round 0, commit eafaa17: not clean. One must-fix, nine nits. File uploads ran inside the machine's `/complete` request, whose daemon timeout is 30 s.

Fix round 1, commit 7827009: not clean. The fix moved the whole Slack delivery to `waitUntil` when the run has output files (`Infra.defer`, wired in `server.ts`). The reviewer's must-fix was that `waitUntil` also stops at 30 s, so a long delivery loses uploads and the `slack.delivered` event.

Fix round 2, commit bd73e37: clean, four nits. A delivery stops starting uploads 20 s after it began, and names each skipped file in the event's `error`.

After round 2, the controller passed on an M7 gate finding. The daemon can send the completion text with raw `[ATTACHMENT:/abs/path]` markers when its own upload fails. The gateway now strips them with `stripAttachmentMarkers` from `@repo/protocol/attachments` before posting (two tests). This change and the merge of `main` (M5.2 and others conflicted in `gateway.ts`, `gateway.test.ts`, `client.test.ts`, `compose.ts` and the README) came after the last review round. Both are small, and `bun run check && bun run test && bun run build` pass.

## Decisions

- Slack's `files.uploadV2` is the three-step external upload: `files.getUploadURLExternal`, a POST of the bytes to the returned URL, `files.completeUploadExternal` with `channel_id` and `thread_ts`. `SlackClient.uploadFile` does all three. The bot token goes only to the two Slack API calls. The upload URL must be https on a Slack file host, and the POST refuses redirects.
- The gateway reads each output file as the run's own principal, so it can read only files its run lists. The text posts first, then the files, one at a time.
- A file that fails does not stop the others and does not throw out of `deliver`. The failure is in the `error` of the `slack.delivered` event, with `delivered: true` (the text did post). With no files the event is unchanged.
- With output files and a `defer` hook (the request's `waitUntil`), the whole delivery runs after the response. Without files, or without a hook (tests, the tick), it runs inline as before.
- `missing_scope` is a config error, so a Slack app installed without `files:write` shows up as a failed upload with that name in the event.
- The check in the task file is the route test in `slack-events.test.ts`: a DM with a PDF, the download job, a claimable run, then a completion with an output file, and the three upload calls in the thread.

## Nits left

- A delivery can still pass 30 s: one very large file, or retry sleeps after an upload that started just before the 20 s mark. The event is then lost with the work.
- A skipped file is named by id, other failures by file name.
- The 20 s budget also applies when there is no `defer` (the tick has no 30 s limit).
- The budget test depends on how many times `post` reads the clock.
- Nothing tests that `composeServices` in `server.ts` passes `waitUntil` through, or that a rejection in the deferred work is caught and logged.
- Each file is held fully in memory before upload (50 MB cap, 128 MB Worker).
- A transient failure of `files.completeUploadExternal` after Slack applied it reruns all three steps and can post the file twice.
- A 429 on the byte POST ignores `Retry-After` (the file download does the same).
- The upload response body is not read or cancelled.
- Raw error messages from storage or service errors go into the `slack.delivered` payload.
- The first call is a GET with query parameters and the last a JSON body; Slack's SDKs send form posts. Not tried against real Slack.
- With files, `slack.delivered` is written after `/complete` returns, so a quick follow-up run in the same thread could reply before the files show.

## Ideas beyond the scope

- Move delivery with files to a Queue consumer or a Durable Object alarm, so it can take longer than 30 s and retry.
- Stream the file body to the upload URL instead of buffering it.
- Tell the person in the thread when a file could not be attached.
