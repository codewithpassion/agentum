# M2.3 review

Task: names for clients that sign in with a published identity (CIMD).

## Verdicts

- Round 0, at 8aae6ae: must-fix. Every request from a client whose name stays null re-ran the Clerk lookup and the CIMD fetch, up to 3 seconds each.
- Round 1, at 09b5b31: must-fix. The retry throttle lived inside the per-request service, so it had no effect, and its test reused one service.
- Round 2, at 5c50a66: clean. The throttle is module state (per Worker isolate), injectable as `nameLookupFailures`, and the test builds a service per call.

The CIMD helper nits from round 0 were fixed in round 1: it reuses `sanitizeOAuthClientName`, the dead `pathname !== ""` test is gone, the content-type check is `application/json` or `+json`, and the rejection test uses a real rejected promise.

## Nits left

- A failed lookup on a client's first request is not recorded, so its second request looks the name up once more before the throttle starts.
- When the failure map reaches 1000 entries it is cleared whole instead of dropping the oldest entry.
- `NameLookupFailures` is exported but only used inside the file.
- No test covers the default module-state map that production uses.
- No test covers the 3 second abort path of the CIMD fetch.
- docs/tasks has two files with the id M2.3 (`M2.3-cimd-client-names.md` and `M2.3-inbox-tools.md`), and the CIMD one is on main but not on this branch.

## Ideas beyond the scope

- The CIMD fetch does not block private or loopback hosts. The client id comes from a token Clerk has already accepted, and redirects are not followed, but an SSRF guard would be cheap to add if Clerk ever accepts arbitrary ids.
- The logo_uri from the document could be shown in Settings next to the name.

## Steps for Dom

None. The existing claude.ai row on staging gets its name on the next `/mcp` request after deploy, if the Worker can reach `https://claude.ai/oauth/mcp-oauth-client-metadata`.
