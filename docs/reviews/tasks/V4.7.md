# V4.7 review

The Cloudflare VM syncs live: it pushes the VM's changes from the lease alarm while a run goes on, pulls only the paths the server announces, and syncs the agent's grant roots with their modes. The VM and isolate prompts name the run's task folder, and the cloud runner no longer handles `[ATTACHMENT:]` markers. This also closes the gap V3.17 left: grants made by the builder now sync into the VM, because the VM reads `CloudStart.library.roots` and not `runtimeConfig.libraryPaths`.

## Verdicts

Round 1 (aab13c0): must-fix. The lease beat awaited the library push, which can wait 30 s for the lock and then walk the whole VM, so it could hold up the Lifecycle driver's other jobs.

Round 2 (47e4595, the fix): clean. The push now starts from `PiRun.#checkpointLibrary` through `ctx.waitUntil`, one at a time, with `waitMs: 0` so it gives way quietly to a sync that holds the lock. The end sync waits for a running push first.

## Decisions to know

- `libraryPathsOf` and `LIBRARY_PATHS_KEY` stay in `packages/services/src/library/sync-paths.ts`. `apps/web/src/components/agent/profile/library-paths.ts` still imports `libraryPathsOf` for the profile editor, so V4.19 removes them. Only `librarySyncRoots` was removed.
- The push runs on every lease beat (20 s, `HEARTBEAT_MS`), not on a separate 30 s timer, and for the first active run only. The VM is one working copy for all runs of the session.
- The isolate prompt names the task folder as `/library/<taskFolderPath>`, the path its file tools reach, not the bare library path.
- A stored `LibrarySyncState` with plain string roots reads as write roots and is upgraded on the next save.
- `agent-form.tsx` told people that a cloud agent returns a file by writing `[ATTACHMENT:/library/path]`. That sentence now names the task folder.
- The VM prompt says changes sync "within seconds" (`liveSync`), the push runs about every 20 s.

## Nits left

- A push that never returns (a hung VM call) keeps `#checkpointing` set, so later checkpoints stop and `complete` waits. A hang in the end sync did the same before.
- A beat in the gap between `await this.#checkpointing` and the end sync's lock can start one more push for the same run. A conflict that push finds is recorded after the lock is released, so it could land after `run.finished`. It is rare.
- Conflict copies and `library.conflict` events go to the first active run of the session, even when another active run made the change.
- Every push walks the whole tree, the wiki included, with no change detection. `createCoalescer` from `@repo/library-sync` is not used here.
- A pull for announced changes that cannot get the lock within 30 s is logged and dropped, with no retry. The next full sync in picks it up.
- `syncLibraryPaths` drops known conflicts under any announced path, including one outside the roots. The audience only sends covered paths, so this cannot happen today.
- If a newer dry run in the same session sets `#vm` to undefined, an older VM run still active stops pushing (existing behaviour).
- `PiRun.libraryChanged` has no test of its own, only `syncLibraryPaths` does, because the Durable Object class cannot run under bun.

## Beyond the scope

- `apps/web/src/components/agent/profile/library-row.tsx` still writes `runtimeConfig.libraryPaths` (V4.19). After it moves to grants, drop `libraryPathsOf` and `LIBRARY_PATHS_KEY`.
- The managed runtime's help text in `agent-form.tsx` still says `[ATTACHMENT:path]` stays plain text.
