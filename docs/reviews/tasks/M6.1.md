# M6.1 review

## Verdicts

Round 0, commit 885c64e: clean. No must-fix, twelve nits. No fix rounds.

## Decisions

- Tables `inbox_threads` (`title`, `created_by`, `last_post_at`) and `inbox_posts` (`thread_id`, `author_kind`, `author_id`, `text`, `run_id`, `file_ids` JSON). Both are workspace scoped, and a thread's posts cascade with it.
- `createInboxService({ db, atomic, clock, events, runs })`. It needs `runs.startRun` while the runs service needs its `gateway`, so `composeWith` pushes `inbox.gateway` onto `gateways` and passes `runs` as a lazy `{ startRun }`.
- Workspace-wide visibility: every user in the workspace reads and posts to every thread. A read-only API key or OAuth client reads only.
- `post` also accepts a run principal (author is the agent, `run_id` is the principal's run). This is for M2.3's `inbox_post`, and its mentions wake with that principal.
- A post's mention does not wake the agent that wrote it. The echo of the fake runtime repeats the input, mention included, so without this rule every fake reply would loop until the guard.
- Post ids come from ulidx's `monotonicFactory`, so they order a thread even within one millisecond or after a clock step back. The events id helper shares state with the events service and does not.
- The wake budget counts the agent's runs in `inbox` sessions over the past hour, so it needs no table of its own. The streak rule reads the newest 3 posts of the thread.
- A wake that `startRun` refuses with a `ServiceError` (busy ancestor, depth limit, no runtime) appends `inbox.loop_stopped` with `reason: "refused"`. The post stays and the other mentions still run.
- The reply gateway loads the run row for the workspace and session, then requires the thread to be in that workspace.
- Mention input is capped at 100,000 characters when waking, the `startRun` limit, because a reply can be longer.

## Checks

`bun run check && bun run test && bun run build` pass, and the grep for drizzle in `apps/web/dist/client` finds nothing. `inbox.test.ts` covers the five checks of the task (user post and reply with `run_id`, agent-to-agent wake with parent run and subject, a quoted run id, the 3-post streak with resume, no mention) plus the budget, a refused wake, workspace isolation, read-only keys and thread ordering. `inbox-router.test.ts` runs the real fake runtime through `composeWith`. Live, against `vite dev` on port 3417 with a fresh local D1: dev login, created a fake agent "Pelican", opened `/inbox`, made a thread, posted "@pelican hi from the browser" and the reply "Echo: @pelican hi from the browser" from Pelican showed in the thread.

## Nits left

- The browser check used the fake runtime, which answers inside the post call, so the poll was not what showed the reply. The poll (every 2 s) is covered only by reading the code.
- Check tests other than the first use a scripted adapter named `fake`, not the real fake runtime, because the echo cannot say `@beta`.
- The streak is read once before the loop over mentioned agents, so a second agent in the same post sees a stale streak.
- The wake budget is checked and the run started in two steps, so concurrent posts can pass 10 an hour.
- `deliver` writes a post even for empty reply text.
- `createThread` reads the clock twice.
- The monotonic factory is per isolate, so posts from two isolates in one millisecond can misorder.
- `checkWakeRate` still returns `timestamps`, which only Agentum's in-memory store used.
- The slug pattern and length limits are repeated in `mentions.ts` and `agents.ts`.
- Column names differ from `docs/architecture/index.html` (`created_by` for `created_by_kind` and `created_by_id`, `text` for `body`). The doc or the schema should move.
- `usePolledQuery` has no guard against a slow older response landing after a newer one.
- The inbox components import `errorMessage` from `components/triggers/format`.
- A run started with an inbox reply target for a thread that does not exist (or is in another workspace) fails in `deliver` after the run is saved as `done`.
- A failed run leaves no post in the thread.
