## Implemented API

Only new `packages/services/src/live-guests/*`, the new `packages/db/src/live-guests.ts` query module and package exports were authored. Existing live-artifacts code/schema/migrations were imported/read, not edited. The requested CLAUDE.md, full PRD section 9, R3.1–7/R3.12–13, L.1 schema, L.6 GuestGrant and startForGuest ports, and L.4b outbox evidence/helper were read.

- `@repo/services/live-guests/invitations`: `createGuestInvitations(deps)` exposes `invite`, `changeRole`, `revoke`. Every call authenticates an existing user Principal, checks workspace/artifact ownership or admin status, refuses read-only credentials and non-live/deleted artifacts. A trusted directory port looks up the canonical address in the workspace; errors propagate rather than becoming outsider grants. Named members receive user grants; outsiders receive workspace-local identities, mandatory future expiry, roles and persisted daily cap (default 20). Only viewer/commenter/editor roles can be assigned. Invites use `hm_invite_` + 32 CSPRNG bytes and store only SHA-256 hashes. A required typed sender receives inviter name, workspace name, artifact title, role, expiry and the HTTPS link. The inviter name comes from a trusted profile port. No token is returned in the ordinary service result or event payload. Sender failure propagates after the committed grant; this does not claim reliable email retry/delivery.
- Role/revoke mutations include the existing `roomInvalidationStatement` in the SAME `atomic` write as the grant mutation and event, then invoke the required delivery trigger. Guest participant IDs are `g:<guestId>`, members `u:<userId>`; the later guest room adapter must use that convention. A compare-and-swap SQL assertion aborts competing stale mutations with their audit/outbox. Sequential repeated revoke and unchanged role are harmless. No post-commit best-effort room refresh substitutes for the outbox. L.4b's system sweep retries durable rows; L.7 must install its durable processor and enforce the five-second socket bound.
- `@repo/services/live-guests/access`: `createGuestAccessReader({ db, clock, guestsOff })` exposes scanner-safe read-only `invitation(workspaceId, token)` and `resolve({ workspaceId, artifactId, sessionToken })`. Neither rotates a session nor records an open. The reader is explicitly an internal building block and must not be directly wired to a viewer route. Missing/expired/revoked/off/forged credentials return null. Every read checks current session expiry, explicit live grant, guest identity, artifact workspace/kind/deletion and workspace guest switch, plus the injected environment emergency switch. Joins validate workspace on every parent even though the schema's foreign keys are not composite. Workspace audience never grants a guest implicit access. Results are distinct protocol `GuestGrant` values, never Principal objects; one guest identity/session may access its multiple current artifact grants, as section 9 requires.
- `@repo/services/live-guests/sessions`: `createGuestSessionLifecycle(deps)` exposes `open`, `renew`, `signout` for an **already authenticated persisted session**. There is intentionally no initial sign-in API. Open/renew recheck live access and rotate a hashed 32-byte session token with a twelve-hour sliding expiry. Rotation compares the old token and rereads role/expiry/workspace/artifact access inside the atomic write; a deletion between preflight and write is also guarded. A successful open adds one `artifact_views` row with surface `guest`, guest identity and trusted privacy-normalized metadata in that same write. Renewal has no view side effect. Signout deletes the matching hashed session even when guest access is disabled, then clears the cookie. Expired sessions cannot resolve/renew; a cleanup job is not needed to enforce expiry. Concurrent old-token reuse produces at most one rotation/open audit. Atomic failures return the same public refusal without SQL details.
- `@repo/services/live-guests/security`: opaque invitation/session tokens, unbiased six-digit Web Crypto CSPRNG codes, and HMAC-SHA-256 code hashing under a private injected >=32-byte pepper. The hash binds workspace, guest, invitation and challenge ID, preventing offline six-digit enumeration from a DB dump or transplant to another challenge. Hashing is deliberately not presented as OTP verification/consumption. Constants encode ten minutes and five tries. Cookie helpers enforce `__Host-hm_guest`, Secure, HttpOnly, Path=/, SameSite=Lax, max twelve hours, no Domain, and reject token/header injection. Clear uses the same attributes and Max-Age=0. Cookies belong only in HTTP Set-Cookie headers. No OTP/session credential belongs in a URL.
- `@repo/services/live-guests/ports`: required directory, typed email and invalidation-delivery contracts, plus a future `GuestRunAuthorizationPort.authorizeAndCharge({ sessionToken, workspaceId, artifactId, agentId }) -> GuestGrant`. The runtime adapter must authenticate the current session, reread current grants and atomically charge the daily cap before delegating to L.6 startForGuest. A submitted GuestGrant is not authentication. The daily cap is stored here; enforcement/runtime wiring remains phase 3 integration.

Cloudflare email/platform skills were applied to the sender boundary. The future EMAIL binding adapter must use generated Worker binding types, a verified platform sender, escaped HTML and a plain-text alternative. No binding/domain configuration, network email calls, actual sends or deployments were performed. The binding setup/prerequisite commands were outside this backend-only brief and were not run.

## Controller persistence blocker

Migration 0027 resolves the invalidation outbox gap and is reused above. L.1 guest tables still have no durable rate bucket ledger. `guest_codes` has workspace/guest/hash/expiry/attempts, but no invitation reference or explicit consumption state. `guest_sessions` already supports the identity-scoped session model; no per-artifact session table is requested.

For the intended query-backed implementation, please supply a controller-owned migration before `requestCode`/`verify` can land:

1. Add `guest_codes.invite_id` referencing `guest_invites.id`, plus an index on `(workspace_id, invite_id, created_at, id)` for deterministic challenge selection. Backfill existing unbound challenges as unusable (or delete those short-lived challenges); never attach them by guessing an invite. Service joins must verify invite/member/guest/artifact/workspace consistency. Codes must be invalidated if their invitation grant is revoked/expired even if another grant for that guest remains live.
2. Add nullable `guest_codes.consumed_at`. This permits explicit atomic one-time consumption and invalidating superseded challenges without deleting attempt/audit evidence. Physical deletion could alternatively represent consumption, but would still need atomic guards and deterministic invitation binding; the current implementation does not pretend the hashing helper consumes anything.
3. Add a dedicated `guest_auth_rate_buckets` table with `kind` (`invite`, `email`, `ip_prefix`), opaque keyed-hash `subject_hash`, `window_start`, `expires_at`, nonnegative `count`, positive `limit`, a unique key `(kind, subject_hash, window_start)`, and `count <= limit`. Email/IP buckets must cover multiple invitations (and environment-wide abuse across workspaces); invitation buckets can bind workspace+invite in their keyed subject. Do not retain full IPs or plaintext emails in the rate ledger. Counts represent reserved sends, so sender failures cannot free the abuse budget.
4. The code-send operation must reserve ALL three buckets, invalidate/supersede the invitation's prior challenge, insert the hashed new ten-minute challenge and its single audit event in one `atomic` write with SQL guards. Concurrent requests must not pass a read/count/write preflight. Verification must atomically charge attempts (including incorrect guesses), enforce five tries/current grant/current invitation/expiry, consume once, insert the hashed session and record one inviter-attributed sign-in event. No process-local limiter, optional no-op port or unkeyed six-digit hash is acceptable. A controller-provided durable coordination adapter with equivalent serialized guarantees is another option; a typed promise alone is not an implementation.

No schema/migration was authored here, per the explicit ownership boundary. Existing audit events were not silently repurposed into mutable rate counters. `requestCode`, OTP `verify`/initial sign-in and their durable rate/attempt/replay tests remain **unimplemented** pending that persistence. Thus R3.4/R3.5 and the code-send/sign-in portion of R3.12 are not accepted; no LG.0 completion is claimed. There is no externally reachable partial auth flow. A controller question with this persistence handoff was raised during implementation.
