## API and dependency contracts

`@repo/services/live-guests/service` exports async `createLiveGuestsService(deps)` and `LiveGuestsService`. All dependencies are injected: DB, Atomic, clock, trusted workspace member directory, trusted inviter profile lookup, typed email sender, durable invalidation processing trigger, HTTPS platform origin, private OTP pepper and the current emergency-switch callback. No service reads environment variables or invents application authentication. The factory composes these isolated modules:

- `invitations`: `invite(principal, { artifactId, email, role, expiresAt?, agentRunsPerDay? })`, `changeRole(principal, { artifactId, memberId, role })`, `revoke(principal, { artifactId, memberId })`. Every call requires a current user Principal and artifact owner/admin rights; read-only API/OAuth credentials, run/system principals, deleted/static artifacts and other workspaces refuse. Named member addresses become user grants; directory failures propagate rather than becoming outsider grants. Outsiders get one identity per canonical address/workspace, a mandatory future expiry and a persisted daily run cap (default 20). Only viewer/commenter/editor roles are assignable. `invite` creates the grant and sends the invitation; the return contains member ID/kind, never the token. Duplicate/conflicting creation can fail its unique constraint atomically; callers must not treat a directory/DB error as outsider authentication.
- `access`: read-only `invitation(workspaceId, inviteToken)` returns landing metadata (the public composed service adds the trusted inviter name) without sending a code, consuming a token, recording a view or changing any row. `resolve({ workspaceId, artifactId, sessionToken })` returns a distinct current `GuestGrant` or null, never a Principal. It checks the current session expiry, exact artifact grant, guest/parent workspace consistency, role, expiry/revocation, artifact kind/deletion, workspace guest switch and injected emergency switch on every call. Workspace audience provides no implicit guest access. One identity/session can resolve each of its multiple live grants, as PRD section 9 requires.
- `auth`: `requestCode({ workspaceId, inviteToken, ip })` is the explicit send-code action. `ip` must come from trusted HTTP/platform metadata, never the submitted form. Missing/invalid IP refuses silently; full IPs are normalized to IPv4 /24 or IPv6 /48 before use. Every response is `{ accepted: true }`, including unknown, off, revoked, expired, limited and failed-delivery cases. `verify({ workspaceId, inviteToken, code, ip?, userAgent? })` returns `{ cookie, expiresAt, grant, location: '/g/a/<artifactId>' }` on success. Every refusal has the same public `Guest access unavailable` message/status without SQL, credential or address details.
- `sessions`: `open({ workspaceId, artifactId, sessionToken }, metadata?)` rotates the credential and records one guest view atomically. `renew(input)` rotates without recording a view. `signout({ workspaceId, sessionToken })` deletes the matching hashed session and returns a cleared cookie even if guest access is off. Sessions expire after twelve hours, sliding on successful rotation. Every HTTP use must call open/renew and return its Set-Cookie; the read-only resolve method is an internal authorization/revalidation building block, not a substitute for rotation or open logging. Open metadata must come from the existing trusted privacy-normalizing HTTP adapter.
- `security`: opaque invitation/session token generation, six-digit CSPRNG code generation, private peppered code/abuse-subject hashing and cookie helpers. `ports`: required directory/email/invalidation contracts and a future `GuestRunAuthorizationPort.authorizeAndCharge({ sessionToken, workspaceId, artifactId, agentId }) -> GuestGrant`. Daily runtime cap enforcement remains later phase 3 integration: authenticate the session, resolve a fresh grant and atomically charge the stored cap before L.6 startForGuest. A submitted GuestGrant object is not authentication.

The later guest HTTP adapter must read only the guest cookie on guest routes; all ordinary application routes continue to ignore it. It must pass the environment's `LIVE_GUESTS_OFF` semantics via the required `guestsOff` callback, not a cached sign-in result. No Principal is reconstructed from a guest identity, cookie or room claim.

## Credentials, durable limits and transaction boundaries

Invitations are `hm_invite_` plus 32 random bytes, stored only as SHA-256 hashes. Session credentials likewise contain 32 random bytes and persist only their hashes. The only credential in any generated URL is the invitation token. Codes, session credentials, pepper and keyed rate subjects are not logged or placed in audit payloads. The private injected pepper must contain at least 32 bytes and remain stable through active challenges/rate windows; rotating it invalidates existing challenges and changes abuse-ledger subjects.

Codes use Web Crypto rejection sampling for an unbiased six-digit decimal value. HMAC-SHA-256 binds the private pepper to workspace, guest, invitation and challenge IDs plus the code. A DB dump cannot enumerate the six-digit space without the pepper, and copying a hash to another invitation/challenge does not verify. Codes expire at ten minutes, charge incorrect and malformed guesses, allow five attempts and consume once. A correct fifth guess is permitted; a fifth failure consumes the challenge. Resending supersedes the prior active challenge on that invitation. An invite link remains a read-only landing/reauthentication entry while its grant lives; `usedAt` records first sign-in and is not used to disable the link permanently.

Rate ceilings are fixed windows, per workspace:

| Subject | Ceiling |
|---|---|
| Invitation | 1 send/minute and 3/hour |
| Canonical email, across invitations | 6/hour |
| Normalized IP prefix, across invitations/guests | 30/hour |

Bucket keys contain workspace, kind, window start and a private keyed subject hash. Window duration is included in the hash domain so the minute and hour invitation buckets cannot collide. Reservations count attempted sends, including sender failures; a failure cannot release the abuse budget. Existing-window limits cannot be relaxed by a configuration change. Expired ledger rows can later be purged using the expiry index without affecting an active window.

All four reservations, superseding the previous challenge, inserting the new hashed challenge and recording `artifact.guest_code_sent` commit in ONE Atomic write. Upsert increments plus SQL count/limit constraints serialize competing reservations, including separately constructed service instances. An exceeded bucket rolls back every bucket, the new code and audit. No async preparation awaits a Drizzle statement before the Atomic boundary. The send audit records the committed send request; SMTP delivery is not claimed. Only after commit does the typed sender run. Failed delivery stays charged and produces the same public response; another explicit bounded request is required.

Verification uses a single guarded update to charge the current attempt and set consumption on success/fifth failure. Its guard checks current code hash, invitation, guest, grant, workspace switch, expiry/revocation and artifact workspace/kind/deletion inside the write. A second guard detects a challenge deleted after preflight. Successful consumption, guest last-seen, hashed session insertion, invite usedAt and the single inviter-attributed `artifact.guest_signed_in` event commit together. Audit/session failures roll consumption and attempts back; concurrent replay cannot mint a second session. Failed guesses commit their attempt without a sign-in event.

Open/renew use token compare-and-swap and reread current role/expiry/access inside the Atomic write. A session deleted after preflight cannot rotate. Open's view row has surface `guest` and guest ID; rotation/view audit roll back together. Current-state reads prevent expiry, workspace switch, emergency switch, deletion and revocation from granting access on the next request, regardless of cookie Max-Age.

Cookie contract: `__Host-hm_guest`, Secure, HttpOnly, Path=/, SameSite=Lax, Max-Age=43200, no Domain. Clearing uses matching attributes and Max-Age=0. Helpers reject malformed/header-injected tokens and longer lifetimes. Credentials are returned only in the Set-Cookie value, not the redirect URL.

Role/revoke writes commit the grant mutation, inviter/member audit and existing `roomInvalidationStatement` in the SAME Atomic call before invoking the required delivery trigger. Competing stale mutations abort their audit/outbox too. Guest participant IDs are `g:<guestId>`; members use `u:<userId>`. A trigger failure leaves the committed outbox available to L.4b's system retry sweep. The later L.7 durable processor must deliver within five seconds, enforce the same participant convention and revalidate guest session/grant/switch access at admission and at most five-second intervals while connected; expiry/deletion/switch/emergency changes must close sockets even without an explicit revoke request. The backend does not implement or claim actual room/socket behavior. Its GuestGrant expiry plus open/renew session deadline are available for connection expiry scheduling.

### Finding: failed delivery and expired grants prevent a normal re-invite (P2)

`invitations.ts` commits the guest identity, grant, hashed invite token and audit before calling `sendInvitation`. If the sender rejects before delivery, `invite` rejects without returning the member ID or token; only the token hash remains in the database. A retry for the same address and artifact fails `artifact_members_guest_unique` because the grant is still unrevoked. The same partial unique index considers an expired grant active, so a new invite with a future expiry also fails after the old one expires. The owner can recover only by discovering and revoking the old grant before inviting again; the service has no resend/reissue operation. The same failed-delivery retry problem applies to named member grants. This makes a transient email failure or ordinary expiry prevent the requested invitation flow, and the committed audit alone does not establish delivery.

Reproduction on the real migrated SQLite database: configure `sendInvitation` to reject, invite an outsider with a future expiry, observe rejection and one persisted member and invite, retry the same invitation and observe a uniqueness failure; advance the clock beyond the grant expiry and retry with a new future expiry, which also fails. An independent temporary test ran this sequence successfully (1 pass, 5 assertions); it was removed after the probe. Fix by providing a safe reissue/retry path and handling expired grants without losing audit history; account for ambiguous sender failures and avoid storing plaintext credentials indefinitely.

## Controller invitation recovery remediation

Inviting an already granted address now atomically revokes the previous unrevoked grant (including expired grants), records its revocation, enqueues room invalidation, and inserts the new grant, invitation hash and invitation audit. Old invitation links/challenges cease authorizing through their revoked grant; no plaintext credential is retained. An owner can repeat the normal invitation operation after failed or ambiguous email delivery, or expiry. Named-member grants follow the same recovery path. Delivery errors remain explicit, and durable automatic email retry is not claimed. The optimistic grant mutation and unique new grant abort competing stale replacements atomically.

The real migrated-DB suite now has 28 tests/1166 assertions passing, including failed/ambiguous sender results, replacement-token validity and old-token refusal, expired guest renewal, named-member retry and concurrent reissues retaining only one live grant/token. Root `bun run check`, `bun run test`, and `bun run build` passed on combined main with the recovery fix. The client bundle scan found no `drizzle`.
