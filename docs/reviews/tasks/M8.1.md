## Decision: session-scoped tokens

Managed Agents fix `mcp_servers` on the Anthropic agent when it is registered or synced. A server entry takes only a name and a URL (checked against SDK 0.118.0), and `sessions.create` has no MCP field, only `vault_ids`. So a run cannot hand the agent a token the way it hands one to a machine. A token on the agent would be shared by every session of that agent, and the check "two concurrent sessions on one agent do not share a token" rules that out.

The credential therefore rides per session. Each Anthropic session gets its own vault, holding one `static_bearer` credential per MCP server URL (the platform's `/mcp` and one `/api/proxy/:connectorId` per assigned connector), all carrying one token `hm_ses_<payload>.<signature>`. The payload is `[sessionId, agentId, workspaceId, issuedAtMs]`, signed with `RUN_TOKEN_KEY` like a run token. The token has no age limit. What decides whether it is good is the `managed_sessions` row:

- the signature checks, and the row is open (`closed_at` null) and was made for exactly this `issuedAt`, so a replacement session kills the old token;
- the row's `current_run_id`, set before the run's first message is sent, is `running` with a live lease and `claimed_by = 'managed'`. The claims returned are that run's.

Because the claims are a run's, `/mcp` (through the principal resolver), the proxy and `credentials.runContext` work on them unchanged. The second turn of a session, for another person, resolves that person's credential on the same token. A run that is claimed but has not launched, or an older run whose Anthropic session lingers, resolves to nothing. Setting `current_run_id` before the send closes the window for the first tool call of a new or a reused session.

Vaults hold 20 credentials, so a managed agent reaches at most 19 connectors. More fails the run with that message.

## What was built

- `packages/db`: `managed_agents`, `managed_sessions`, `managed_runs` and `workspace_anthropic_keys`, migration `0001_faithful_kulan_gath.sql`.
- `packages/services/src/managed/`: `gateway.ts`, `events.ts` and `config.ts` ported from Agentum with the shared worker agent, multi-agent, memory stores, skills, desktop and transcript code removed (their tests come with them), `keys.ts` (per-workspace key, encrypted with `SECRETS_KEY` and bound to the workspace row), `service.ts` (the step logic), `runtime.ts` (the adapter), `run-events.ts`, `types.ts`.
- `ManagedPoller`: one Durable Object per run, an alarm per step (`apps/web/src/server/managed-poller*.ts`), plus the tick job `managed.rearm` that nudges every running managed run once a minute.
- `run-tokens.ts`, `workspaces.ts` and the proxy accept `hm_ses_` tokens.
- A settings page at `/settings/managed-agents` for the key, and the runtime select on the agent form with the limits written next to it.
- `wrangler.jsonc`: `MANAGED_POLLER` in the three places, DO migration tag `v3` after `PiRun`'s `v2`.

## What does not work on a managed agent

Each of these is said in the agent form, and the file case is also said to the agent in its message.

- Attached files: the message says how many files could not be passed. The agent cannot read Harbourmaster files.
- Skills are not synced. Library access still works through the platform MCP tools.
- `[ATTACHMENT:path]` in an answer stays plain text, and a managed run has no output files.
- Images returned by a connector tool never reach the model (the API drops MCP image results). The task asked for custom tool results where images matter. None were built, because no platform tool returns an image and a connector's images cannot be intercepted. This is a gap, listed below.
- A session stops at $10 of spend, and one budget covers a session reused for up to seven days.
- No usage or cost is stored on the run.
- A cancelled or failed run closes its session, so the next run starts a fresh Anthropic session and the earlier conversation is not in context.

## Nits left

- `endFailed` and the run-too-long path act on a session without the run check, so a step still running for a cancelled run could touch a session another run just took over (a gap of one step).
- `launch` is not idempotent: if `sendMessage` or `createSession` succeeds and the `sent_at` write fails, the retry sends again, into a new session.
- A cancel that lands during launch before the Anthropic session id is stored interrupts nothing, and the session that is then created runs the cancelled input.
- A launch in flight during a key change can write `managed_agents` or `managed_sessions` rows under the old key after the atomic delete. Every later run then fails on the stale agent id until the key is saved again.
- When `keys.resolve` throws inside `abandon`, the row is closed but the vault is not deleted and Anthropic is not told to stop.
- Closed sessions keep their vaults when the cleanup failed, and sessions that never get another run keep theirs. Nothing sweeps them.
- `rearm` reads at most 100 running runs with no order.
- `interrupt`, `rearm` and `step` take no principal. They are called only from the Durable Object and the tick.
- `pollEvents` falls back to the whole session history when the last event has a null `processed_at`.
- Key changes append no audit event.
- Events over 64 KB lose their text in the final reply (`finalReply` reads the stored payload, not the blob).
- `events.ts` keeps copied helpers that nothing uses: `isSessionReusable`, `agentText`, `customToolCalls`.
- The `mcpServers.length > 0` guards in `gateway.ts` can never be false, because the platform server is always listed.
- `agent-form.tsx` says "opus, sonnet or haiku": `modelFor` swaps any other model id for Sonnet.

## Ideas beyond the scope

- Bridge connector tools that return images through a client-run custom tool, so the model sees them.
- Store the session cost and token usage on the run from the session's usage.
- A tick job that deletes vaults of closed or idle sessions and archives old Anthropic sessions.
- A per-agent budget in `runtimeConfig` instead of the fixed $10.
- Choose the model from the catalog with a picker, so the form cannot name a model that is swapped.

## Steps for Dom

- The two Anthropic resources the live check left behind (two vaults, two sessions, one agent, one environment named `harbourmaster`) are safe to delete in the Anthropic console.
- To run a managed agent on staging or production: set the workspace key on `/settings/managed-agents`, and make sure `PUBLIC_BASE_URL` is the public address (it is, for both deployed environments). `RUN_TOKEN_KEY` and `SECRETS_KEY` must exist there already.
- The release that adds `ManagedPoller` creates a Durable Object class (tag `v3`), so it goes out as `wrangler d1 migrations apply DB --remote` then `wrangler deploy`, never `versions upload`.
- Locally, a managed agent needs a tunnel and `PUBLIC_BASE_URL` set in `apps/web/.env.local`.
