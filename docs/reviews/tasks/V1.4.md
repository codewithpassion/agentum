# V1.4 review

Task: SessionStream Durable Object and the resumable SSE route. Branch task/V1.4-session-stream-do.

## Verdicts

- Round 1 (03b396b): not clean, 2 must-fix, 5 nits.
- Round 2 (8e6d681, the fix commit only): clean, 0 must-fix, 7 nits. Two fix rounds were not needed beyond the first.

Round 1 must-fix, both fixed in 8e6d681. With `defer`, the frames of one port went out as concurrent RPCs and could arrive out of order, so `streamPublisher` now chains deferred sends. And `publish` in the core awaited every writer, so a client that stopped reading could stall the publisher and, on paths without `defer`, the event append behind it. Writes are now fired without awaiting, and a writer with more than 100 unfinished writes is dropped.

## What changed

- `apps/web/src/server/session-stream.ts` is the `SessionStream` Durable Object, named by session id. Its logic is in `session-stream-core.ts` (fan-out, 25 s ping, drop on a failed or stalled write). Nothing is stored.
- `session-stream-frames.ts` maps a stored event to an `event` frame plus a `run` frame for status-changing `run.*` events. A payload with `payloadRef` goes out as `truncated: true`. Only message, tool, run and request event types are streamed or replayed, listed exactly.
- `session-stream-port.ts` has `streamPublisher(namespace, defer?)` and `streamListener(port)`. `composeWith` registers the listener with `events.onAppend` and `runs.onEvent` when `Infra.streams` is set. A failing publish logs and never fails an append.
- `routes/session-stream.ts` serves `GET /api/sessions/:sessionId/stream` on a cookie group. It subscribes to the Durable Object first, replays stored events after `Last-Event-ID` or `?after=` in pages of 500, then relays live frames and drops any id the replay already sent. A hidden or unknown session answers 404, an overlong resume id 400.
- Services: `sessions.get` (visibility check without a transcript) and `events.notifyStored`. `startRun` with `offerLater` writes `run.queued` and `message.user` with `insertStatement`, which skips listeners, so it now reads them back and notifies the `runs.onEvent` listeners (refinement in the task file).
- `wrangler.jsonc` has `SESSION_STREAM` in all three places and migration `v5`. The class is exported from `src/server.ts`.

## Checks

`bun run check && bun run test && bun run build` pass, and the grep of `apps/web/dist/client` for `drizzle` is clean. The live staging check from the task file is the controller's.

## Nits left

1. `session-stream.ts:31`: a writer dropped for stalling is closed with `close()`, which finishes only after its buffered frames drain. `abort()` would end it at once.
2. `session-stream-core.ts:8`: the limit of 100 unfinished writes counts frames, not bytes, so a burst of deltas to a slow client could drop it. It reconnects and replays stored events but loses those deltas.
3. `session-stream-port.ts:30`: one send chain per port covers every session in a request, so one hung RPC delays publishes to other sessions in the same request.
4. `session-stream-core.ts:3`: the header comment does not mention the stalled-writer drop.
5. `session-stream-core.ts:91`: the `.catch` on the ping publish is dead, because `publish` always resolves.
6. `routes/session-stream.ts:112`: no test covers the empty first chunk change.
7. `runs.ts:657`: the Slack path does one extra D1 read before its answer, because the Slack status listener is always registered on the runs events.
8. The replay is built as one string in memory before the first byte goes out.

## Ideas beyond the scope

- Stream `request` frames from the V1.5 request service. V1.4 sends only the `request.*` event frames.
- Page the replay straight into the response instead of building it first.

## For Dom and the controller

- v5 creates a new Durable Object class. The first staging and production release must go out with `wrangler deploy`, not `versions upload`. A PR preview of this branch may fail until staging has been deployed with v5.
- Check on staging that `request.signal` aborts inside the Durable Object when a client disconnects (kill `curl -N` and confirm the DO stops pinging it). If it does not, the writer is dropped on the next failed ping, up to 25 s later.
