# V1.11 review

## Verdicts

- Round 1 (5dc681c): must-fix. `poll` moved the session cursor before the requests for a `requires_action` idle were opened, so a step that failed in between lost the idle for good.
- Round 2 (5d46ae1, the fix only): clean. Requests now open before `storeProgress`, opening is idempotent on (run, tool use id), and a test covers a failed open being retried.

## Nits left

- A send is claimed on `delivered_at` before it goes out, so a crash between the claim and the send leaves the session blocked until the 60 minute limit. A send whose reply was lost is sent again after the release.
- `waitingOf` sums each request's wait on its own, so overlapping requests count their overlap twice (the scope says "summed").
- After "always allow" the same tool asks again in the same run, because the rule reaches the toolset only when the next run's launch syncs the agent.
- A blocked call missing from the current page makes `openRequests` re-read the whole session history.
- `requiredEventIds` collects from every idle in a page, not only the last. Harmless while `open` is idempotent.
- `reduceEvents` runs twice on one page, in `poll` and in `settle`.
- No test covers the "The person gave no answer." fallback for an empty `answers` map.
- V1.9 left a narrow window: a `kick` that lands while the poller's alarm handler waits on `step` is overwritten by the handler's closing `setAlarm`. An answer in that window waits for the next 15 s tick.

## Ideas beyond the scope

- `requests.open` inserts the row, then announces and marks the run waiting. A failure after the insert makes the retry return the existing row without marking the run waiting. Making the follow-up steps run on the existing-row path too would close it.
- `openRequests` stops at the first call nobody can answer, leaving requests it already opened pending while the run fails. Cancelling them on that path would tidy the cards.
- A rule change could be applied to the live Anthropic agent mid-run instead of at the next launch.
