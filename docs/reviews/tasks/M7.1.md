# M7.1 review

## Verdicts

Round 0, commit 6d8c883: not clean, two must-fix. A chat component imported a value from `@repo/services/runs/types`, and the files service stamped `createdAt` with `new Date()` instead of an injected clock.

Round 1, commit 04eaa31: not clean, one must-fix. The service could take a clock, but `compose.ts` did not pass `infra.clock`.

Round 2, commit a87868e: clean, one nit.

## Decisions

- `FileBlobs` is `{ get, put, delete }` and moves binary bodies. The existing `Blobs` is text only, so `Infra` gets a second field, `fileBlobs`, backed by R2 in `r2-files.ts`. Tests use `memoryFileBlobs()` from `@repo/services/files/memory`.
- `POST /api/files` takes a bearer path and a cookie path. An `Authorization` header selects the bearer path, which accepts only an `hm_run_` token and never falls back to the cookie session. Without the header, Hono's `csrf()` runs and the Clerk session decides. A cross-site form cannot set `Authorization`, so skipping `csrf()` for bearer calls opens nothing.
- A run reads only files its run lists in `input_file_ids` or `output_file_ids`, as the scope says. A file the run uploaded itself is not readable by that run until `completeRun` lists it as an output.
- `GET /files/:id` answers 404 to every refusal of a signed-in caller and 401 to a caller with no session or token.
- `/files/*` needed the `composed` middleware, which only covered `/api/*`. `server.ts` now shares one middleware between the two.
- The composer-owned-file rule (a file uploaded by user U cannot be attached to a run started by user V) was already in `startRun` through `requireFiles`. M7.1 adds a route-level test for it.
- `INPUT_FILES_MAX` and `MAX_FILE_BYTES` live in `@repo/db/shared`, so the chat reads them without importing the services package.
- `files.describe` (tRPC) returns names, sizes and types for the chips. Unknown ids and ids of other workspaces are left out.
- Retry in the chat resends the files of the run it retries.

## Checks

`bun run check && bun run test && bun run build` pass, and `grep -rl drizzle apps/web/dist/client` prints nothing. The four checks from the task file are in `apps/web/src/server/routes/files.test.ts`: run token (download of input and output files, upload with its own run id, 404 for any other file), workspace A against B, a composer upload by U attached by V, and a cross-site form POST. `packages/services/src/files.test.ts` covers the service with a fake R2. The composer was not driven in a browser.

## Nits left

- `chat.tsx` comment above `attachFiles` still says the first failure is shown. A count or size message now hides an upload failure.
- `files-router.ts`, `files.ts` (service) and `use-file-infos.ts` each hold the 100-id cap for `describe`.
- `GET /files/:id` answers 401 with no session, where the scope says 404 on any refusal. Nothing about a file leaks either way.
- `fileResponseHeaders` is exported from `routes/files.ts` and used only there.
- PDFs are served without the CSP `sandbox` on purpose, so Chrome's viewer opens them.

## Ideas beyond the scope

- `request.formData()` buffers the whole upload, up to 50 MB, plus the `File` built from it, inside a Worker with 128 MB of memory. A near-cap upload has not run on a deployed Worker. If it fails there, stream the multipart body to R2 instead.
- A message with only attached files cannot be sent, because `input.text` needs at least one character.
- A run cannot read back the file it uploaded itself before completion.
