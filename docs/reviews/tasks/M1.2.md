# M1.2 review

## Verdicts

Round 1, commit e76786f: must-fix, three findings. Round 2, commit 01c9c84 (the fixes only): clean. One fix round.

The round 1 must-fix items were:

- `canRunAsAgent` used `sudo -l`, which answers from policy and can say yes through a cached password, an unrelated `ALL` rule, or a binary `hm-agent` cannot reach. It now runs `sudo -k -n -u hm-agent <claude> --version`.
- `resolveClaudeBinary` followed `realpath` into a versioned path (`~/.local/share/claude/versions/<v>`) that goes stale at the first auto-update. It now keeps the path `which` finds, and requires it to be absolute.
- `enroll` ignored `--claude`. It is now passed through, and a test covers it.

## Decisions

- Only 4401 stops the client. A 1012 reconnects with backoff, as the task's check says. The backoff counter resets only after a connection has stayed up 30 s past `hello_ack`, so two daemons on one credential settle at about two handshakes a minute and do not storm the relay.
- The relay sends no pong, so the client has no pong timeout. It still times out a missing `hello_ack` after two heartbeats.
- `install-service` runs as the daemon's own user, calls `sudo` itself for `useradd`, `visudo -cf` and `install`, and refuses to run as root. The sudoers rule is checked with `visudo` before it is installed. A failure at any point of the agent-user setup leaves the unit installed and falls back to single_user.
- `enroll` decides `single_user` by running claude as `hm-agent`. The probe runs at enrol, so `install-service` has to run before `enroll`. The config also stores `claudeBinary`, the path the sudoers rule names, for M1.4.
- `build` compiles for the host into `dist/harbourmaster`, so `turbo run build` needs no network. `build:release` cross-compiles `dist/harbourmaster-linux-x64` and `-linux-arm64`.
- `install-service` writes the unit and runs `enable`, not `enable --now`. It restarts the unit only when a config exists, so a machine that is not enrolled yet does not crash-loop.
- `hello.agentSdk` is `"none"` and `agents` is `[]` until M1.4.

## Checks

`bun run check && bun run test && bun run build` pass. The live check ran against `vite dev`: `bun scripts/dev/enroll-token.ts` printed a code, the compiled `dist/harbourmaster enroll` wrote a mode 600 config in a mode 700 directory, `run` connected, and `bun scripts/dev/machines.ts` listed the machine online. Restarting the dev server made the daemon reconnect with 1 s, 1.8 s and 3.9 s delays. SIGTERM stopped it cleanly, also while it waited to reconnect. `build:release` produced both cross-compiled binaries. This box has no sudo, so `single_user` was true, as it should be.

## Nits left

- `--claude` is taken as given and may be relative. The path from `which` is checked.
- The install-service failure text assumes one cause (a private home directory). `canRunAsAgent` returns a boolean, so sudo's stderr is lost.
- That message does not say to pass the same `--claude` to `enroll`. The usage text does.
- "Not on the PATH" also shows for a relative `which` answer or `--claude ""`.
- `enroll.test.ts` still has `sudo` return the binary path as stdout, left from the `sudo -l` probe.
- The probe has no timeout.
- `client.ts` has no connect timeout, because the ack timer starts at `onOpen`.
- A 1012 logs as a bare close. A hint that another daemon may hold the credential would help.
- `sudoersPath` maps `a.b` and `a_b` to one file. The username is not escaped in the rule.
- `hm-agent` gets `/bin/bash`. `sudo` runs the command directly, so `/usr/sbin/nologin` would also work.
- `install-service` run as `bun src/main.ts` writes bun's path into `ExecStart`.
- `run` does not warn when the config is wider than mode 600.
- `build` under turbo compiles a 100 MB binary on every CI run (outputs are cached). `bun-linux-x64` needs AVX2, and the `-baseline` target covers older CPUs.
- SIGHUP has no handler, so closing a terminal ends `run` by the default action.

## Ideas beyond the scope

- Dead-connection detection. With no pong, a socket dead after sleep or a NAT drop goes unnoticed until TCP gives up, about 15 minutes. A relay pong, or a WebSocket-level ping if it works against Workers, would fix it. That touches contract C4.
- `single_user` is fixed at enrol and the hello frame does not carry it, so running `install-service` after `enroll` never corrects the server. Sending it in `hello` would remove the ordering rule.
- A relay-side hint, or a distinct close code, for "another daemon replaced you".

## Steps for Dom

On a box with sudo:

1. Install Claude Code where `hm-agent` can execute it, for example under `/usr/local/bin`. A binary under a 750 home directory (such as `~/.local/bin/claude`) fails the probe, and the machine falls back to single_user.
2. `./dist/harbourmaster install-service [--claude <path>]`. It asks for the sudo password, creates `hm-agent` and `/etc/sudoers.d/harbourmaster-<user>`, and installs the user unit. Lingering must be on (`loginctl enable-linger <user>`), or it exits 2.
3. `bun scripts/dev/enroll-token.ts`, then `./dist/harbourmaster enroll <code> --server <url> [--claude <path>]`, then `./dist/harbourmaster run` or `systemctl --user restart harbourmaster`.
4. `bun scripts/dev/machines.ts` should list the machine online with `single_user=false`.
5. `sudo -u hm-agent cat ~/.harbourmaster/config.json` should be refused.
