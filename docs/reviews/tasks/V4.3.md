## Decisions to know about

- `librarySyncScope` includes `wiki/` as `read`, so a claim's `paths` for older daemons now holds home, wiki and grants. An older daemon syncs every path as writable, so a local edit under `wiki/` fails with a 403 at sync-out, per file and not fatally.
- The cloud VM sync still reads the legacy `runtimeConfig.libraryPaths` (`vm-library-sync.ts`) until V4.7. A legacy path without a matching grant now reads as `not_found` for a cloud run, and the wiki is not synced there. `CloudStart.library.roots` carries the new scope for V4.7.
- The skills-store migration reads the library as a person, because it moves the whole workspace's `skills/` folders and a run cannot read those anymore.
- Legacy `skills/<agentId>/` paths are no longer writable by a run without a grant. V4's skills store replaces that layout.
- `taskFolder` in the claim is V4.9's and is not sent.

## Nits left

- `pendingConflicts` resolves the member twice (an extra agent and grants query per call).
- `stat` on a folder above a grant returns its `updatedBy` and `mtime`.
- A write grant below a path that is a file tells the run a file is in the way.
- A grant on `wiki` or the agent's home shows twice in the Library row of `agent-profile.ts`.
- `listGrants` writes a `library.access` event on every read, and `removeGrant` on a missing grant succeeds and logs an event.
- `cloud/types.ts` and `runs/types.ts` use inline `import("@repo/db/shared")` types.
- `library-access.test.ts` does not cover `readVersion`, `compare`, `restore`, `pendingConflicts` on a file above a grant, or the event payloads, and the machine-claim test titled "legacy claims keep paths only" checks only the live claim.
