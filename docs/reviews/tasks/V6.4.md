## Decisions

A computer-only machine's `machines.credential_hash` holds `computer-only:` plus 32 random bytes (base64url), not a SHA-256 hash. A hash is lowercase hex, so no bearer token matches it. `list` reads the prefix to leave `agent_host` out of `roles`. Nothing in the schema recorded the daemon role (V6.1's review listed it as an open point), and a migration was outside this task. The schema comment now says so.

`createEnrollToken` takes `role` (default `agent_host`) and an optional `machineId`. A `machineId` needs role `computer`. A machine that is gone, revoked or in another workspace is `not_found`, and one that already has a computer is `conflict`. The name is optional when a machine is named, and required otherwise.

`createMachinesService` takes a required `atomic`, because a computer enrol writes two rows (the machine and its credential, or the credential and `computer_status`). `compose.ts`, `scripts/dev/local.ts` and two tests pass it. `openLocalDatabase` now types its db as `BunSQLiteDatabase` so the dev scripts can build `sqliteAtomic`.

`enroll` spends a code only for the role it was minted for, so a daemon body with a computer code (or the reverse) gets null and leaves the code unspent. The spend stays one conditional write.

`revoke` also sets `computer_status` to `offline` and appends `computer.offline` when the computer was online, because the status column is separate from the daemon's `status`. The credential rows stay, since `revoked` is read on every lookup.

`markComputerOnline` stores `{ arch, clientVersion, desktop, os, workdir }` from the hello. `markComputerOffline` takes no reason, because `ComputerPresencePayload` carries only `machineId`.

`attachComputer` takes cloud and managed agents and live machines with the computer role in the same workspace. A clash on V6.1's unique index maps to `conflict`. Detaching (`null`) skips the runtime check. `CloudStart.computer` (`{ desktop, machineId }`) is filled in `cloud/runtime.ts` and left out for a revoked computer.

The HTTP enrol route (`apps/web/src/server/routes/machines.ts`) is unchanged: it still parses the daemon body only. The service already takes the union, so V6.5 or V6.9 swaps in `machineEnrollRequestSchema`.

## Nits left

- Two codes minted for one machine before either is used can both add a computer credential: the second enrol checks `computer_status` first, but the check and the batch are not one statement. The schema has no unique index on (machine, role) to catch it.
- The computer body's `hostname`, `os`, `arch` and `clientVersion` are validated and dropped at enrol. `computer_capabilities` fills at the first hello, and `hostname` is stored nowhere.
- `enrollTokenInputSchema` accepts `machineId` and `machineName` together and ignores the name.
- A computer-only machine's `status` stays `offline`. V3.11 and the machine pickers must read `roles`, not `status`, to tell it from an offline daemon.
- A machine that already has a computer cannot take a second code, so a lost computer credential means revoking the machine (which ends the daemon too).

## Ideas beyond the scope

- A re-enrol path that replaces the computer credential, for a lost credential.
- A unique index on `machine_credentials (machine_id, role)` and a `machines.roles` column, which would also remove the marker prefix.
