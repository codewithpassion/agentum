# V4.2 review

Task: Versioned library writes, compare, restore and retention. Branch task/V4.2-library-versions-service.

## Verdicts

- Round 1 (bbff667): not clean, 2 must-fix, 14 nits.
- Round 2 (7a950f8, fix commit only): clean, 0 must-fix, 5 nits.

Round 1 must-fix items, both fixed in 7a950f8. The next version number was read before the batch, so two concurrent writes to one path collided on the unique index after the live blob was already replaced. `write`, `restore` and `remove` now number the version in SQL inside the batch (`insertNext`), and seeds use `onConflictDoNothing` (`insertSeed`). A rejecting `notify` failed a committed change and, in `remove` and `move`, skipped blob cleanup. `changed` now catches it. Each fix has a test that fails without it.

## What changed

`write`, `remove`, `move` and the new `restore` add `library_versions` rows in the same `atomic` batch as the entry and the event (`packages/services/src/library.ts`, helpers in `library/versions.ts`). A file with no history gets a version 1 snapshot before its first change. A recursive folder `remove` writes one tombstone per file. `move` rewrites the path of the moved versions and adds a `move` version. New methods: `versions`, `readVersion`, `compare`, `restore`, `pruneVersions`. `createLibraryService` takes an optional `notify`. The tRPC router gains `versions`, `readVersion`, `compare`, `restore`, `move` and `stat`.

## Checks

`bun run check && bun run test && bun run build` pass at the head. The reviewer also ran the real service against Miniflare D1 with the migrations and confirmed the numbering subquery counts a seed inserted earlier in the same batch.

## Nits left

1. `library.ts` `writeFile` and `remove` still query `previous` and compute a version number that `insertNext` overwrites.
2. `move` numbers versions in JS with plain `insert` (and offsets when the destination has history), so a write racing a move on the same path can still hit the unique index. It also differs from the refinement's "only the path column".
3. Each moved file gets a `move` version with a full extra copy of its bytes, and bytes are read twice (`prepareMoveVersions`, `copyRows`).
4. Version and seed blobs are written before `atomic`, so a failed batch or a lost seed race leaves an unreferenced blob that prune never sees. A seed read after a racing write can record the new bytes as version 1.
5. `prune` loads every version row across all workspaces into memory per run, with no paging. V4.6 wires the tick job, so scope it then.
6. `compare` skips the `LIBRARY_TEXT_MAX_BYTES` cap that `decodeLibraryText` applies, so it can return two 10 MB texts over tRPC.
7. `versions` and `readVersion` return the whole row including `blobKey`, `sha256` and `workspaceId`.
8. A move notifies `[from, to]` only, while a remove notifies every removed path.
9. `notify` errors are dropped without logging.
10. An entry whose blob is missing now makes `write` and `remove` fail with not_found, where before the next write repaired it.
11. The recursive remove test has one file in the folder.
12. `versions.ts` hard-codes the live object key format and imports a type from `library.ts` (type-only cycle).
