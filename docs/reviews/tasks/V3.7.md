## Decisions

- `agentBuilder.saveDraft`, `dryRun`, `create` and `discard` live in `agent-builder/lifecycle.ts`, exported as `@repo/services/agent-builder/lifecycle` (the input schemas the router uses). `service.ts` composes them and takes `routines` and `runs` as new deps, which `compose.ts` passes.
- `saveDraft` writes `name`, `instructions` (the "does" text, then a "Rules:" list), `soul`, `handsTo` and `runtimeConfig.libraryPaths`. It returns the agent record, so the page reads `id` and `slug` from it.
- No voice preset text existed, so `lifecycle.ts` holds a small map from each preset to its soul text.
- `dryRun` takes the sample chips and sends them as `key: value` lines, or a fixed sentence when the sample is empty. It starts the run with session origin `dry_run` and `private: true` and `{ dryRun: true }`, and returns `{ runId, sessionId }`.
- `create` re-checks the draft with `reconcileDraft` against the current catalogue and refuses while any gap is open, before any write. It then updates the row, activates it with `CLOUD_DEFAULT_MODEL` and the draft's runtime, and assigns connectors and skills, creates each routine (approved, since a person made it), and reserves the address (the `address` input, else `suggestAddress`, skipped when the draft already has one). A failing step stops the rest and the error says what was done and what was not. The agent is already active by then, so a retry of `create` is refused. `mail` and `slack_mention` starts create nothing.
- `adapterFor` in `runs.ts` also picks the cloud adapter for a dry run, so a cancel or sweep reaches the right runtime after the agent's runtime changes.
- Dry runs are filtered out of the desk run lanes and totals, `tasks.list`, and the session list and search. `sessions.get`, `transcript` and `visibleSessions` are untouched, so V3.13 keeps its stream. Their tests: `desk.test.ts`, `tasks/service.test.ts`, `sessions.test.ts`. The "create assigns everything" tests are in `agent-builder/lifecycle.test.ts`, not `service.test.ts`.

## Nits left

- `address` is checked for length only. A bad format or a taken address fails after the agent is active, as a reported partial failure. `suggestAddress` throws for a one-character slug.
- When `activate` fails (for example a bad machine), the earlier `update` has landed and the raw error comes back without the Done / Not done wording. The agent stays a draft.
- Two `create` calls at once both pass the draft check. The second rewrites the now-active agent with `update` and logs an extra `agent.updated` before its `activate` fails.
- `discard` of an archived agent that was never a draft succeeds without saying so.
- The session filter keys on origin `dry_run` and the desk and task filters on `runs.dry_run`. `dry_run` is in the browser's `SESSION_ORIGINS`, so a real run a client puts in such a session shows on the desk but not in the session list.
- `create` is tested on recording fakes. Nothing runs `connectors.assign`, `skillsStore.assign` and `routines.create` on the real services right after `activate`.
- The `dryRun` comment in `runs/types.ts` says a dry run "skips every write", which V3.8's gate does, not `runs.ts`.

## Beyond the scope

- A draft cannot hold connector or skill assignments, because the assign services refuse a non-active agent. A dry run on a draft therefore has no assigned connectors or skills, only the built-in tools. V3.13's browser check ("a dry run of a draft with a write tool shows Would …") needs either assignments that accept a draft or the cloud runtime reading the draft's tools from somewhere else. Decide this before V3.13.
- Drop `dry_run` from the browser's `SESSION_ORIGINS` so a client cannot start a real run in a dry-run session.
