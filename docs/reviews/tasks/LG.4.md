## Delivered behavior

- Browser navigation to `/g/:token` and `/g/a/:artifactId` serves a standalone HTML/client entry before Clerk. It mounts neither the workspace shell nor a Clerk provider. Explicit JSON requests retain the LG.3 route contracts. Invitation GETs only read landing metadata; no send, consume, rotation or view is performed. HTML responses retain no-store/no-referrer headers. The standalone Vite asset is referenced by the client build as well as the Worker build so its URL is present in public assets.
- The invitation page shows title, inviter, workspace, role and expiry. Only “Send me a code” sends mail. Six-digit numeric input uses one-time-code autocomplete; successful verification follows the trusted grant artifact ID. Delivery acknowledgement remains deliberately generic, and failure never claims mail delivery.
- The viewer reuses `DocumentEditor`, `DeckRuntimeGate`, `TicketedRoom` and `TicketedDeckRoom` with guest-only HTTP/image/comment ports. It shows inviter/workspace, current role and “Your visits are logged.” Signout clears access; refusals are revalidated against the current grant before showing “This invite has ended” and the known inviter. A role-refused action is not automatically treated as revoked access. Reconnect constructs a fresh room in place, discarding rejected optimistic state and allowing queued rotations to finish.
- All guest fetches, including protected image downloads and transcript polling, use one serialized queue. Web Locks additionally coordinate that queue across supported browser tabs. Initial join holds the queue through authenticated WebSocket upgrade; it releases before room policy reads, avoiding a handshake deadlock. Subsequent ticket renewal uses the existing socket's stable server reference. Ordinary HTTP rotation does not become a new socket credential. The existing provider renewal tests remain part of root validation; no fifteen-minute wall-clock browser renewal is claimed.
- Canonical `/files/:id` paths remain in shared document/deck state. Guest-owned bytes are downloaded through artifact-scoped endpoints into revocable object URLs. Optional editor/scene display ports render those URLs without changing codecs or shared state. Uploads obtain the owned bytes before inserting a node. Guest history/export ports are absent because no guest history/export contract exists.
- A separate guest comments panel supports threads, replies, selection anchors and resolution at commenter/editor roles. Viewer editing/comment controls are absent or disabled by the existing editors. The shared artifact-origin agent transcript is read-only and polled through the serialized guest endpoint; no member file lookup, member navigation or approval action is exposed.
- The People section in the existing member share dialog supports email invite, viewer/commenter/editor, 1/7/30-day or custom expiry, daily cap (default 20), role change and revoke. Admins can change the workspace “Guests can be invited” switch. Errors do not claim successful delivery. Named-member rows currently display their stored user ID; guest rows display the authorized invited address.
- Guest ask execution remains disabled: document ask ports and all composers are absent, deck ask controls are disabled, and the comments panel explains that restricted execution is unavailable. No readiness or success is fabricated.

## Additive contracts and backend correction

The missing owner/admin People read is now `liveGuests.people({artifactId})`. It uses the same owner/admin and workspace checks as invite mutations, returns only this artifact's non-revoked grants and workspace switch state, and never returns invitation/session credentials. Guest identity joins prove matching workspace. Focused migrated service tests cover authorized rows, non-owner/cross-workspace refusal and absence of token hashes.

The missing guest invitation list is `GET /api/guest/artifacts/:artifactId/invitations`, through the normal rotating-cookie handler. It authorizes the current artifact first and again after reading, and returns at most 1,000 live document/deck grants for that same guest identity and workspace, excluding deleted artifacts, revoked/expired grants and member grants. The viewer shows this small list and navigates in the existing document so a pending cookie response is not cancelled. Tests cover live-list/refusal behavior and actual navigation between two grants in the desktop/mobile browser runs.

Reviewing browser failures also exposed a race in LG.3 `resolveReference`: it read a session token hash and then performed a second grant lookup by that hash. HTTP rotation between those reads could invalidate a still-live stable reference. `findGuestSessionReferenceGrant` now performs the same tenant/artifact/expiry/switch joins directly by persisted session ID in one query. HTTP authentication still requires the current token hash, and signout still deletes the session. No schema, room authority or codec was changed. Existing stable-reference rotation/signout tests and the real workerd browser runs exercise the correction.

Generic guest action refusals do not distinguish revoked access from a role change during an in-flight comment. The client therefore performs a serialized current-grant check before displaying ended access. A browser assertion was also corrected to wait for the actual comment POST response and persisted article before initiating downgrade; textarea text alone was not sufficient evidence of persistence.

## Independent review on merged main `766cfae0e628e3570c1ef5e874dae075f566858e`

**Finding P2 — invitation navigation retains and accepts stale token state.** `guest-entry.tsx` keys the artifact viewer by path but reuses `GuestLanding` when the pathname changes from one invitation token to another. In `landing.tsx`, the token effect neither clears the prior landing, sent/code/error state nor ignores an old response; send and verify likewise have no navigation guard. Consequently browser back/forward between invitation URLs can show the previous artifact and its already-open code form under the new URL while its request is pending or even after it fails. An earlier pending verify can also redirect to the old grant after navigation. The requests still carry their captured tokens and backend authorization remains in force; this finding is a wrong-invitation UI and stale-navigation issue, not an established cross-tenant access bypass. Key the landing by token and fence or cancel all token-bound async completions, including the redirect, and exercise delayed success/failure and navigation while verification is pending. This is established by code inspection; an executable delayed-response reproduction was not completed.
