# M6.2 review: woken agents get their thread id and recent posts

## Verdicts

- Round 1 at ba468a3: must-fix. The wake input told the agent to reply through `inbox_post`, but the run's final text is already delivered to the thread, so a real agent would post twice and fire every mention twice.
- Fix at 04af143: the input now says the final answer posts itself and `inbox_post` with the thread id is for extra messages or mentions.
- Round 2 on 04af143: clean.

## What was built

`packages/services/src/inbox/wake-input.ts` builds the input. The waking post comes first, then the thread id and the `inbox_post` and `inbox_read` instructions, then up to 10 earlier posts (8000 characters in total, 2000 per post, newest kept, oldest first). Earlier posts are one JSON line each between `<untrusted-thread-posts>` markers, with `<` escaped so a post cannot close the block. `inbox.ts` reads the earlier posts and passes them in. No new tables.

Two existing tests expected the fake runtime's echo to equal the bare post. The echo now carries the whole wake input, so they check the start of it and the thread id.

Live check, local dev with the fake runtime: a post `@pelican please reply here` after one plain post gave an echo with the thread id, the instructions and the earlier post inside the block. The fake runtime cannot call `inbox_post`, so that tool call is covered by the existing MCP tests and was not run live.

## Nits left

- An escaped line can grow up to 6x (`<` becomes `<`), so one line can exceed the 8000 budget, and then the block drops with no notice.
- A near-maximum waking post loses up to about 8.3k characters from its end, because the context block takes part of the 100,000 cap.
- `earlierPosts` runs once per mentioned agent in `wakeOne`, not once per post.
- The 10-post cap is applied in both the SQL limit and the builder.
- The input does not say when the caps dropped posts.
- The module comment in `wake-input.ts` still says the block "says where to reply".
- No test pins the wording of the double-post fix.

## Ideas beyond the scope

- Put the waking post's author in the input, so agent B can tell who wrote the post it answers.
- The fake runtime echoes its whole input, so in dev an earlier post that mentions another agent wakes that agent through the echo. The loop guard bounds it. Echoing only the waking post would stop it.
