## Decisions to know about

- A delivery status notification is recognised before the loop guard, because DSNs are usually `Auto-Submitted` themselves.
- A report that is not a delivery status (read receipt, abuse report) is dropped without a row, an event or a run.
- Mail to an agent that is not active is stored and starts no run (`startRun` refuses it and `receive` treats that as stored only).
- Attachments are written with the new run's principal into `<taskFolder>/mail/`, names reduced to a safe basename with collision suffixes. Files over `LIBRARY_FILE_MAX_BYTES` are skipped and named in the run input.
- `mail.setTrigger` is people only and refuses read-only API keys and apps.

## Nits left

- A delayed-delivery DSN (`Action: delayed`) counts as a bounce.
- A redelivery rewrites the attachments (a new library version each time), and a late one writes into a finished run's folder.
- If an attachment write throws, `receive` throws after the run is queued. Only the queued-run sweep picks it up.
- The loop guard knows only the workspace's own addresses. Agents in two workspaces on the shared mail domain can still loop.
- A very long sender `Message-ID` as thread id can exceed the 200-character `externalKey` cap and raise a ZodError.
- The run input is cut at `INPUT_TEXT_MAX` after `JSON.stringify`, and a very long subject can leave the quoted JSON unterminated.
- No test has more ids than one batch for either batched lookup, and no test covers a report with only one of `reportType` and `contentType`.
- Outsider tests cover `thread` and `setTrigger` but not `threads` and `threadForTask`.
- The DSN id regex is anchored to line starts, so an id in an indented or quoted copy of the original's headers is missed. Matching through `In-Reply-To` and `References` of the DSN still works.
- Dropped reports leave no event.
- Nothing builds `InboundMessage.headers` (`reportType`, `contentType`) yet, so the bounce check and the report drop do not trigger outside tests until V5.7's `email()` handler fills them.
