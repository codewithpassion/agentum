# M5.1 review

## Verdicts

Round 0, commit 353b263: not clean. Four must-fix, about twenty nits.

Fix round 1, commits 6d082ee and b3fd4fe (which also merged `main`): clean, eight nits. No further round was needed.

The four round 0 must-fix items, all fixed:

- Agent text reached Slack with `<@U...>`, `<#C...>` and masked links intact. The client now escapes `&`, `<` and `>` in every post.
- The gateway sent any absolute `/connect/` URL privately, whatever its host. It now accepts a relative path or a URL under `PUBLIC_BASE_URL`, replaces every copy in the thread only when the requester can be reached, and records a failed private send in the `slack.delivered` event.
- Two download jobs for one run could overlap (the `waitUntil` job and a sweep, or two sweeps). A download now takes a lease on `runs.lease_until` and clears `pending_files` with a compare-and-set.
- The atomic write was not the only work before the 200: the `run.queued` and `message.user` events and the offer to the runtime came after it. `startRun` takes an `offerLater` option, the two events join the atomic write, and the offer runs in the route's `after` job (the minute sweep re-offers a run whose job was lost).

## Decisions

- `url_verification` is answered without a signature check. The challenge carries no `api_app_id`, and the app row cannot exist yet when Slack checks the URL while an app is being created from a manifest. Echoing a string back gives nothing away.
- The route checks, in this order: capped body (256 KB), JSON, challenge, envelope, app by `api_app_id` (status `installed` only), signature with the app's signing secret, `team_id` equal to the row's. Every failure after the envelope is the same 401.
- The dedupe key is a SHA-256 of app id, channel and message `ts`, not the event id, so a retry and a second event for one message (a DM that also mentions the app) both hit one row. `slack_events_seen` is checked first for the 200, and the unique index covers two deliveries at once.
- One atomic write holds the session, the run, `run.queued`, `message.user`, the dedupe row (with the run id) and `slack.received`. For an unlinked sender it holds the dedupe row and a `slack.unlinked_sender` event. A failed write throws, the route answers 500 and no dedupe row exists. `startRun` got a third argument, `{ alongside, offerLater, pendingFiles }`, for trusted callers inside the Worker, kept out of `StartRunInput`. `message.user` keeps at most 20,000 characters of text in the event of an `offerLater` run (the 64 KB atomic event cannot go to R2); the run row keeps all of it.
- Session key is `team:channel:threadTs`, with `threadTs` the message's own `ts` when it is not in a thread, as the task says. The overview (open question 8) says one session per DM channel. The two disagree; the code follows the task. In the agent view each DM conversation is a thread, so this matches there.
- Only a DM and an `app_mention` are acted on. A channel message without a mention, `app_home_opened` and every other event type are ignored with a 200. The app's own bot user and any message with `bot_id`, `bot_profile` or its own `app_id` are ignored.
- The principal is `{ kind: "user", via: "slack" }` for the Clerk user in `identity_links`. A user is not re-checked against the Clerk organisation at message time, only when the link is made. A user who leaves the org keeps their link until someone deletes the row.
- Unlinked sender: `waitUntil` job reads the Slack email with `users.info`, asks Clerk for the user with that verified address (exactly one match), and links only when that user is a member of the workspace's organisation (`clerkOrgMemberCheck`, cached 60 s). Otherwise the thread gets "I don't know you yet. Ask Dom to add you."
- Pending files: the descriptors (id, name, mimetype, size, URL, team) are stored in `runs.pending_files`; a new column `runs.pending_attempts` counts failed downloads, and the third one fails the run with a `run.failed` event. The attempts are the `waitUntil` job and the next two minute sweeps. `runs.fetchPendingFiles` is the one code path for the job and the sweep. Files go to R2 through the files service as `source: "slack"`, owned by the requester. Types outside a short allow-list (text, images, PDF, JSON, Office, zip) and files over 50 MB are skipped without failing the run.
- `slack_apps` follows the overview: `app_id` is unique across workspaces (it is the lookup key), one row per (agent, team), `signing_secret`, `bot_token` and `client_secret` are ciphertext bound to workspace, table, row and column (`slackSecretBinding`). M5.2 writes them with the same binding. `bot_token`, `client_id` and `client_secret` are nullable for an app still in `created`.
- The gateway posts with up to three tries (429 waits for `Retry-After`, at most 5 s), never throws, and records the outcome as a `slack.delivered` event. A Connect path in the delivered text is found by the pattern `/connect/<id>` because the needs-auth text of M3.3 is the model's to repeat. The M3.3 note moved "ephemeral message when a `connector.needs_auth` event is appended" into M5.2; this task's gateway only handles a link that is in the answer.
- The minute tick trims `slack_events_seen` rows older than a day (`slack.purge-seen`).
- `scripts/dev/seed-slack-app.ts` declares small table shapes of its own instead of importing the schema, because `boundary-lint` keeps `@repo/db/schema/*` inside the services package. It will need a touch if the Slack tables change.
- Fixtures are in `scripts/dev/fixtures/`, read by both `slack-events.test.ts` and `slack-replay.ts`.

## Nits left

- `startRun` with and without `offerLater` stores different `message.user` text above 20,000 characters, and the cut is not tested.
- The download lease is not checked when the file row is stored or when a failure clears it, so a holder that outlives its 5 minutes can upload a second copy (orphaned) or clear a newer holder's lease. A `waitUntil` cannot live that long.
- `replaceAll` of a relative `/connect/x` also rewrites the tail of an absolute URL on another host in the same text, or a longer `/connect/x2`. No link goes out privately; only the visible text is mangled.
- The origin check for a Connect link is case sensitive, and the link pattern allows `..`.
- A relative Connect link is sent bare when `PUBLIC_BASE_URL` is empty (staging and previews).
- Skipped files (too big, wrong type, refused download) are dropped without a note to the agent or the person.
- An archived agent or a refused principal drops the message with a 200 and no reply in Slack.
- An unlinked sender in a public channel gets a public reply, a `users.info` call and a Clerk lookup on every message, with no rate limit.
- The failed-download path writes the failed status and the `run.failed` event in two writes, and tells nobody in Slack.
- Files that downloaded before a later one failed are orphaned, and the retry fetches them again.
- `redirect: "error"` on the file download fails the attempt if Slack answers with a redirect. Not tried against real Slack.
- A real `.html` attachment never arrives, because the client treats an HTML response as a login page.
- The failure injection in the route test rejects the whole `atomic` call. A unit test (`runs.test.ts`) shows a failing extra statement rolls the run back, but the route test does not.
- `slack/apps.ts` has no test file of its own.

## Ideas beyond the scope

- Re-check Clerk organisation membership when a linked user sends a message (cached, so it adds little to the 3 s window), or drop `identity_links` when someone leaves the org.
- Reply in the thread when the agent is archived, when a file is skipped, and when a run fails because its files could not be downloaded.
- Plain replies in a thread the agent already has a session for, without a mention (channel watch territory).
- Pairing codes for unknown senders instead of "ask Dom".
- Rate limit the unlinked-sender reply per Slack user.
- Show the Slack thread's session in the UI with a Slack badge (M6 or later).
