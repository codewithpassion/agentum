## Findings

1. A run queued behind a waiting run dies. An agent runs one run at a time, and the M4.4 sweep fails any run that stays `queued` for more than one hour with "Never claimed". An approval waits up to one hour too. In the first Slack attempt, three runs queued behind a waiting approval and all failed "Never claimed" (for example 01M5VA5X4NF4Y7YPQRZ62G9A13 at 06:16:49). A Slack message to an agent that is waiting on an approval nobody answers is lost the same way. Suggested follow-up: measure the one hour from when the run could start, or skip runs queued behind a waiting run of the same agent.
2. "Always allow" does not remove the rule. `setRule(allow)` flips it to `mode: allow`, and the next call no longer asks. The behaviour is right, but the V1.15 wording ("removes the rule") is not. The Settings list should show an `allow` rule so a person can delete it.
3. The `request` stream frame (`requestFrameSchema` in `packages/protocol/src/stream.ts`) is defined but nothing publishes it. The web learns of requests through the `request.*` event frames. Delete the schema or publish it.
4. Settled cards exist only in a live view. The page builds cards from stream `request.*` events and from still-pending requests, so after a reload an answered, expired or cancelled card is gone. This may be intended.
5. The scrub covers tool rows, not model prose. On cloud the model repeated `sk-test-1234567890abcdef` in its own sentence once (session 01M5V99752N4W69D0S1851N1P7, `message.assistant`). Out of C.19 scope.
6. Agent Task sessions last about 30 minutes. A long check needs a fresh `agent-login` and a new browser session when a call answers 401.
7. For managed runs the `tool.result` event arrived 3 s before `request.expired` for the same request (run 01M5V9RCK8Y9JHS6H9G1SWJ5EX). The poller writes the result from its own poll. Harmless.
