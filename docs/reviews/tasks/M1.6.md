# M1.6 review

## Verdicts

Round 0, commit a3a61d2: clean, ten nits. No fix round was needed.

## Decisions

- Single-user machines only. A run's files move through plain `node:fs` in the work directory. On a multi-user machine hm-agent owns the work directory and the daemon's user cannot read or write it. The daemon fails a run that has input files before it touches the directory ("File transfer is not supported on a multi-user machine yet"), and it refuses every `[ATTACHMENT:path]` marker there with a `[attachment refused: name]` note. The other options were to add `cp` to the sudoers rule and copy through a temp file, or to let the run die on a permission error. Neither fitted a size S task, and none of it can be tried on this box (no sudo, no hm-agent).
- The file routes take the run token, so the files client (`files-api.ts`) is separate from `createRunApi`, which uses the machine credential. File bodies never pass through the masker. Error text does, and also drops the raw run token.
- Input files go to `work/inbox/`. A single-user `prepareWorkDir` empties `inbox/` before every run. A download name is cut to its last path segment, control characters are replaced and leading dots are removed. Two files with one name keep the first and prefix the second with its id. A file that cannot be fetched (including the route's 404 for an id the run does not list) fails the run before Claude Code starts and names the id.
- The first message is the input text, then a list of `inbox/<name>` paths relative to the work directory.
- Markers are read only from the text of a successful result. A marker is uploaded when its path, after `realpath`, is a regular file inside the work directory and at most 50 MB. Anything else is refused and the run still completes as `done`: the marker leaves the text, a `[attachment refused|missing|failed: name]` note takes its place, and the id is left out of `fileIds`.
- Heartbeats now run until the completion body is built, so uploads of large files do not cost the run its lease. An abort during a download or upload stops the transfer and posts `aborted`.
- The 50 MB cap is a local constant that mirrors `MAX_FILE_BYTES`, because the daemon does not import `@repo/db`.
- The claim fixture lists one input file. `executor.test.ts` and `run.test.ts` empty it by default, since `run.test.ts` runs on a multi-user config.
- The route half of the check (404 for a file the run does not list) was written in M7.1 at `apps/web/src/server/routes/files.test.ts`. It is not repeated here.

## Checks

`bun run check && bun run test && bun run build` pass. Daemon tests cover: two input files on disk before the first message and named in it, duplicate names, a 404 download failing the run, multi-user refusal, a marker inside `work/` uploaded with its id in the completion, an absolute path, a marker outside `work/` refused with nothing uploaded, a symlink escaping `work/`, a missing file, a failed upload, multi-user refusal of markers, and an error result never scanned.

Live, on `vite dev` (port 3417) with the compiled daemon under a separate HOME with `~/.claude` linked in: in the browser I attached `note.txt` to a chat message and asked the agent to quote it. The upload, queued run, daemon download into `work/inbox/`, and the reply "The secret word in this file is: albatross-42." all worked. A second message asked the agent to write `out/report.txt` and attach it. The daemon uploaded it as a `run` file (`run_id` set), the run finished with `output_file_ids` holding the id, and the transcript shows a `report.txt` chip next to the `note.txt` one.

## Nits left

- Downloads for all input files run at once and sit in memory before any is written. The server allows up to 100 ids of 50 MB each. `run-files.ts` `fetchInputFiles`.
- `uniqueName` does not re-check the id-prefixed name, and a long name plus the prefix can pass the 255-byte file name limit. Both are very unlikely.
- The size and realpath checks happen before the upload reads the file, so a process the agent left running could change the file in between. The work directory is the agent's own.
- `OutboundFile.mime` and `size` are computed and unused; the upload takes the type from `Bun.file` again.
- `FILE_REQUEST_TIMEOUT_MS` (120 s) covers the whole request, so a 50 MB upload slower than about 3.5 Mbit/s fails and leaves an `[attachment failed]` note.
- No test aborts a run mid-download or mid-upload, or checks that heartbeats continue during a slow upload.
- The non-abort `catch` in `completionBody` builds the completion from the raw text. It cannot be reached today, because `uploadOutputs` catches every failure except an abort.
- Fixed after the review, with no new logic: the header comment of `executor.ts` said heartbeats run until the completion is posted (they run until its body is built), and the multi-user branch of `uploadOutputs` now trims its text like the single-user branch.

## Ideas beyond the scope

- Multi-user file transfer: add `cp` to the sudoers rule and copy through a daemon-owned temp directory, or give the daemon a group-readable `inbox/` and `outbox/`.
- Stream downloads to disk and upload from disk with a progress-based timeout, so the 50 MB cap holds on slow links.
- Show a refused or failed attachment as a chip state in the transcript instead of a text note.

## Steps for Dom

- Multi-user machines cannot take input files or return attachments yet. A run with input files on one fails with a clear message.
- Nothing else needs your accounts or dashboards. The daemon needs no new sudoers entry or Worker setting.
