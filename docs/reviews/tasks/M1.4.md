# M1.4 review

## Verdicts

Round 0, commit 4fdef80: must-fix, one finding. The executor waited for the child's `exit` event only. Bun emits `error` and never `exit` when a process fails to start (no permission on the claude binary, no sudo), so the wait never ended, no completion was posted and the agent's slot stayed taken until the daemon restarted.

Round 1, commit 1b6c863 (the fix and some nits): clean. One fix round.

The fix commit also made the daemon refuse offers once it is stopping, put a 30 s timeout on every call to the Worker, and added an executor test that shows the run's masker holds both needles.

## Decisions

- The claim response now carries `run.workspaceId`. The work directory is `<workspaceId>/<agentId>/work`, and the daemon had no other source for the workspace id: the config holds only the machine id, the run token is opaque, and agent ids alone would have broken the layout the architecture names. The change is additive and touches `packages/protocol`, the claim service, the fixture and three tests. C4 was already amended in M1.1 and M1.3, so I did not treat it as frozen here, but it is a contract change and Dom should know.
- The daemon cannot create or empty a directory that `hm-agent` owns, because `/home/hm-agent` is not open to the daemon's user and the sudoers rule allowed only the claude binary. The rule now also allows `/bin/mkdir` and `/bin/rm`, and carries `CWD=*` so the daemon can start claude with `sudo -D <work dir>` (the daemon's user cannot `chdir` into hm-agent's home itself). Claude under `bypassPermissions` as hm-agent already runs arbitrary commands as that user, so mkdir and rm add no privilege. `CWD=*` needs sudo 1.9.3 or newer. A machine that ran `install-service` under M1.2 keeps the old drop-in until it runs `install-service` again.
- On a `single_user` machine the work directory is `~/harbourmaster/<workspaceId>/<agentId>/work` under the daemon user's home, and no sudo is involved.
- The spawn goes through the SDK's `spawnClaudeCodeProcess`. In multi-user mode the command becomes `sudo -n -u hm-agent -H -D <work dir> <claude> <args>`. sudo's `env_reset` decides what reaches claude, so nothing is on the command line and the daemon's env filter only matters on `single_user` machines. SIGKILL cannot be relayed through sudo, so the abort path in multi-user mode is SIGTERM, then SIGKILL to the sudo process after 5 s.
- The SDK is pinned to 0.2.119, the version bruce-next and the reuse notes were checked against. `hello` reports `claude-agent-sdk@0.2.119` as `agentSdk`.
- `pathToClaudeCodeExecutable` is always `config.claudeBinary`. The compiled daemon cannot find the SDK's bundled `cli.js`, so a machine enrolled without a claude binary fails the run with a message that says so. The compiled binary builds and starts with the SDK in it.
- `resume` is passed only when `session.runtimeMachineId` equals this machine and `runtimeRef` is set. `model` comes from the agent, `maxBudgetUsd` from `runtimeConfig.maxBudgetUsd` when it is a positive number. `canUseTool` is not set, because setting it makes the SDK add `--permission-prompt-tool stdio`.
- The first user message waits behind a gate that opens when `setMcpServers` settles. A `setMcpServers` failure is logged and the run goes on without the servers. Live, the `harbourmaster` entry reports failed because `/mcp` does not exist until M2.1.
- Events are numbered from 1 and sent every 500 ms, one send at a time. A failed send keeps its batch for the next tick, except for a 4xx other than 408 and 429, which drops it. A 409 on events or on a heartbeat aborts the run. A 409 on `complete { status: "aborted" }` counts as done, as the M1.3 review suggested.
- The abort order is fixed: abort the query, wait for the process `exit` or `error` event, flush the events, post the completion, then release the slot. A 1012 close, a relay `cancel`, a signal and a 409 all take this path. The daemon waits for runs to post `aborted` before it exits on SIGINT or SIGTERM.
- The masker covers every body sent to the Worker and the stderr tail that goes into a failure message, with the run token and the machine credential as needles. `[ATTACHMENT:path]` markers pass through as text.
- `/api/dev/offer` is a dev-only route (mounted under `import.meta.env.DEV`) that asks the relay to offer a run. `scripts/e2e/skeleton.ts` writes its runs straight into the local D1 database, as `scripts/dev` does, and nothing else would offer them to the connected daemon before the minute sweep.
- The env filter passes `HOME`, `PATH`, the locale and terminal names, `XDG_*` and `CLAUDE_CONFIG_DIR`. It does not pass the other `CLAUDE_*` names. The first live run showed a daemon started from inside a Claude Code session handing its bridge and child-session variables to the child.
- The fixture under `apps/daemon/fixtures/tool-run/` was recorded from a real Claude Code 2.1.301 run (a tool search, an MCP tool call and a file read), then cut down to the fields the daemon reads and scrubbed of paths, ids and tokens.

## Probes

Both probes ran live in `single_user` mode against a local HTTP MCP server, with Claude Code 2.1.301 and the SDK 0.2.119.

Does `canUseTool` fire under `bypassPermissions`? No. The probe set a `canUseTool` callback and the run made four tool calls (a tool search, an MCP tool and a file read among them). The callback fired 0 times.

Are the servers from `setMcpServers` connected before the first turn? Yes. `setMcpServers` returned `{ added: ["harbourmaster"], errors: {} }` about 5.9 s after the query started (the first connect includes Claude Code's startup). At that point the MCP server had already seen `initialize` and `tools/list`, `mcpServerStatus()` reported `connected` with the tool list, and the `system/init` message listed the server as `connected`. The generator yielded the first user message one millisecond after `setMcpServers` returned.

## Checks

`bun run check && bun run test && bun run build` pass. `bun test apps/daemon` covers the goldens (three event batches and the `done` completion from the recorded stream), the options passed to `queryFn` (`bypassPermissions`, `allowDangerouslySkipPermissions: true`, `strictMcpConfig: true`, the instructions in `systemPrompt.append`, no `mcpServers` key), `setMcpServers` before the first message, `resume` only for a matching machine, a heartbeat 409 and an abort during the MCP handover both posting `aborted` only after the process exits, a process that fails to start, and the masker.

Live, on this box in `single_user` mode, against `vite dev` on a spare port and the compiled `dist/harbourmaster`:

- `bun scripts/e2e/skeleton.ts` passed twice. The reply to the first message contained "Pelican" (the instructions reached the model), the second reply was "heron", and the third prompt, asking which word was requested before, was answered "heron" (the session resumed through `resume`).
- While a run was active, the claude child's `/proc/<pid>/cmdline` held no `hm_run_`, nor did its `environ`. Its argv is the SDK's flags only.
- `grep -r hm_run_` over `~/.harbourmaster`, the work directories and the Claude project directory of the work directory found nothing. A grep over the whole of `~/.claude` finds the prefix, but only in session transcripts of the build agents, which quote source code.
- A run cancelled in the database while Claude Code was in a tool call: the next events post got a 409, the daemon aborted, the process was gone, and the completion went out as `aborted`.
- The Vite log shows no `database is locked`, although the skeleton polls D1 from a second process.

Not run here, because this box has no sudo and no `hm-agent`: the multi-user spawn through `sudo -u hm-agent -D`, the work directory commands through sudo, and the cmdline and grep checks against the `hm-agent` home. The argv is covered by a test; the rest is in the steps for Dom.

## Nits left

- `executor.ts`: any `error` event on the child ends the wait for its exit. Node also emits `error` when `kill()` fails, so a process that is still alive could release the slot early. Checking `pid === undefined` would limit it to start failures.
- `run-api.ts`: `REQUEST_TIMEOUT_MS` has no test.
- `run.ts`: on a 4401 credential rejection the daemon exits without aborting running runs, so their completions are never posted and the leases expire. Their children end when the pipes close.
- `agent-env.ts`: `DENY_EXACT` can never match now that `CLAUDE_` is not an allowed prefix. It stays as a backstop, and its comment still describes it as active.
- `executor.ts`: a failed `api.complete` is logged and not retried. The reaper interrupts the run after the lease, but a finished answer is lost.
- `runtimeConfig.maxTurns` and `allowedTools` are ignored, and `hello.agents` stays `[]`.
- Events that carry a very large tool output go out in one request. The Worker moves anything over 64 KB to R2, but the request body is unbounded.

## Ideas beyond the scope

- A session transcript for resumed runs lives in the `hm-agent` home on one machine. A run on another machine starts without history. Moving agents between machines needs the transcript exported with the session.
- The `tool.result` payload holds the tool output as text only. Images become `[image]`.
- The relay could send a pong, and the daemon could drop a dead socket sooner (M1.2 noted this too).

## Steps for Dom

1. Give `hm-agent` a Claude Code login: `sudo -u hm-agent -H claude`, then sign in. The machine uses this login for every run.
2. Rerun `./dist/harbourmaster install-service [--claude <path>]` on the machine. The sudoers drop-in now also lists `/bin/mkdir`, `/bin/rm` and `CWD=*`, and the old rule does not carry them. `CWD=*` needs sudo 1.9.3 or newer. Check with `sudo visudo -c`.
3. Enrol again if the machine was enrolled while `single_user` was true, so the server records `single_user false`. Then start the daemon and the dev server and run `bun scripts/e2e/skeleton.ts --server <url>`.
4. During a run, check that `cat /proc/<claude pid>/cmdline` holds no `hm_run_`, and that `sudo grep -r hm_run_ /home/hm-agent ~/.harbourmaster` finds nothing. The claude process runs under `sudo -u hm-agent`, so find the pid with `pgrep -u hm-agent claude`.
5. Confirm the work directory is owned by `hm-agent`: `sudo ls -ld /home/hm-agent/harbourmaster/*/*/work`.
