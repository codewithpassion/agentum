# V1.20 review

Task: scrub question displays, keep answers raw on the row (V1 gate MF2 and MF3).

## Verdicts

Round 1, at 064c204: clean, no must-fix. Zero fix rounds.

## What changed

- `requests.open` runs each question's text, header and choices through the masker and `redactText` before it stores and announces the display.
- The row keeps the runtime's own question texts in a new nullable column, `run_requests.question_keys` (migration 0014). `requests.answer` stores the answer raw on the row and maps display-keyed answers back to those texts by index, so `askUserQuestionAnswers` and `outcomeText` see the runtime's wording. Rows from before the migration have no keys and pass through unchanged.
- The `request.answered` event, the tRPC answer result and `listPending` carry the scrubbed answer. `questionKeys` is stripped from the record.
- Slack's `settle` reads the raw outcome, but the settled card renders only the status line, so no answer text reaches Slack. The web card reads events only.

## Nits left

- `records.ts` `runtimeAnswers`: two questions that scrub to the same display text collapse into one answer key on the client, and the first one gets the answer.
- Choice labels now pass `redactText`, and a chosen label is not mapped back to its original. A label shaped like a token reaches the runtime as `[redacted]`. Masking alone already did this for granted secrets.
- The masked-question check lives in `packages/services/src/requests.test.ts` and calls `askUserQuestionAnswers` from there, not in the protocol or daemon tests. It covers the same path.
- The `requestRecord` docstring says "the record a runtime gets", but Slack's `cardOf` also uses it for `display` only.

## Beyond the scope

- Map a chosen choice back to its original label by index, the same way the keys are mapped.
- Key answers by question index in the client contract, which removes the duplicate-display collapse.
