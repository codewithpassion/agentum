## Decisions

- `oauth_clients` has `client_id` unique across workspaces and `workspace_id NOT NULL` with an FK, so a pending row needs a workspace at first sight. A new client is recorded pending in the first allowed Clerk org (in `ALLOWED_ORG_IDS` order) the token's user belongs to. A user in none gets 403 `forbidden` and nothing is recorded, so a stranger on the Clerk instance cannot fill anyone's queue. There is no pending cap for the same reason. A user in several allowed orgs sees the pending row only in the first one.
- The approved row names the workspace and the access (`read` or `write`) of an OAuth principal. `Principal` gained `oauthClient: { access, clientId }`, and `deriveSubject` refuses a read-only OAuth client like a read-only API key, so the rule holds on every bearer route. The resolver's `verifyClerkOAuthToken` now returns `{ access, clientId, userId, workspaceId }`.
- Approval is per client, not per user. Once a client is approved, any member's token for it works, as long as that member belongs to the approved workspace's org. The resolver checks that membership on every request (60 s cache, through the injected `isOrgMember`).
- `oauth-auth.ts` turns a Clerk token into the claim. A pending or revoked client throws `OAuthDeniedError`, which `/mcp` answers with 403 `client_not_approved` and a message naming the client id and `/settings/connected-apps`. The app's own name stays out of the message because whoever registered the app chose it.
- A 401 from `/mcp` now carries `resource_metadata` in `WWW-Authenticate`, and `error="invalid_token"` only when a token was sent. A Clerk outage (or a refused secret key) is a 503 with `Retry-After`, never a 401. The token cache is 60 s per isolate, keyed by SHA-256, and never outlives the token.
- Settings management (list, approve, change access, revoke) needs a session user, like API keys. Approving asks first, names the client id, and flags apps that share a name.
- The `CLERK_ISSUER_URL` override from flightdex was dropped. The issuer comes from the publishable key.
- Approve and revoke write no event, because there are no event types for them.
- The smoke script calls the Clerk Backend API by `fetch` and `/mcp` by raw JSON-RPC, so it adds no dependency.

## Nits left

- The confirm dialog empties its title and text while it fades out, and the duplicate-name warning in it is plain text.
- The dialog asks the member to match the client id the app "was refused with", but that id only appears in the 403 body, which a client such as Claude.ai may not show.
- The duplicate-name check only lowercases, so a look-alike name escapes it.
- A Clerk user in no allowed org who shows a token for an already recorded client gets 403 `client_not_approved` (with the settings URL) rather than `forbidden`, which tells them the client id is known.
- A user in several allowed orgs is sent to `/settings/connected-apps` in whichever org is active, which may not hold the pending row. The home-workspace lookup also asks Clerk once per allowed org.
- The name lookup reads the first 100 OAuth applications and has no timeout.
- `first_seen_by` is stored but not shown.
- The route test asserts `misconfigured: false` only; the `true` case is covered in `clerk-oauth.test.ts`. The log line is the same level as an outage.
- No test drives the confirm dialog (the web package has no React test setup).
- The `.well-known` documents and the 401/403 answers have no CORS headers on `/mcp`, so a browser-based client (MCP Inspector) cannot read the challenge. Claude.ai connectors call from a server.
- The ported `clerk-oauth.ts` still describes verified Clerk behaviour from 2026-09-21 in its header.

## Ideas beyond the scope

- An `oauth_client.approved` and `oauth_client.revoked` event, like `api_key.created`.
- Bind an approval to the user who first showed the client, or to a member list.
- A pending cap per workspace if registration ever opens to strangers.
- A tsconfig for root `scripts/`, so they are type-checked in CI.
- `CLERK_ISSUER_URL` if a custom Clerk domain is ever used.
