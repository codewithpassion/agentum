## Decisions

- A routine is a `triggers` row of kind `routine`, with `cron`, `timezone` (the workspace's unless given), `prompt`, `next_run_at`, `consecutive_errors`, `disabled_at`, `last_error` and `settled_run_id`. `token_hash` and `token_prefix` are now nullable, so migration 0012 rebuilds the table and copies the http rows. `triggers.list`, `revoke` and the summary read only `http` rows. Ids are `rtn_<ulid>`.
- `fireDue` fires each due row with one atomic write through `startRun`'s `alongside` option: the run keyed `trigger:<id>:<slot>` and `UPDATE triggers SET next_run_at = <next> WHERE id = ? AND next_run_at = <slot>`. A duplicate slot undoes the whole write; the run id it tried differs from the one `startRun` returns, so the first run is read back and not dispatched again. A failed write leaves the slot, counts one error, and the next tick retries. Errors count only while the slot is still the one that failed, so a crash after the write (run left `queued`, offered again by the sweep) is not the routine's error. Slots missed while the tick was down collapse into one run, and the next slot is the first after now. Routines of an org outside `ALLOWED_ORG_IDS` do not fire.
- `settleRuns` judges each routine's runs after `settled_run_id` in order, up to the first run that has not ended. A candidate is a routine whose first unjudged run has ended, oldest first. `done` resets the count, `failed` and `interrupted` add one, `cancelled` counts for nothing, and the fifth in a row sets `disabled_at`. One update per routine, guarded by the old count and watermark, sets the count, last error and watermark; `disabled_at` is `coalesce` in SQL so a concurrent pause or resume stays. `runs` got an index on `(actor_id, id)`.
- `cron.ts` is the bruce-next copy (parser folded in) with changes at the DST edges, and its upstream gap test was changed on purpose. A job with `*` in the hour field runs in real time. Any other job runs on the wall clock: the repeated fall-back hour fires once, in the first pass, and a wall time inside a spring-forward gap fires once when the gap ends. The parser reads `5/15` as 5-59/15 and has parser tests. Day and weekday must both match, as upstream.
- Migration number: 0011 was taken by M6.1 on main, so the routines migration is 0012 after the final merge. It was checked on a fresh local D1 with `wrangler d1 migrations apply DB --local`, and on a database with an http trigger row (kept intact).
- The UI is `/routines`: a table (pause, resume, remove) and a create dialog with presets (every few minutes, hourly, daily, weekdays, weekly, monthly) that compile to cron, a custom cron field, and an optional timezone. Presets are in `apps/web/src/components/routines/presets.ts`.

## Nits left

- `fireDue` has no `id` tie-break after `next_run_at`; tied rows come in SQLite's order. Nothing starves.
- `trigger.fired` is written after the atomic write. A crash before it leaves a run without that event, and the read-back path does not add it (the http path has the same gap). Its payload key `requestId` holds the slot, where the http path holds the caller's request id.
- A schedule with no next slot (such as `0 0 31 2 *`, refused at create) leaves an enabled routine with `next_run_at` null if it appears later; nothing records an error.
- A run stuck `queued` blocks judging of that routine's later runs until it ends. The reaper only ends `running` runs.
- One settle call can do up to 100 routines times (1 read + 1 update) in sequence, on top of `fireDue`, against the Worker's subrequest budget.
- The settle comment on the `asc(triggers.id)` tie-break, and the name of the last settle test, claim more than they check.
- `ENDED` in `routines.ts` needs a cast in `judge`.
- Custom cron accepts only the 5-field subset (`*`, number, list, range, step). No names, `L`, `W` or `#`.
- `*/N` with N not dividing 60 gives uneven slots at the hour boundary, as in any cron.

## Ideas beyond the scope

- The queued-run sweep in `runs.ts` takes the oldest 100 `queued` or `offered` runs, and nothing expires a queued run. With 100 runs that can never be claimed (a minutely routine on an offline machine), a healthy run stranded by a crash is never offered again. The controller is filing this as its own task.
- Edit a routine (cron, prompt, timezone) instead of delete and recreate.
- A routines tab on the agent page, as for triggers.
- Show the next five fire times in the create dialog.
- A `routine.disabled` event when a routine switches itself off, and a notice in the inbox.
