# M8.3 review

## Verdicts

- Round 1 (470a998): clean. No must-fix items, thirteen nits.

## Decision: Skills API, not files in the session

A managed agent gets its workspace skills through Anthropic's Skills API. Each Harbourmaster skill (a folder with `SKILL.md` and its other files) is uploaded as one custom skill, and the Anthropic agent lists it in `skills`. The sandbox mounts a listed skill, every file included, under `/workspace/skills/<name>/`, and the agent reads `SKILL.md` from there.

The other option was to put the files into each session's environment as session files. The Skills API won for these reasons:

- The agent attaches skills once, so sessions need no per-session upload step and no extra calls between the session starting and the first message.
- Skills are versioned on Anthropic's side. A changed skill is a new version, and the agent's fingerprint includes the skill refs, so an agent whose skill changed is synced and gets a fresh session, the same path an instruction change takes.
- The agent's skill list is the one place that says what it has, so removing a skill is a detach.

Sync runs at session start (`launch` in `managed/service.ts`), because the Skills API needs the files read from the library as the run. `managed_skills` (migration `0002`) keeps one row per agent and skill with the Anthropic skill id, the version, and a hash of the file paths and etags. An unchanged skill costs no upload. A new skill is uploaded, a changed one gets a new version, and a skill that is gone is detached with the next agent sync and then deleted. A key change clears `managed_skills` with the other Anthropic ids.

A managed agent "Skillful" got the skill `ts-hello` through the Skills tab (`SKILL.md`) and the Library page (`scripts/hello.ts`).

- Asked to use the skill for "pelican", the agent replied `codeword:nacilep:49:net-200`. The script reverses its argument, multiplies the length by 7 and fetches example.com.
- After changing the script (multiplier 8) and asking again for the same word, the reply carried 56 (and 48 for "walrus"), so the new version reached the agent.

It did not reproduce in isolated tests of concurrent and sequential version deletes, nor with an agent or session attached. `deleteSkill` now deletes versions one at a time, and the second removal run deleted cleanly. The cause was not pinned down.

Objects the live check made at Anthropic were deleted: skills, sessions, vaults. Agents cannot be deleted, only archived, so these are archived and stay in the list as archived: the agents of the probe runs and the app's "Skillful" agents. The `harbourmaster` environment predates this task (M8.1) and was left.

## Nits left

- `skills-sync.ts`: a delete that fails with 404 (mirror already gone) keeps the row, so every launch retries and logs again. Treat 404 as removed.
- The failure log in `removeStale` reads only the error name. Reuse `describeError` from `service.ts` so the HTTP status shows.
- A mirror whose delete failed, with the skill re-added with identical files, reuses the old row. The row may point at deleted versions, so the agent sync fails on each launch of that agent until the key changes.
- `mirror`: the loser of a race deletes its upload without a try/catch, so a failed delete fails the launch. `update` has no race guard, so two launches at once leave an orphan version.
- Launch A may list a skill that launch B removed and deleted a moment before, so A's agent sync fails. Concurrent launches only.
- Old versions are never deleted when a new one is made. They pile up until the skill is deleted.
- A local error from `loadLocalSkills` (such as "limited to 200 files and 5 MB") is retried as if Anthropic were down and ends as "Anthropic could not be reached". A skill that Anthropic rejects while Harbourmaster accepts it fails every run of the agent the same way (a name with "claude" in it is the likely case, not verified).
- `loadLocalSkills` repeats the folder grouping and `SKILL.md` check of `loadSkills` in `apps/web/src/server/pi-run-skills.ts`. Every launch re-reads each `SKILL.md`.
- No tests for the race path in `mirror` or for a failed delete in `removeStale`.
- The agent form says "this workspace's skills". The agent gets its own skills and the shared ones, and its own win on a name clash. The old wording was the same.

## Ideas beyond the scope

- Pin the file hash on an etag-free path, or store the hash of content, so a rename that keeps etags is seen.
- One shared mirror per workspace skill instead of one per agent, for the `_shared` skills, which are uploaded once per agent today.
- Delete old skill versions after a newer one is attached, and sweep archived agents' skills.
- Tell a person on the agent's Skills tab which skills reached the managed agent and which were left out, and why.
