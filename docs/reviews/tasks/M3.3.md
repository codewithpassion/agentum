## Decisions

- `createCredentialsService` takes `{ clock, db, fetch, secretsKey }`. The task names `atomic` too, but every write in it is one conditional UPDATE, so the parameter would be unused. `resolve` also takes `workspaceId` and an optional `machineId`, because the rows are scoped by workspace and the `single_user` rule needs the machine. `runContext({ runId, workspaceId })` reads `on_behalf_of_user_id`, `claimed_by` and the session id from the run row, and the proxy passes them on.
- `resolve` returns `ok` with the decrypted header to send (a header connector's own header name, or `Authorization: Bearer` for OAuth), `not_assigned`, `needs_auth` or `retry`. A connector that takes no login resolves `ok` with a null credential. `needs_auth` carries a `cause` (`missing`, `needs_auth`, `revoked`, `no_person`, `single_user_machine`), the owner and the Connect path. The path is null when no person can connect: a `user` mode run for nobody, and the `single_user` case.
- The `single_user` rule: a run for anyone but the person who enrolled the machine resolves the agent credential in `user_or_agent` mode and records `note: "single_user_machine"`. In `user` mode it is `needs_auth`, since that mode never takes the agent's credential. `agent` mode is unchanged.
- Refresh follows the design. The lease is one conditional UPDATE (`version`, `status = 'ok'`, lease null or past). The winner calls the token endpoint once and writes behind `version`, its own lease and `status != 'revoked'`. A loser polls `version` every 100 ms for 5 s with the injected clock's `sleep`, then answers `retry`. `needs_auth` is written only by the winner and only when the token endpoint answers 400 or 401, or the stored endpoint no longer passes the SSRF guard, or there is nothing to refresh with (a header credential, or an OAuth credential without a refresh token). A 5xx, a timeout or a dead connection releases the lease and answers `retry`. `OAuthTokenError` now carries the HTTP status for this.
- Refresh ahead (`expires_at` within two minutes) happens inside `resolve`, and only for a credential that has a refresh token. Its loser does not wait: the token still works, so it is used until it expires.
- `/api/proxy/:connectorId` follows the overview's order: bearer token and run row (`verifyRunToken`), the assignment join (403 and a `proxy.denied` log line), resolve, forward, the cap, one event. A request gets exactly one of `connector.call`, `connector.needs_auth` or `connector.timeout`, so `initialize`, `tools/list` and notifications each log a `connector.call` too. The payload has connector id, JSON-RPC method, tool name, HTTP status, duration, owner kind, the `single_user` note and an outcome, never arguments or results.
- Answers the model sees are JSON-RPC errors with HTTP 200 (`needs_auth` with the Connect link in the text and in `error.data.connectPath`, `retry`, `timeout`, a refused or redirected upstream). The proxy never hands the client a 401, because Claude Code would start an OAuth flow of its own. A 401 from the connector triggers one refresh and one second try.
- The upstream response is read whole inside the cap and returned. Only `content-type`, `mcp-session-id` and `mcp-protocol-version` come back, and only `accept`, `content-type`, `last-event-id`, `mcp-protocol-version` and `mcp-session-id` go out, so the run token never reaches the connector. The login and its token part are replaced with `[redacted]` in the body when a connector echoes them. POST and DELETE are forwarded, GET answers 405 (no server stream through the proxy, which clients accept). The Worker checks the stored URL with the SSRF guard on every call and does not follow redirects.
- The cap is `PROXY_CAP_MS` (5 minutes) and one `AbortSignal.timeout` covers the first try, a refresh and the second try. The route takes `capMs` so a test can use 300 ms against a stub that sleeps 1 s, where the task's check uses `--sleep 310`.
- `buildMcpServers` (in `connectors/mcp-servers.ts`) names each entry after its connector (lowercase, dashes, at most 40 characters, `-2` on a clash, never `harbourmaster`), in assignment order. The claim route uses it, so every assigned connector is in `mcpServers` with the run token and the proxy URL.
- `connectors/test-seed.ts` writes connectors, assignments and encrypted credentials straight to the tables for tests. It is exported from the services package (`./connectors/test-seed`) because the web tests use it too.
- The stub's `--fail-once` does not record the request it refuses, so the refreshed call is the first entry in `stats().calls`.

It adds a provider that refuses (400) and one that is down (503), a connector that echoes the login, and the `single_user` event note.

Live, against `vite dev` on port 3318, the compiled daemon with its own HOME enrolled as a `single_user` machine, the stub behind a cloudflared quick tunnel (the SSRF guard has no loopback exception), and a real Claude Code 2.1.x run with the haiku model: the agent ran `sleep 90` three times (4 minutes 40 seconds with no connector traffic, so the run lease was extended by several heartbeats), then called `mcp__stub__echo` and answered `live-m33`. The daemon log says `mcp servers added: harbourmaster, stub`. The transcript has `tool.call` for `mcp__stub__echo`, and the event log has `connector.call` for `initialize`, `notifications/initialized`, `tools/list` and `tools/call` with tool `echo`. The first attempt showed that Claude Code's Bash tool refuses a bare `sleep`, so the wait used `python3 -c "import time; time.sleep(90)"`.

## Nits left

- `scrub` matches the raw login only. A connector that JSON-escapes it (a `/` as `\/`, a quote) can still echo it past the redaction.
- `BEARER_PREFIX` repeats the `BEARER` regex in `proxy.ts`.
- `outcomeOf` records a connector's 4xx (other than 401 and 403) and 5xx as `ok`. `httpStatus` tells them apart.
- The catch after authentication returns 503 without an event, so a request that already reached the connector and then hit a thrown error (a failing refresh) logs no `connector.call`.
- No proxy test for the `proxy.denied` log line, the 503 from the catch, the `refused` and `redirect` outcomes, or the `single_user` text in `user` mode as the model sees it. The last is covered at the service level.
- A header credential that gets one 401 becomes `needs_auth` for good. That is the design (the provider refused), and it means one flaky 401 disables a pasted key until it is pasted again.
- `isRefusal` counts any 400 or 401 from the token endpoint, not only `invalid_grant`. A missing OAuth client or unparsable config also writes `needs_auth` without asking the provider.
- `refreshedAhead` decrypts the secret a second time. After a successful fenced write, `?? row` would hand out the old row if it vanished.
- `runContext` reads the `runs` table from the credentials service. `resolve`, `refresh` and `runContext` take a raw `workspaceId` and do not call `authorize()`. Every query is scoped by workspace and the proxy is the only caller.
- The upstream response has no size cap, and an SSE answer is held until the stream closes. A server that keeps the stream open after its result ends in `connector.timeout` although the result arrived.
- Refresh ahead runs inside `resolve`, before the request body size check, so a call refused with 413 can still hit the token endpoint.
- The proxy route uses the global `fetch` and the credentials service uses compose's `connectorFetch`. They are the same in production.
- `./connectors/test-seed` is a public export of the services package.

## Ideas beyond the scope

- The Slack gateway sends the needs-auth Connect path as an ephemeral message. No Slack gateway exists yet (only `noneGateway`), so this part of the task is not built. The `connector.needs_auth` event carries the owner, the cause and the Connect path, so the gateway can read them from there when the Slack lane lands.
- A service to revoke a credential. The proxy tests fake it with an UPDATE that sets `status = 'revoked'`, bumps `version` and clears `refreshing_until`, and the real one must do all three.
- Log a `connector.call` only for `tools/call`, if the handshake events turn out to be noise in the transcript view.
- Stream the upstream response for a long SSE answer once the cap is proven on a deployed Worker.
