# V4.26 review

Version prune off the every-minute full scan.

## Verdicts

Round 1 (9598f82): must-fix, two findings.
- Neither prune query used the new `created_at` index, so every run still scanned the whole table. Fixed by ordering the excess query on `created_at, version` and dropping the `ORDER BY` from the expired-delete query. Both plans now search `library_versions_created_at_idx`.
- `dropHistory` re-read a file's whole history, so a version written after the tombstone mid-prune would be deleted. Fixed by bounding it to versions up to the tombstone, with a test.

Round 2 (52a01c7, fix commits only): clean.

## Nits left

- The `version` tiebreak in the excess query's `ORDER BY` adds a temp B-tree sort. Cheap, and harmless.
- Each excess pass restarts at the oldest `created_at`, so it re-reads old rows that are kept as a file's newest 20, once per batch of 90.
- No test pins the query plan. The row-count test would not catch a fall back to a full scan.
- The prune gate reads the wall clock, and `scheduled()` ignores `controller.scheduledTime`. A cron run that starts more than a minute late skips that hour, and a failed prune retries the next hour, not the next minute.
- `tick.test.ts` builds the fake services with an `as unknown as Services` cast.

## Beyond the scope

- A bounded number of passes per tick would cap the first run after a long backlog.
