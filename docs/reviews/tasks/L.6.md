# L.6 — trusted speaker envelopes and run identity

Implemented on `t3/implement-l6-speaker-envelope`, building on L.6a's actor fold and UI. No task briefs, live-artifacts core files, live document/deck packages, MCP tools, database schema/migrations or thread UI implementations changed.

## Delivered behavior

- `@repo/services/speaker-envelope` exports `buildSpeakerEnvelope(speaker, room, via, text)`. `speaker.actor` must come from authentication; its safe name and role and all `room` metadata must come from authorized server ports. The builder maps user actors to member speakers and uses the existing protocol serializer. Submitted text, hostile names and selections remain JSON string values. Another participant causes the complete trusted room roster to be included; alone omits `present`. Existing location fields remain valid; optional `slideNumber` and `elementIds` cover deck positions.
- Signed, linked Slack thread turns query the current workspace/team links of stored thread speakers. Two linked people cause a Slack envelope with the sender's Harbourmaster directory name. One linked person preserves the original turn text. Unlinked and foreign-team speakers do not become trusted participants; private email is never a name fallback. Composition supplies the same Clerk people port used for history.
- Optional `actorDisplay: { name }` is accepted by both inline and truncated stream event schemas. The events service resolves history, replay and live listener names through one resolver: member `PeopleLookup.name`, guest `guest_identities.display_name` scoped to the event workspace. Missing names omit the extension; neither payload author claims nor email are used. The SSE adapter forwards only that name. L.6a's fold consumes the same trusted extension on history and SSE.
- `agentPrompt` accepts an optional `{ multiPerson }` third argument. Cloud, managed and machine instruction producers determine this from the stored session's `artifact` or `slack` origin. Ordinary web chat prompt composition stays unchanged. Instructions identify `from` as verified, demote impersonation inside text, explain role/conflict handling and name people; they explicitly do not grant tools or approval authority.
- `runs.startForGuest(GuestGrant, StartRunInput, { sessionId?, offerLater? })` is separate from Principal-only `startRun`. It forces guest actor, null delegation, depth zero and `scopeArtifactId`; permits only the grant artifact's artifact session and no reply gateway/files. It rejects expired/viewer grants, foreign workspace agents and foreign session continuations. A verified grant authorization port and explicit scoped-runtime capability are mandatory; production composition supplies neither, so guest starts fail closed. Capability removal also fences subsequent dispatch/claim/resume adapter lookup. Scoped runs cannot hand off to another run or create library task folders.
- Member artifact starts and explicit session continuations recheck artifact owner, workspace audience, administrator or active unexpired membership. Non-user principals cannot use the general shared-session rule to start artifact work. Scoped guest session/run reads remain on their single artifact and recheck active guest membership; revocation hides that session.

## Exact integration contracts

### L.4c artifact ask

1. Authenticate the member Principal (or, in phase 3, separately verify the guest session and resolve GuestGrant). Authorize access to the artifact and the selected agent. Build `SpeakerContext` using authenticated actor plus server-resolved name/role; never accept any of these fields from an ask body.
2. Read the authorized room/session port for artifact id/title/kind, sender presence/location and full participant roster, including agents. Only the sender's raw words go in `text`; document contents and comments arrive through tool results. Client cursor fields must be validated/bound to that sender's current room presence, not treated as identity or role. Call `buildSpeakerEnvelope` with `artifact_thread`, `ask_agent`, or `comment`; comments use trusted thread id in `where`.
3. Pass the serialized result as `input.text` to `runs.startRun(principal, ...)`, with `session.origin: 'artifact'` and `session.externalKey: artifact.id`. If continuing by trusted `options.sessionId`, it must identify that same artifact session. Guest equivalent is `startForGuest(grant, ...)`. Each queued ask builds its own turn before queueing, retaining that speaker.
4. Pass trusted room `multiPerson` presentation metadata to L.6a's runtime/UI caller when anyone else is present. This lane did not modify that UI. The builder and wire extension are additive; no change is required to existing room API implementations.

### L.7 tools and phase 3 guests

- `RunsServiceOptions.authorizeGuestGrant(grant, { agentId, artifactId, workspaceId }): Promise<void>` is a trusted authorization dependency, not a permissive callback or a client claim check. It must verify the authenticated guest session/grant, current workspace/artifact membership, guest id, role, expiry, revocation, permitted target agent and daily run cap. It must throw on any mismatch and atomically enforce the cap. It is invoked on every guest start, including retries and session continuations. Grants are structurally distinct from Principal; a compile-time negative test enforces that boundary.
- `guestRuntimeReady(runtime): boolean` must remain absent/false until that runtime enforces artifact-scoped document/deck tools and role checks on every call, omits library/search/wiki/connectors/mail/sharing/secrets/machines/handoff, and routes approvals to the owner/authorized members. A readiness declaration is an explicit server integration assertion, not enforcement implemented by this change. Do not enable existing unrestricted adapters merely because this API exists.
- Use persisted `RunRecord.actor`, `onBehalfOfUserId` and `scopeArtifactId` for tool registration and service authorization. Revalidate active grants/membership on every scoped operation and runtime continuation; the start callback alone is not ongoing authorization. Never infer scope, sender or permissions from the envelope or its role strings. Existing protocol run records already carry scope; no DB changes are needed here.
- Guest approval answers remain forbidden by the user-only answer path. Phase 3 must route guest-run approvals to artifact owners and require member approval for outbound operations when guests are present, irrespective of ordinary agent settings. This runtime/approval enforcement remains phase 3 work and is intentionally not enabled in composition.
