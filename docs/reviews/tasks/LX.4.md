# LX.4 — sandboxed deck embeds

Implementation commit: `b4c55f9f` (`feat(decks): render authorized artifact pages as sandboxed embeds`).

Implemented 2026-10-27 for live-artifacts PRD R4.5 and the deck embed design. This is a bounded member feature with production wiring, rather than an iframe-only prototype. `docs/tasks/LX.4-deck-embeds.md` is intentionally unchanged.

## Production wiring

- `packages/protocol/src/deck.ts` defines the immutable source identity: `artifact:ARTIFACT_UUID:VERSION_ID:SHA256:PATH.html`. Version IDs include the existing ULIDs. The constrained path grammar excludes queries, fragments, escapes, traversal, arbitrary URLs, SVG, and inline HTML.
- `packages/live-deck/src/index.ts` admits `type="embed"` with a required `prop-src` identity. Scene, constrained HTML, local operations, network updates, and checkpoint restore all validate it. The existing host ownership callback must admit the exact identity. Images still require their original `/files/…` grammar. Limits are 16 embeds per slide and 128 per deck, alongside the existing element, nesting, scene, and update limits.
- `packages/services/src/live-artifacts/service.ts` derives authorized source identities from joined artifact/version/file rows with matching workspace IDs, a published version, a nondeleted `page` artifact, and `workspace` audience. Private pages, proposed versions, other workspaces, documents, dashboards, and apps are not eligible. The bounded catalog reads at most 2,000 file rows. This uses existing artifact ownership tables; no schema or migration was added.
- The existing `ownBlobUrls` policy/session field now also carries immutable embed identities for decks. Its TypeScript shape is unchanged. `production-room.ts` already obtains it through `roomPolicy`; all existing `Deck` instances use that exact policy for tools, binary admission, recovery and restore. `artifact-room.ts` refreshes the policy for `deck_read` and returns `embedSources`, enabling agents to discover usable file identities. `deck_write` uses the actual constrained-HTML adapter and guarded room commit, not a separate embed endpoint.
- `liveArtifacts.resolveEmbed` is a workspace/member procedure. It authorizes access to the deck and rechecks the exact source before calling the production `embedUrl` port in `infra.ts`. That port uses the existing artifact view signing key to mint a five-minute, member-only, version/file/hash-bound content URL. Scene state never stores bearer URLs. There is no share/public fallback.
- `artifact-content/routes.ts` remains the serving boundary. An embed claim must name a real manifest HTML file with the expected SHA-256; alternate HTML documents, alternate frame/document destinations, entry redirects, and the generated document page are refused. The version's ordinary relative JS/CSS/image assets and `_hm/bridge.js` continue through the existing route. All response paths retain the existing CSP/header wrapper. Content-addressed R2 blob integrity remains the existing artifact-storage contract.
- `deck-page.tsx` supplies the member resolver and authorized source catalog. The actual editor has a **Embed page** picker; the main editor scene and presentation use `DeckEmbed`. Thumbnails and speaker next-slide previews do not execute embeds. The component validates the resolver's local content URL against the source artifact, version, and file path, refreshes expiring URLs, and shows explicit loading/refusal states.
- `sandbox-frame.tsx` extracts the existing frame/nonce/navigation-blanking shell without its member tRPC import. The existing `ArtifactFrame` still supplies its normal member/link calls. Decks use the shared shell in preview mode, which supplies no privileged tool/storage/message handlers. Sandbox tokens, opaque origin, source/nonce checks, link confirmation, and CSP are preserved. A missing member resolver yields an explicit unavailable message; no guest-to-member identity conversion exists.
- Presentation uses measured scene transforms instead of CSS `zoom`; this fixes actual embedded-control hit testing on narrow Chromium viewports.

## Concurrent edits and export behavior

Embed props and styles retain Y.Map key identity. Guarded HTML writes merge independent embed keys, protect same-key ABA edits, and retain element/type/replacement guards. Human geometry edits do not block an independent agent change; contested keys are skipped with reasons. Existing editor undo origins, room checkpoint transactions and authoritative restore semantics are reused. Restore invalidates retained observations.

Checkpoint HTML explicitly renders an embed placeholder. PPTX and print/PDF rendering produce visible placeholders for pinned embeds and structured `embed_placeholder` warnings, retaining the existing warnings for unsupported flow geometry. The original constrained interchange still preserves source identity. The export/download service has only a minimal inventory integration: it accepts well-formed authorized embed identities so the core can validate a placeholder export; its asset read path still accepts only `/files/…` and never downloads HTML. A real service export test verifies the PPTX placeholder and warning while only the existing PNG is read.

## Independent review — 2026-10-27

Reviewed merged main `13e15c25447cac9fe9b44dedd5d15d3f8fe82615` (implementation `b4c55f9f`, report `f05ac47f`) including the merged LG.3 room integration. **Verdict: changes requested** for the following availability and recovery defects.

### P1 — Removing a source can make an entire deck impossible to edit or restore

Repro: add an authorized embed to a deck, then delete the source page or change its audience so it no longer appears in the workspace catalog. The member resolver correctly refuses a new token, but every subsequent room mutation refreshes policy and `commitDeck` first applies the *existing* complete state to a trial deck under that new policy (`apps/web/src/server/live-artifacts/artifact-room.ts:332`, `:1106`). That fails before the update removing the embed can be applied. The restore path likewise applies the current scene before the requested checkpoint (`:1525`), so restoring a clean checkpoint through the room does not repair it. A fresh room initialized from the checkpoint also validates it against current ownership. Export validation uses the same current inventory, so its placeholder is not a reliable escape for this state. This affects unrelated edits and can strand the deck until the source is made eligible again or an out-of-band repair occurs. Preserve denial of content access and new unauthorized references, but permit removal/replacement and restore of an authorized scene without requiring the old scene to pass current source authorization.

Independent boundary reproduction: constructed a valid deck with one embed, then applied its encoded state to a trial `Deck` whose ownership callback denies that source; it throws `/slide/s/element/e/@prop-src: blob does not belong to artifact`. The room code performs precisely that trial before applying the incoming removal. Existing token expiry itself is handled by refresh; deletion or loss of eligibility is the trigger here.

### P2 — The 2,000-row catalog cap silently excludes valid sources and can invalidate existing decks

`packages/services/src/live-artifacts/service.ts:264` limits joined **file rows** to 2,000 before filtering to valid HTML source identities, with no ordering or pagination. Repro: publish workspace pages whose first 2,000 joined files are assets/non-HTML and then publish an eligible HTML page. That page can be absent from the catalog despite satisfying every permission condition; `resolveEmbed`, room policy, and export inventory all use this same truncated set. An existing embedded identity can also fall outside the selected rows as the workspace grows or query order changes, triggering the P1 failure without any permission change. Bound resource use while ensuring exact source authorization is independent of a truncated discovery listing, and make discovery pagination or truncation explicit.

## Controller remediation of independent review

The room retains only embed identities already present in its admitted scene when refreshing source policy. These remain opaque, editable placeholders after source restriction/deletion, never content permissions. Current member/source authorization is still required by resolveEmbed; newly invented or wrong-hash identities remain refused. The authenticated member policy endpoint includes the room's retained references so reloads and periodic client policy refreshes do not strand the scene. Checkpoint decoding/rendering accepts structurally valid embed identities as placeholders without loading HTML; image ownership validation is unchanged. Room ingress and restore still enforce the admitted/current identity policy.

Source authorization no longer uses a truncated catalog. The query filters HTML paths in SQL and resolver authorization additionally selects the exact artifact/version/hash/path with all tenant and eligibility joins. Room policy is complete; the UI discovery slice remains bounded separately and cannot revoke existing references. This complete room inventory scales with eligible workspace HTML sources; it is not a claim of a constant-cost per-reference policy lookup.

Added actual production-workerd cases with 2,001 additional eligible HTML rows, an existing source beyond the old cutoff, private-source URL refusal while editing/removing/checkpointing its placeholder, member policy retention, and deleted-source removal. Added a separate actual room owner-restore case that removes an unavailable embed. The restore case uses the existing fixture owner admission, not a claim that agents can restore (production member-only restore remains enforced).

## Independent remediation review — 2026-10-28

Reviewed `e17376d5c7fd10e3c460da2221e421c7e33aab31`, including integration `f581181d` and remediation `0cf58ea1`. **Changes requested:**

### P2 — Retaining an unavailable reference admits new uses of that reference

`artifact-room.ts` `refreshPolicy` unions every source in the accepted scene into the same `policy` used by `commitDeck` and the scene adapter's `ownsBlob` callback. That callback is identity-only, not bound to the previously admitted element or occurrence. Once a page becomes private or is deleted, an editor can add a second embed using the same retained identity, or use it elsewhere in the candidate scene, even though it is no longer in the current eligible catalog. The member client policy similarly includes the retained identity. This conflicts with the requested boundary that retention only permit existing opaque references to be edited/removed/restored, without granting new admission. `resolveEmbed` independently rechecks the exact current source and still refuses fresh content; this finding does not claim content disclosure. An independent core probe modeled the room's retained-identity callback and successfully copied the revoked identity into a second element. Bind the exception to accepted occurrences or otherwise distinguish preservation/removal from new admission, including binary updates and restore.

### P2 — A newly initialized room still rejects an unavailable checkpoint

When durable room metadata exists, `initialize` recovers using its saved policy. However, when a room has no saved metadata, `initialize` obtains only current `ownBlobUrls` and applies `initial.state` under that policy before any accepted references can be retained (`artifact-room.ts` initialize/installDeck). If the persisted checkpoint contains a source that has since become unavailable, this fails before the room can open for removal or restoration. The placeholder-only checkpoint codec does not change this admission path. This is specifically a fresh-room/recovery-from-checkpoint boundary, not a claim that normal durable-object restart loses its metadata. An independent core probe applied a valid embedded checkpoint under a deny-all ownership callback and reproduced the ownership exception. Recovery needs a trusted provenance for previously accepted checkpoint references while continuing to reject unadmitted ingress and fresh content authorization.

The exact resolver query now includes workspace, eligible artifact/version, path and hash predicates independently of the 2,000-item discovery slice. The production workerd test actually inserts 2,001 additional HTML rows and verifies the existing identity remains in room policy and resolves. The discovery endpoint still silently slices to 2,000 with no pagination or truncation indicator, so the prior discovery usability concern remains; the former authorization cutoff is removed. The implementation materializes the complete eligible catalog for room policy, so this review makes no constant-cost scaling claim.

The actual production fixture verifies private-source URL refusal, retained client policy, edit/removal and checkpointing; the separate room fixture tests restoring a clean checkpoint. Those fixtures do not exercise adding a second revoked reference or opening a fresh room from a revoked checkpoint. Checkpoint decoding accepts structurally valid embed identities solely as placeholders, while image ownership remains checked; the member resolver performs fresh source authorization. Guest embed and signed fullapp/staging acceptance remain open.

## Controller followup: exact retained elements and cold initialization

Retained source permission is now keyed by slide ID, element ID and source identity; it no longer grants that identity to arbitrary new elements. The core ownership callback supplies the element context through isolated candidates and the MCP scene adapter. The room keeps current eligible sources separately from retained placeholders and refreshes retained bindings after a successful durable mutation. A removed binding cannot authorize later reuse while the source is unavailable.

Cold initialization and durable recovery first validate the entire trusted persisted checkpoint using the closed deck grammar, image ownership and placeholder-only embed identities. Only then are exact existing embed bindings retained. This path is used only for authoritative stored bytes, never incoming WebSocket or tool updates. New edits still need current source eligibility or an exact retained binding, and serving content still requires fresh resolver authorization.
