## Verdicts

One must-fix: Bun 1.3.11's recursive `fs.watch` on Linux reports nothing for files in a folder made after the watch started, and the run's task folder is always made after. Fixed in 958737e: `fsLibraryWatcher` watches each folder on its own, adds a watch for each new folder and reports what a new folder already holds.

Round 2 (958737e, fix commits only): not clean. One must-fix: a folder deleted and made again under the same name was never watched again. Fixed in e57fc5b by unwatching and rewatching it and reporting its contents.

Round 3 (e57fc5b, fix commits only): clean.

## Limit that stays

Bun (1.3.11, Linux) keeps a dead entry for a watched path that was deleted, so a new `fs.watch` on that path sees nothing for the rest of the process. After `rm -rf x && mkdir x`, the daemon reports what `x` holds at that moment, and later edits in `x` wait for the 5-minute checkpoint. Probes: `tmp/V4.5/probe/r2.ts`, `r3.ts`.

## Decisions

- The `library_changed` routing sits in `run-manager.ts` and `executor.ts` (`libraryChanged`), tested in `run-manager.test.ts`, `executor.test.ts` and `library-sync.test.ts`, not in `client.test.ts`. The client only passes the frame on, and `client.test.ts` checks that.
- The watcher is skipped on a multi-user machine: hm-agent owns the work directory and the daemon user cannot watch it. Those runs keep the checkpoint, and the prompt says changes go back when the run ends. A pull on announce works there.
- A claim without `roots` (or with an empty list) falls back to `paths` as write roots. Without a library copy the prompt has no task folder and no marker sentence.
- `apps/daemon/package.json` declares `@repo/db` for `taskFolderPath` (the daemon already got it through `@repo/protocol`).
- Removed with the marker code: `attachments.ts` (and its test), `WorkFiles.read` and `resolveOutbound`, `uploadOutputs`, the `fileIds` completion path.

## Nits left

- `files-api.ts` `upload` and its tests are unused in the daemon now. The Worker route stays.
- `AGENT_HEAD` and `AGENT_REALPATH` in `agent-user.ts` are unused now and still in the sudoers rule that `install-service` writes, with a comment about attachments. Dropping them changes the sudoers output, so it is left for a decision.
- Files a pull writes fire the watcher, so each `library_changed` pull is followed by one sync out that finds nothing to send.
- `covered` does no path cleanup (a trailing slash on a root or an announced path does not match).
- One inotify watch per folder of the library copy. A very large library could hit the limit, and then the watcher falls back to checkpoints with a warning.
- `run.test.ts` checks the `library_changed` frame is logged and harmless, not that it reaches the manager (`run-manager.test.ts` covers the manager).

## Ideas beyond the scope

- A periodic rescan of watched folders would close the Bun delete-and-recreate gap, at the cost of repeating the checkpoint.
- Skip the sync out that follows a pull by ignoring the paths the pull wrote.
