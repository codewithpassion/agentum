## Decisions to know about

- A missing `CF_EMAIL_ROUTING_TOKEN` is the "provisioning pending" state. An adapter without the token throws `RoutingNotConfiguredError`. `provision` then keeps the row at `provisioning` with `last_error` "Provisioning pending: Cloudflare Email Routing is not configured yet", logs no event, and `provisionPending` retries it. Any other routing error sets `failed`, logs `mailbox.failed` and keeps the reason.
- `provision` emits `mailbox.provisioned` and `mailbox.failed`. `disable` emits nothing.
- The mail trigger row has the id `mail:<mailboxId>`, is created enabled, and survives retries. `disable` sets `disabled_at` on it, and an explicit `provision` of a disabled mailbox clears it.
- `EmailRoutingPort.findRule` returns `{ id, managed }`. This is a change to the V5.1 port. V5.7's adapter must name rules `harbourmaster:<address>` in `createRule` and return `managed: true` for such a rule, otherwise a crash between rule creation and the row update leaves the mailbox `failed` for good.
- The service sits in `packages/services/src/mail/index.ts` (barrel and implementation together), exported as `@repo/services/mail`.
- Without `mailbox`, `mailRouting` and `mailDomain` in the infra, `provision` answers "Mail is not set up here" and writes no row. `provisionPending` returns at once.

## Nits left

- `deleteRule` failing during an address change writes no `mailbox.failed` event, and `disable` lets a `RoutingNotConfiguredError` out raw.
- The event listener makes two Cloudflare calls inside the agent create or reserve request (the refinements chose this).
- A lost race in `prepare` can still make both callers run `route`, which could orphan a rule and log `mailbox.provisioned` twice. The window is the listener against the minute tick.
- An agent that is refused every time (its address held by another agent's disabled row) is retried and logged each tick, and the user never sees it because no row is written.
- The sweep has no ORDER BY, and the sweep test relies on insertion order.
- `prepareFailed`'s race path has no test.
- The system principal's first `authorize` call uses the made-up workspace id "system", and the "taken in another workspace" check stays next to the `findRule` check although the refinements said to replace it.
- Adopting a managed rule is by name alone, so two environments sharing one zone and domain could adopt each other's rules.
