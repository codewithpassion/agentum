# V2.16 review

## Cause

Seen on staging with `agent-login`. The pending-session gate calls `window.location.assign` after it activates the organisation. The loader requests in flight on the old page (`agents.list`, from the `_app` and `/desk` loaders) are aborted by the unload. Fetch rejects them with "Failed to fetch", and the router logs a `TRPCClientError` in the console. A page that is already signed in does not show it. It was not a real failing route.

## Fix

`apps/web/src/integrations/trpc/unload-safe-fetch.ts` wraps the browser fetch of the tRPC link. A request that fails after `pagehide` stays pending, and `pageshow` clears the flag. `client.ts` builds one wrapper for the page. The SSR link is untouched. About 46 lines with the wrapper and its wiring, plus 4 tests.

Checked locally with a delayed `/api/trpc` response and a reload during a client navigation: three "Failed to fetch" errors without the change, none with it. The staging check could not be re-run without a deploy.

## Verdicts

Round 1 (a8ef9ae): clean. Nits only, none applied.

## Nits left

- The fix assumes `pagehide` fires before the aborted fetch rejects. True in Chromium. Firefox may cancel on navigation start, so the error could still show there.
- A page restored from the back/forward cache with a failed in-flight fetch would keep that promise pending. Browsers keep such pages out of the cache today.
- Every failure while unloading is swallowed, including mutations. Harmless on a dying page.
- The "stays pending" test fires `pagehide` before the request starts, not between start and rejection.

## Ideas beyond scope

The router logs loader errors to the console on its own. A shared error boundary for loader failures could show a real failure to the user instead.

## Steps for Dom

Deploy to staging, then run `bun run agent-login --env staging` from `apps/web` in a fresh browser session and check the console on `/desk`, `/agents` and `/sessions`.
