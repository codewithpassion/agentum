## Decisions to know about

- Mail approvals are keyed on tool `mail_send` and a `mail:` tool use id together, not on the prefix alone, so a daemon cannot open a prefixed approval that never wakes a run.
- A message whose release or approval opening failed gets the status `failed`. No `mail.failed` event exists, so the outcome shows in `mail_read` only.
- `mail.today` counts a held message only when it was created today in the workspace timezone.
- The `agent-profile.ts` filter for `mail:` keys changes nothing today, because mail rules are always `allow`. It guards against a future `ask` mail rule.
- Expiry runs from the minute tick on production only, so staging cannot show it.

## Nits left

- The decision handler does not claim the message before `release` or `discard`, so two concurrent handlers for one request could both send. One handler runs per event today.
- `failHeld` discards before it sets the status. A failing discard hides the original error and leaves the message `held`.
- If `requests.open` fails after it inserted the row, a pending approval can stay visible and answering it does nothing.
- `today` leaves out a mail held on an earlier day and still pending. It also lists disabled mailboxes, and a disabled mailbox address still counts as inside.
- No test covers a mail approval that is still pending in a managed run (`waitingOf`).
