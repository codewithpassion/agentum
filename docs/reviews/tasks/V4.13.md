# V4.13 review

Library and wiki MCP tools. Implemented in Codex (commits 1a19a99, 9edb7e7), then checked and fixed by the dispatcher.

## Verdicts

Round 1 (540c16a): must-fix, two findings.
- `library_write` refused valid base64 above about 2 to 4 MB because the validator regex repeated a group per 4 characters. Fixed with a linear check and a 10 MB round trip test.
- The etag conflict test only passed through a made-up message. `library_write` now catches a `conflict` ToolError and adds re-read and retry guidance, tested with the service's real text.

Round 2 (57dd2ce): clean.

## Nits left

- `library.test.ts` tests only `%%%` as malformed base64. No tests for `====`, whitespace, url-safe characters or the empty string.
- The conflict wrapper adds ". " after the service message, so a message that already ends in a period would show "..".
- The refused-path test fakes a `forbidden` message. The real service answers `not_found` for refused reads.
- `library_read` has no size cap. A 10 MB file comes back as about 14 MB of base64, twice (structuredContent and text).
- The web stub ports reject with a plain Error, so until V4.21 the six tools show in `tools/list` and answer the generic failure text.
- A leading `/library/` in a path is not stripped or rejected.
- `wiki_suggest_edit` `body` has no `.max` in the schema, the service enforces it.
- `MAX_FILE_BYTES` copies `LIBRARY_FILE_MAX_BYTES` from `@repo/db/shared`, with no comment naming the source.

## Beyond the scope

- `apps/web/src/server/mcp/base64.ts` has an older strict base64 validator that strips whitespace. V4.21 should pick one validator.
- V4.21 adapters must map `versions()` rows to `LibraryVersionInfo` and drop `blobKey` and `workspaceId`.
