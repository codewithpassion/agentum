# V5.7 review

Implementation by Haiku workers (the routing adapter and the inbound handler) and the dispatcher (wiring, services, tests).

## Verdicts

- Round 1, at 33aadb6: not clean. One must-fix. The routing adapter required `total_pages` in `result_info`, and the Cloudflare list may leave it out, which would have failed every `findRule` with "HTTP 200".
- Round 2, at e7e7f96: clean. The adapter now stops on a short page when `total_pages` is missing. The same commit makes the inbound handler reject a message PostalMime throws on, and cancel the reader on an oversize stream.

## What was built

- `apps/web/src/server/email-routing.ts`: `createEmailRoutingPort`, the `EmailRoutingPort` over `/zones/<zone>/email/routing/rules`. Rules are named `harbourmaster:<address>` with a literal `to` matcher and a `worker` action. `findRule` returns `managed: true` for that name. A missing token, zone or Worker name throws `RoutingNotConfiguredError` before any request, so mailboxes stay "provisioning pending".
- `apps/web/src/server/mail-inbound.ts` and the `email` export in `server.ts`: reads the stream, parses with PostalMime and calls `mail.receive`. It fills `InboundMessage.headers` (`contentType`, `reportType`, `autoSubmitted`, `listId`, `precedence`), so the V5.4 bounce check and read-receipt drop now fire. Over 10 MiB, an unknown address and an unparseable message are rejected. An error from `receive` propagates so the sender retries.
- `apps/web/src/server/mail-infra.ts` and `compose.ts`: the mailbox port over the `MAILBOX` Durable Objects, `FILES` and the `EMAIL` binding, plus the routing adapter. An empty `MAIL_DOMAIN` leaves the three infra fields unset, which turns mail off.
- `tick/runtime.ts`: `mail.provision-pending` beside `requests.expire`.
- `packages/services/src/mail/agent.ts` (`mail.agent`): `hasActiveMailbox`, `listThreads` and `readThread` for a run principal, and `isActiveAddress` for the system. Thread and message ids are the D1 ids that `send` and `reply` return, and each message carries its D1 status.
- `apps/web/src/server/mcp/mail-ports.ts` and `routes/mcp.ts`: the `mail` port group, and `mail: true` only for a run whose agent has an active mailbox. A `MailError` becomes a tool error the agent can act on.
- `wrangler.jsonc`: `send_email` `EMAIL`, `MAIL_DOMAIN`, `MAIL_ZONE_ID` and `MAIL_WORKER_NAME` at the top level, in `env.staging` and in `env.staging.previews`. `.env.example` lists `CF_EMAIL_ROUTING_TOKEN`.
- Two small changes elsewhere: the sent result of `mail.send` and `mail.reply` now carries `rfcMessageId` (the MCP result type needs it), and `packages/mailbox/src/inbound.ts` slices the raw bytes before hashing so apps/web type-checks it.

## Decisions to know about

- The `MailboxDO` stub satisfies `MailboxClient` without a cast. `tsc` is the type test V5.6 asked for.
- Production `MAIL_DOMAIN`, `MAIL_ZONE_ID` and staging `MAIL_ZONE_ID` are empty strings. Mail is off in production and "provisioning pending" on staging until they are set.
- The Cloudflare rules API request body comes from my knowledge of the API, not from the docs search (it did not return the reference). The fake-fetch tests pin the body I expect. V5.12 confirms it against the real zone.
- The `email` handler does not use `ctx.waitUntil`, so run start happens inside the SMTP session. The decision record allowed either.

## Nits left

- `findRule` has no page cap when `total_pages` is missing. An API that ignored `page` and kept returning 50 non-matching rules would loop forever. The biome-ignore reason in `email-routing.ts` still mentions `total_pages`.
- `deleteRule` compares the error code to the string "not found", and Cloudflare codes are numbers. Only the 404 path works.
- `managed` is decided by the rule name alone, so staging and production on one zone could adopt each other's rules for the same address (also in the V5.3 review).
- `await reader.cancel()` on an already errored stream can reject, and `toInboundMessage` errors (a malformed base64 attachment hitting `atob`) still make the sender retry.
- A `user+tag@` recipient is rejected as "Unknown address" if subaddressing is on for the zone.
- `hasActiveMailbox` ignores whether mail infra is configured. With `MAIL_DOMAIN` empty and a leftover active row, the tools are listed and every call fails with "Mail is not set up here".
- `mail.agent`'s `authorize` call checks a principal's workspace against itself. The queries do the real scoping.
- A message in the mailbox store with no D1 row (a crash between store and index) keeps its store id in `readThread`.
- `.slice()` before the digest copies up to 10 MiB for mail with no `Message-ID`.

## Ideas beyond the scope

- Hide the mail tools when mail infra is off, with one flag from `compose` instead of the DB check alone.
- Use `ctx.waitUntil` for the run start in the `email` handler.

## Steps for Dom

- Create the Cloudflare API token (Zone, Email Routing Rules, Edit on `rockyshoreslabs.io`) and give it to the controller for `wrangler secret put CF_EMAIL_ROUTING_TOKEN --env staging`.
- Set `MAIL_ZONE_ID` in `env.staging.vars` to the zone id of `rockyshoreslabs.io` (the zone's Overview page). Until then staging mailboxes stay "provisioning pending".
- For production, pick the mail domain, turn on Email Routing and Email Sending for it, then set `MAIL_DOMAIN` and `MAIL_ZONE_ID` in the top-level vars, and `CF_EMAIL_ROUTING_TOKEN` as a production secret.

For the controller: the first deploy of a Worker that has `send_email` and the `MailboxDO` migration (`v6`, already in main) goes out with `wrangler deploy`. V5.12 should test on staging that a throwing `email()` handler makes the sender retry, and that the rules request body is accepted.
