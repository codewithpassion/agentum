## Delivered service behavior

- startForGuest still takes a distinct GuestGrant, but now also requires an authenticated guest session credential in trusted options.guestSessionToken. A callback accepting a submitted grant is insufficient: the service hashes the credential, tenant-joins the current session, identity, artifact and grant, and compares the guest, role and expiry. Viewer grants, expired/revoked/deleted access, workspace mismatches, absent readiness, absent authorization policy and absent emergency-switch wiring refuse.
- Each inserted guest run records immutable provenance in guest_run_scopes: workspace, run, exact member grant and stable authenticated session ID. Session credential rotation keeps authority because the session ID persists. Signout/deletion/expiry ends it. Reissuing a grant does not revive runs bound to the revoked grant. Legacy scoped rows without provenance fail closed.
- The cap assertion executes BEFORE inserting a run, in the SAME Atomic write as session selection/creation, the run, its provenance and queued events. It rechecks current database guest authority inside the transaction. SQLite/D1 write serialization makes the counted starts and insertion indivisible; separately constructed services cannot overspend a budget.
- The policy is UTC calendar days, keyed by workspace and guest identity. Count all guest starts across that workspace's artifacts against the CURRENT selected invitation's agent_runs_per_day (default 20; zero denies). Different invitations can set different ceilings, but each compares against the same total spent. A newly inserted run costs one even if later cancelled, failed or interrupted. A continuation with a new requestId costs one; a retry with the same workspace requestId, agent, actor and scope returns the existing run without another insertion/charge. Cross-caller/agent/artifact key reuse remains conflict. Retain run/provenance history: there is no refund or budget reset through cancellation or re-invitation.
- A cap refusal, revoked/expired grant, invalid session or switch refusal rolls back every insertion-side row. Request-key recovery rechecks current authority before returning a previously valid run, so revocation racing a retry cannot recover stale authority. Infrastructure errors are not disguised as cap errors.
- Dispatch/re-offer, system claim, resume, approval delivery, heartbeat, event ingestion, completion and scoped run reads revalidate current guest access. Conditional claim/wait/resume/heartbeat/completion SQL also checks the exact live provenance, session, grant, artifact, active agent and workspace switch. Revocation between preflight and the claim/resume UPDATE cannot change the run's state. Lease/terminal cleanup remains available; cancellation and abandonment bypass execution admission so an expired guest can still be stopped.
- authorizeScopedRun(principal, runId) is the shared current lifecycle guard. Run principals must match the stored run ID/agent/workspace. Requests call it before scoped reads/operations. SessionsService requires this port for scoped callers and refuses them if omitted; its visibility predicate also checks exact current provenance, session, grant and workspace authority.
- Guest requests stay in the shared artifact session. The existing Needs-you/desk path consumes requests.listPending: the owner sees these requests even though onBehalfOfUserId is null, and any currently authorized member who sees the session can answer. A guest/run principal cannot answer. Answer/cancel SQL rechecks member session visibility and current guest authority at the write. Scoped pending inserts are also current-authority guarded. All scoped needsApproval calls require approval regardless of stored agent rules. Guest takeover requests are denied. Expiring requests for ended guest authority closes them without resuming the runtime.
- Ordinary daemon claims include general secrets, connector configuration and library capabilities. They now categorically refuse scoped guest runs BEFORE signing a token or resolving secrets. Machine reconnect offers omit them and the existing machine runtime refuses scoped dispatch. This is a deliberate execution gate, not a claim that the ordinary daemon payload has become safe.

## Error contract

Guest run authorization/configuration/cap refusals use ForbiddenError with code forbidden and message "Not allowed: runs.guest_access". Atomic cap assertions use an existing NOT NULL constraint internally, translated only when that exact SQLite assertion is found through the Drizzle/D1 cause chain; SQL/credential details are not returned. Malformed typed inputs retain existing schema validation errors. Foreign idempotency-key reuse remains ServiceError(conflict); ordinary missing resources and lifecycle state conflicts retain existing not_found/conflict behavior. Read-hidden ordinary sessions retain not_found; missing SessionsService scoped authorization wiring also hides the session.

A state change racing an operation can prevent its conditional write. Ordinary state contention remains a conflict/false result; claim/resume/heartbeat recheck guest authority after a failed conditional write so an access loss is reported as guest_access. No claim or resume is granted by an envelope or cached role string.

10. Revalidate open room/HTTP/SSE connections and active tool work when the guest session/grant expires, is revoked, or workspace/emergency switches change. Rooms must close affected sockets within the PRD deadline. Lifecycle guards stop the next dispatch/claim/resume/read/write admission; they do not replace room socket invalidation or interrupt a tool already executing remotely. ## Independent security review on main cdce1739

Verdict: **changes required before guest execution is enabled; no approval**. One medium-severity lifecycle race is established below. This is a bounded service-leaf finding, not a claim of a currently reachable production guest exploit: current web composition does not configure the guest execution admission ports, and the existing machine runtime and machine claim refuse scoped runs. The previous incomplete recheck remains superseded by this review, not an approval.

### Finding — event ingestion can commit after revocation (medium, enablement blocker)

`ingestRunEvents` in `packages/services/src/runs.ts` checks current provenance through `authorizeRunWrite`/`adapterFor` before loading the last sequence and awaiting the secret masker. It then appends each event without a current-guest predicate at the write. A grant or session can be revoked during that await; the already-admitted batch still writes events after access has ended. This contradicts the delivered claim that event ingestion is fenced at the admission boundary. It can persist and publish guest-run output after revocation; this evidence does not establish arbitrary tool execution or a currently exposed production route.

Independent migrated-SQLite reproduction: create a valid guest run, claim it as system, and configure `secrets.maskerFor` to revoke its `artifact_members` row before returning null. Call `ingestRunEvents` with sequence 1 and a `message.assistant` payload. The call returns `lastSeq: 1` and the event is present after revocation; a subsequent `authorizeScopedRun` rejects with `ForbiddenError`. The probe uses the actual service and `sqliteAtomic` on a database with all migrations and foreign keys enabled. Fix the write boundary so each scoped event append is conditional on current exact provenance, and test revocation/session expiry/workspace switch races after preflight and between events in a batch. Treat the external emergency switch and effect delivery as separate integration concerns: a database predicate cannot atomically observe an external callback.

### Scope and evidence

Reviewed migration 0030, its provenance constraints and index; guest session authentication and current SQL predicates; start, retry recovery, dispatch, system and machine claims, wait/resume, event ingestion, scoped run/session reads, and request open/answer/cancel paths; machine adapter; `GuestGrant` and relevant service/composition call sites. `GuestGrant` is a strict schema structurally distinct from the `Principal` union; the existing compile-only negative test exercises the boundary. This uses one local SQLite connection and scheduled concurrent promises, not independent D1 deployment or multi-process contention evidence. The probes support the bounded behavior but cannot prove all D1 interleavings. Dispatch and resume delivery are preflight checks across an external adapter boundary, not atomic revocation of work already handed off. ### Controller ingestion remediation

Each scoped event append now uses a conditional INSERT with the exact current guest-run provenance predicate, evaluated after masking/payload IO and at the database write. The external emergency switch is rechecked immediately before constructing that write; it remains an external admission check, not a database-atomic external guarantee. A refused insert throws before sequence advancement or listener notification. Ordinary event append and atomic insert share the row builder. Payload blob writes can precede refusal, leaving an unreferenced blob as in the existing blob-first event path; no event row or event notification exposes it.

Nine migrated-SQLite regressions passed (27 assertions): grant revocation, session expiry and workspace disablement during masker await, payload blob await and immediately before the second insert. They verify zero events after pre-first-write revocation, only the first already-admitted event for a mid-batch revocation, and refusal of subsequent retries. Production guest execution remains disabled; independent remediation review and integration acceptance remain open.
