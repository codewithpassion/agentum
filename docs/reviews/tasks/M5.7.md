# M5.7 review: agents start Slack messages in channels and DMs

## Verdicts

- Round 1 (d46bfe5): not clean. One must-fix: in a thread the agent started from a `ui` or private session, another linked person's reply or mention went to the owner's session and was dropped by the actor check in `findSession`.
- Round 2 (2f6c835, fix commit only): clean.

## Fixed in round 2

- Another person's mention in such a thread opens its own Slack session for the thread. Their plain thread reply is ignored.
- A `not_in_channel` or `channel_not_found` answer from Slack now tells the agent to ask for an `/invite`, not to reinstall.
- A port comment now says `to` is the resolved target.

## Nits left

- The send cap counts events before the post, so parallel runs of one agent can pass 30. A send whose record write fails is not counted.
- `to` as an email still calls `users.info` once per linked person before matching.
- `findThreadSession` runs twice per thread reply (gate and `admitRun`).
- The `ui`/private actor rule in `slack.ts` repeats the one in `findSession`.
- After another person's mention opens the fallback session, their later plain replies in that thread are ignored, because only the agent's own thread row is checked. Mentions continue it.
- The fallback session has no history of the `ui` session that posted the message.
- `slack_send` and `slack_destinations` are listed for every non-read-only caller. They refuse with a clear message when the caller is not an agent run or the agent has no Slack app.
- The "Harbourmaster name" of a linked person in `slack_destinations` is the link's email, because there is no user name table.
- If an agent has Slack apps in several Slack teams, the oldest installed one is used.
- `threads.test.ts` no longer checks the actor fields. No tests for the private-session branch, or for `channel_not_found` on a DM post.
- `row.origin as SessionOrigin` in `threads.ts` is an unchecked cast.

## Ideas beyond the scope

- Let a reply from anyone in the workspace reach the agent's session when the thread came from a routine or trigger (no owner).
- Show the `slack.message_sent` events in the Log with the channel name. They already carry it.
- A per-agent setting for the hourly cap.
- Document `slack_send` in `docs/architecture/build-plan.html` and `reuse.html`, which list tool names.
