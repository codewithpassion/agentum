# M6 gate review (M6.1, with M2.3's use of it) at abb446e

## Verdict

Clean. Nothing is must-fix. The work covers all of M6 in `docs/architecture/build-plan.html#m6`: the two tables, `createInboxService({ db, atomic, ... })` and its router, the `@slug` parser, user and run wakes, the inbox gateway, both loop-guard rules with `inbox.loop_stopped`, and the inbox page. M2.3's `inbox_list`, `inbox_read` and `inbox_post` call the same service methods through `apps/web/src/server/mcp/ports.ts`, so they go through the same `authorize()` and the same wake path as the UI.

## What I checked

- The M6.1 merge is 5895bae and the M2.3 merge is 8f5c237, both in `m6-start..abb446e`. I reviewed the service, the schema and migration 0011, the router, the compose wiring, the UI, and M2.3's tools and ports, against both task files, CLAUDE.md and HANDOVER "Rules that are easy to break".
- `bun run test`, `bun run check` (boundary-lint clean) and `bun run build` all pass. A grep for `drizzle` in `apps/web/dist/client` finds nothing.
- `inbox.test.ts` covers all five checks in the task. The streak test asserts `reason: "streak"`, so the depth limit cannot pass it by accident. It also covers the budget, refused wakes, workspace isolation and read-only keys.
- The rules hold. The service is a factory and never reads `env`. The post and the `last_post_at` update are written through `atomic`. Both tables have `workspace_id NOT NULL` with no default. There is one `exports` entry (`@repo/services/inbox`) and no barrel file. The service is built in `composeWith`. The UI uses only `@repo/db/shared`. No binding was added and `context.ts` did not change.
- The subject stays server-side. `deliver` loads the run row for the workspace and session, and wakes with a run principal built from that row. `post` with a run principal loads the run, and run tokens resolve only while the run is `running` (`run-tokens.ts:175`). `deriveSubject` takes `onBehalfOfUserId` from the parent run and never from text. `completeRun` marks the run done before `deliver` (`runs.ts:776-796`), so an inbox chain is not refused as a busy ancestor.
- Browser check of the poll path, on `vite dev` port 3471 with a fresh local D1, dev login and agent-browser. I created a fake agent "Pelican" and a write API key, then opened a new thread in the browser and posted a message with no mention. With the page left alone, I sent `inbox_post` "@pelican ping from outside the browser" through `/mcp` with the key. That call returned the started run id. Without a reload or any interaction, the page then showed both the outside post and "Echo: @pelican ping from outside the browser" from Pelican. The browser's own post call had returned long before that reply existed, so only the 2 s poll could have shown it. Screenshot: `/home/roboto/devel/harbourmaster-wt/tmp/M6-gate/poll.png`. This also covers M2.3's tool-to-reply path end to end on the dev server.

## Findings

| # | Severity | Finding | Area | Resolution |
|---|----------|---------|------|------------|
| 1 | nit | A woken agent gets only the post's text as input (`packages/services/src/inbox.ts:416`). The thread id and the other posts are not in the input. The agent cannot call `inbox_read` on its own thread unless it guesses the id from `inbox_list`. B, woken by A, never sees the person's earlier posts. The milestone does not ask for thread context, but multi-agent threads will need it. | service | Later task: put the thread id (and perhaps the last few posts, marked untrusted) into the wake input. |
| 2 | nit | A stopped wake (streak, budget, refused) gives the person no sign. `post` returns `runs: []`, and the composer ignores the result (`apps/web/src/components/inbox/post-composer.tsx:41`). The event exists only in the event log. | UI | Show "not woken: reason" under the post, or read `inbox.loop_stopped` into the thread view. |
| 3 | nit | The wake budget counts every inbox run of the agent, including wakes from people (`packages/services/src/inbox.ts:344-369`). A person who mentions one agent 11 times in an hour gets nothing on the 11th, silently (see 2). This matches the plan's wording, which is per agent. | service | Decide whether a person's own wakes count. If not, filter on `actor_kind = 'agent'`. |
| 4 | nit | A failed run, or a run whose `deliver` throws, leaves nothing in the thread (`packages/services/src/runs.ts:789-796`). The `deliver` error surfaces after the run is already saved as done. The M6.1 review already listed this. | service | Already in the M6.1 review's ideas ("run failed" line, validate the reply target at start). |
| 5 | nit | The streak is read once per post, before the loop over mentions (`packages/services/src/inbox.ts:453`). The budget is checked and the run started in two separate steps, so concurrent posts can pass 10 an hour. Already in the M6.1 review. | service | Leave it, or move it into a guarded insert when the real runtime makes it matter. |
| 6 | nit | `readThread` returns the newest 500 posts and does not say when older ones were dropped (`packages/services/src/inbox.ts:261-267`). `inbox_read` passes that on to agents unchanged. | service | Add a `truncated` flag or a cursor when threads get long. |
| 7 | nit | The page polls `listThreads` and `readThread` (up to 500 posts) every 2 s, even in a hidden tab. It does not skip a tick while a load is still in flight, and an older response can land after a newer one (`apps/web/src/components/inbox/use-polled-query.ts:36-38`). The staleness point is in the M6.1 review already. | UI | Pause when `document.hidden`, skip a tick while one is in flight, and later fetch only posts after the last id. |
| 8 | nit | The `inbox_post` description ends "Use inbox_read first to see what it answers." It means "afterwards" (`packages/mcp/src/tools/inbox.ts:68`). | MCP | Reword it to "Call inbox_read afterwards to see the reply." |
| 9 | nit | `inbox_post` cannot start a thread, so an agent or MCP client can only post into threads a person made, and the M2.3 smoke needs a thread made in the UI (`scripts/smoke-mcp.ts:136`). The milestone does not ask for it, and the M2.3 log records it. | MCP | Add `inbox_create_thread` if agents should open threads. |
| 10 | nit | The inbox components import `errorMessage` from `components/triggers/format` (`apps/web/src/components/inbox/new-thread-form.tsx:8`, also `post-composer.tsx`, `use-polled-query.ts`). That couples the inbox to another feature's folder. Already in the M6.1 review. | UI | Move `errorMessage` into a shared place. |

Must-fix: 0. Nits: 10.
