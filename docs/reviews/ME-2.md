## Verdict

Not clean. Two must-fix findings remain. Each is a path that can carry one person's private notes to other people.

Round 1 is resolved. ME.14 put one rule in `library/private-notes.ts`. The prompt calls it, and so do the library (`resolveMember`, which the tools, daemon routes and VM sync go through), the audience and `visibleSessions`, which guards `search_history`, `read_session` and the session list. A run in a team room, Q&A, Slack channel, artifact, mail, A2A, routine or trigger session gets no private file, even when one person started it. A Slack DM gets its notes back. A member cannot post into another person's `ui` or private session: the chat path finds a session by actor and external key, and a sub-thread reply checks `visibleSessions` first.

ME.15 keeps `memory/private/` out of the VM and daemon working copies in both directions. It purges any leftover private folder before a run starts, and a failed purge stops the run. ME.16 and ME.19 count any `network.request`, `browser.action`, web tool, shell or unseen-network tool, blob-stored tool call and answered connector call. When such an event arrives late, notes already applied go back to held. ME.17 and ME.18 limit shared-note changes to owners and admins, and decisions to owners, backups and admins. Private held notes and private dream questions still go only to their person.

The other merges keep the rule. The team dream reads only shared member files and room posts, and room runs no longer carry private notes. The agent dream groups evidence per person and gives a note built from one person's evidence that person's private file. It drops a note that mixes two people's evidence.

The two gaps that remain sit at the edges of the rule. A run that may read a person's private notes can still write shared notes. And a daemon that was never upgraded still gets the private file from the server.

## Task-ready scope and check

### MF-1 A run that sees a person's private notes writes its notes to that person's file

Scope. Make the write side use the read rule. In `scopeOf` in `packages/services/src/memory/provenance.ts`, a run's note takes `privateNotesUserOf(run, session)` from `library/private-notes.ts` as its `userScope`, instead of keying on `session.private`. A run in A's own `ui` or private session then writes to `private/<A>.md`, and every other run still writes shared notes. Hand-offs and subagents follow through their own sessions, which `runs.ts` already makes private to the parent's actor. A person's own "remember from chat" stays as it is, because that is the person's choice. Update `docs/v4/memory-format.md` to state one rule for reading and writing.

The cost is that the agent's shared memory stops learning from one-to-one app chats. Those notes go to the person's file, which matches what the agent dream already does with `ui` evidence. The controller can choose one of two other ways instead. One drops `origin === "ui"` from the rule, so only private sessions see private notes and app chats lose them. The other holds such shared notes for the person to approve. It must not hold them for the owner, because the owner would then see the private text.

Check. Service tests: a `remember` from a run in A's non-private `ui` session lands in `private/<A>.md` with `userScope` A. B, the owner and an admin do not see it on Knows, in `memory.changes` or on the rail. A `remember` from a team room, Slack channel, artifact or Q&A run that A started still lands shared. A `remember` from A's Slack DM still lands private. A hand-off from A's `ui` session writes to A's file. Update the `service-notes.test.ts` cases that pin `RUN.ui` to `userScope: null`. `bun run check && bun run test && bun run build` pass.

### MF-2 The server never hands a private memory file to a working copy

Scope. In `apps/web/src/server/routes/run-library.ts`, make the handlers that `registerLibraryRoutes` mounts refuse `agents/*/memory/private/**` on list, stat and read. Both prefixes, `/api/runs/:id/library` and `/api/session/library`, share them. List leaves those entries out, and stat and read answer not found. No working copy needs the file, because every run gets its private notes from its prompt. Old daemons then cannot receive it, whatever their version. Leave the prompt's reader, which reads through the library service, and the platform MCP library tools as they are, since neither writes to a shared disk. Change ME.15's Dom step so upgrading machines is only about cleaning copies that already hold a file.

Check. Route tests: a run that passes the private-notes rule for A gets no `private/<A>.md` when it lists `memory/`, and gets not found on stat and read of that path, on both prefixes. The same run still has A's notes in its launch context. The VM sync and daemon tests still pass. `bun run check && bun run test && bun run build` pass, and `cargo test` in `apps/agentum`.
