## What the scope and check asked for, and where it is

- Session-scoped versus run-scoped tokens is decided and written down (docs/reviews/tasks/M8.1.md, "Decision"). `hm_ses_` tokens live in a vault per session. `verifySessionToken` (packages/services/src/run-tokens.ts:239) resolves a token to the session's `current_run_id` only while that run is `running`, `claimed_by='managed'` and its lease is live. The proxy (routes/proxy.ts:480) and the principal resolver (workspaces.ts:261,301) accept the new kind.
- The gateway, events, config and workspace-keys files are ported with their tests (gateway.test.ts, events.test.ts, keys.test.ts). Agentum has no config.test.ts, and `modelFor` is tested in gateway.test.ts:734.
- Schema: four tables, migration 0001 plus meta, and every table has `workspace_id NOT NULL`.
- `ManagedRuntime.dispatch` (managed/runtime.ts) and the `ManagedPoller` DO, which arms one alarm per run. `MANAGED_POLLER` is in all three places in wrangler.jsonc (:11, :58, :84). Tag `v3` is new, `v1` is untouched, and the migrations stay top level only.
- The agent form has the runtime select, and the managed limits are stated (agent-form.tsx:176-185).
- The key is per workspace, encrypted with SECRETS_KEY and bound to the row, and set in the UI. No app code reads `ANTHROPIC_API_KEY`: the only hit outside tests is a comment in pi-run-models.ts:9.
- Every case in managed.test.ts that the check names is present: dispatch, complete, budget stop (:503), a second-turn run for another person resolving that person's credential (:886), and two concurrent sessions on one agent not sharing a token (:959).
- Layering holds. The routers are thin, the services are built in composeWith, there is one exports subpath per module, multi-row key writes go through `atomic`, and `step`/`rearm`/`interrupt` are reached only from the DO and the tick.

## Findings

No must-fix findings. All findings are nits. The ones marked (carried) were already listed as nits in docs/reviews/tasks/M8.1.md and are still true at this commit.

1. nit: packages/services/src/managed/config.ts:50-57 and apps/web/src/components/agent/agent-form.tsx:138-161. `modelFor` quietly swaps any unknown model id for Sonnet. A managed agent gets a free-text model input with "Use opus, sonnet or haiku". Since C.11, cloud agents get a picker and a clear unknown-model error. This is the strongest must-fix candidate, but I kept it a nit: it is deliberate, tested (gateway.test.ts:749), and documented, and the run still works on a real model rather than failing. The task's "not quietly" wording is about unsupported features, not model choice. (carried, now inconsistent with cloud)
2. nit: packages/services/src/managed/config.ts:15-43 and packages/services/src/cloud/models.ts:7-40. There are two model catalogs with the same three ids, in two shapes, with two alias resolvers. One catalog would serve both, for example in `@repo/db/shared` next to `AGENT_RUNTIMES`.
3. nit: apps/web/src/components/agent/agent-form.tsx:1. A client component imports a value from `@repo/services/cloud/models`. CLAUDE.md says what a React component needs comes from `@repo/db/shared`. The bundle grep passes only because that module imports nothing. (C.* side, at the agent-form touchpoint.)
4. nit: apps/web/src/routes/_app/settings.managed-agents.tsx:96-101 and apps/web/src/components/shell/nav/runtime.ts:15-20. The page and the nav call this the Managed Agents key. Since C.6 the same key also drives cloud agents (apps/web/src/server/pi-run.ts:124). The cloud description in agent-form.tsx:186-195 never says that cloud agents need it.
5. nit: apps/web/src/routes/_app/settings.managed-agents.tsx:127-136 and packages/services/src/managed/keys.ts:154-159. Remove and rotate have no confirm step and no warning. `forgetAnthropicIds` makes every running managed run fail on its next poll ("The Anthropic session is gone", service.ts:742), and a removed key also stops cloud runs.
6. nit: packages/services/src/managed/service.ts:356. `dropVault` logs the raw SDK error object. `stopSession` (:424) and `step` (:871) use `describeError` so that nothing the API echoes reaches the logs. I found no key in Anthropic SDK error objects, but the logging is inconsistent with that rule.
7. nit: packages/services/src/managed/service.ts:184-233 and packages/services/src/runs.ts:600-636. The "older run of the session still waiting" `notExists` guard is copied in both places. Managed allows one running run per session, while `claimRun` (C.*) allows one per agent (runs.ts:605). Managed needs the per-session rule because the check requires concurrent sessions per agent. Still, the shared order guard could be one helper, and the asymmetry deserves a comment.
8. nit: packages/services/src/runs.ts:1264-1297 and packages/services/src/managed/service.ts:833-852. When the reaper interrupts a managed run (for example after a ManagedPoller outage over 90 s), nothing tells Anthropic to stop and nothing closes `managed_sessions`. `prepare` returns DONE without calling `abandon`. The token is safe, because the run is no longer `running`, but the Anthropic session keeps spending until it idles. Cloud runs got outage tolerance in C.4. Managed runs did not.
9. nit: packages/services/src/managed/service.ts:738-741. The missing-key or missing-row path in `poll` fails the run without `offerNext`. The next queued run in that session waits for the 60 s sweep.
10. nit: packages/services/src/managed/service.ts:715-717. On the run-too-long path, `gateway.interrupt` is not guarded. If it throws, the run goes through the failure counter (up to 5 more steps) instead of ending. `stopSession` already does the guarded version.
11. nit: packages/services/src/managed/service.ts:644 and :717. `endFailed` and the run-too-long path call `closeSession` without `onlyRun`. A late step of a cancelled run could close a session that the next run has just taken over. (carried)
12. nit: packages/services/src/managed/service.ts:593-614. `launch` is not idempotent. If `sendMessage` or `createSession` succeeds and the `sent_at` write then fails, the retry sends again, into a new session. (carried)
13. nit: packages/services/src/managed/service.ts:893-905. A cancel that lands during launch, before `sent_at`, interrupts nothing. The session created next runs the cancelled input until it idles. (carried)
14. nit: packages/services/src/managed/keys.ts:189-212 and service.ts:311-321, :512-519. A launch in flight during a key change can write `managed_agents` or `managed_sessions` rows under the old key after the atomic delete. (carried)
15. nit: packages/services/src/managed/service.ts:805-817. If `keys.resolve` throws inside `abandon`, the row is closed but the vault is not deleted and Anthropic is not told to stop. (carried)
16. nit: packages/services/src/managed/service.ts:352-358, :385-387. Nothing sweeps vaults of closed sessions whose cleanup failed, or of open sessions that never get another run. (carried)
17. nit: packages/services/src/managed/service.ts:912-919. `rearm` reads at most 100 running runs, in no order. (carried)
18. nit: packages/services/src/managed/service.ts:855, :893, :912. `step`, `interrupt` and `rearm` take no principal. CLAUDE.md wants workspace reads behind a principal and `authorize()`. They are only reachable from the DO and the tick. (carried)
19. nit: packages/services/src/managed/gateway.ts:392-394. When the last event has a null `processed_at`, `pollEvents` falls back to listing the whole session history. (carried)
20. nit: packages/services/src/managed/keys.ts:169-229. Setting or removing the key appends no audit event. Only `set_by` is stored. (carried)
21. nit: packages/services/src/managed/run-events.ts:57-68, :74-98. `finalReply` reads the stored payload, not the blob, so an event over 64 KB loses its text in the final reply. (carried)
22. nit: packages/services/src/managed/events.ts:150, :117-141. `isSessionReusable` is unused, and `reduceEvents` still builds `agentText` and `customToolCalls`, which nothing reads. (carried)
23. nit: packages/services/src/managed/gateway.ts:410, :440. The `mcpServers.length > 0` guards can never be false, because the platform server is always listed. (carried)
24. nit: apps/web/src/server/routes/mcp.ts:2. The header comment names only `hm_run_`. The route now also takes `hm_ses_` through the principal resolver.

The staging check covers cloud agents only, and HANDOVER's "Things nobody has verified yet" does not list a managed run on a deployed Worker (ManagedPoller alarm plus vault credentials against the staging URL).
