# V5 milestone gate, review 1

Commit cc40925 on main. Range v5-start..cc40925. I reviewed only the V5 merges: V5.2 54fa372, V5.1 a66b0cb, V5.6 80e2aad, V5.8 3bbfa8f, V5.3 7605a93, V5.4 0d7831e, V5.5 4b433b0, V5.7 dfcb858, V5.9 f5c6cbe, V5.11 fb600e2 and V5.10 8b17c1e. ## Verdict

Not clean. There are 4 must-fix findings and 27 nits.

The CI steps pass in the review worktree. `bun install --frozen-lockfile`, `bun run check`, `bun run test` and `bun run build` all exit 0 (logs in this folder). The services suite ran 2506 tests, web 2663, mailbox 127 and mcp 294. `apps/web/dist/client` contains no `drizzle`.

Wrangler bindings are in all three places. `MAILBOX` DO, `send_email` `EMAIL` and the three `MAIL_*` vars sit at the top level, in `env.staging` and in `env.staging.previews`. Previews turn mail off with an empty `MAIL_DOMAIN`, and migration `v6` sits at the top level only. Migration 0019 is the only V5 schema change. No later migration touches the mail tables, and no V4, V6 or V7 commit breaks a V5 rule.

The bound-parameter findings rest on Cloudflare's statement that DO SQLite limits match D1's, which allows 100 bound parameters per query. `bun:sqlite` allows 32,766, so the tests cannot catch them.

I dismissed one candidate. A sub-review said "Always allow" covers only the first outside recipient. It covers them all: `allowOtherRecipients` (`packages/services/src/mail/outbound.ts:415-443`) writes the other rules, and `outbound.test.ts:271` tests it.

The nits left in `docs/reviews/tasks/V5.*.md` still stand. I don't repeat them here.

## Tasks

### V5.13 Keep mailbox Durable Object queries under 100 bound parameters

Scope
- `packages/mailbox/src/store.ts`: insert attachments in chunks in `insertInbound` and `createEmail`, so that no statement binds more than 100 parameters. Chunk `findThreadByIds` (or keep only the newest 49 ids, documenting the choice). Replace `attachmentsOf(emailIds)` with a join on the thread, or chunk it.
- Put the limit in one constant (for example `DO_MAX_BOUND_PARAMS = 100`) beside the store. Pass a smaller chunk size into tests.
- Optional, same files: cap the length of `safeFilename` (`inbound.ts:75-85`) so the R2 key stays under 1,024 bytes, and replace DEL.

Check
- `packages/mailbox/src/store.test.ts` adds a bound-parameter guard. A test drizzle wrapper (or `bun:sqlite` with `SQLITE_LIMIT_VARIABLE_NUMBER` lowered, if available) throws above 100 parameters. Under that guard, mail with 20 attachments stores, a `References` header with 120 ids resolves its thread, and a thread with 150 messages reads back with its attachments.
- `bun run check && bun run test && bun run build` pass.

### V5.14 Provision a pending or missing mailbox from the profile

Scope
- `apps/web/src/components/agent/profile/mail-status.tsx`: show the Retry button for `provisioning` as well as `failed`. For "provisioning pending" a label such as "Try again" fits. It calls `mailbox.provision`.
- `profile-header.tsx` (and the Channels Email chip): when `mailbox` is null, the agent is active and it has an `email_local`, offer "Set up mail", which calls `mailbox.provision`. A draft agent shows nothing new.
- No services change. `provision` already handles both cases.

Check
- `profile-logic.test.ts` or `mail-logic.test.ts` covers when the action shows: provisioning yes, failed yes, active no, null mailbox with address on an active agent yes, and a draft no.
- Browser check (dispatcher, local dev): an agent with no mailbox row gets one from the button. A `provisioning` row moves to `active` against a fake or configured routing port.
- `bun run check && bun run test && bun run build` pass, and there is no `drizzle` in `dist/client`.

### V5.15 A reply to an agent-started thread continues the sending session

Scope
- `packages/services/src/mail/inbound.ts` `startInbound`: when the thread already has a `session_id` and that session is not the thread's `mail:<mailboxId>:<threadId>` session, start the reply's run in that existing session. Don't open a new mail session, and don't overwrite `mail_threads.session_id`.
- `packages/services/src/runs.ts` / `runs/types.ts`: add a trusted `StartRunOptions` field (for example `sessionId`), not part of `startRunInputSchema`. It continues a known session of the same agent and workspace and skips the ui and private actor check, which a mail trigger cannot pass.
- Keep `requestId: mail:<externalMessageId>` for idempotency.

Check
- `inbound.test.ts`: a run in a `ui` session sends mail to an outside address (allowed), and an inbound reply on that thread starts a run in the same session. `threadForTask` for the first run still returns the thread. A thread first started by inbound mail still continues its mail session, and a redelivery still starts one run.
- `bun run check && bun run test && bun run build` pass.

### V5.16 Mail between a workspace's own agents is not lost

Scope
- `packages/services/src/mail/inbound.ts` `receive`: mail from the same workspace's agent address is stored (`storeInbound`), indexed (`mail_threads`, `mail_messages`, `mail.received`) and shown, but starts no run. This keeps the loop guard against agent ping-pong. `Auto-Submitted` and list mail stay dropped.
- If the controller or Dom wants inside agent mail to start runs, that is a separate decision. Note it in the task log.

Check
- `inbound.test.ts`: mail from another agent of the same workspace is stored and listed in `threads`, and no run starts. Auto-replies and list mail are still ignored. Mail from an outside address still starts a run.
- `bun run check && bun run test && bun run build` pass.
