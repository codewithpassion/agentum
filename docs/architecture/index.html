One-paragraph summary

Harbourmaster stays one Cloudflare Worker (Hono, TanStack Start, tRPC, D1, Clerk) plus one Durable Object class and one new app. The Worker owns agents, sessions, runs, connectors, credentials, triggers, the Slack gateway, the inbox, the append-only event log, and an MCP server that Claude and the agents themselves call. Agents do not run in the Worker in v1. They run on machines Dom controls, through a Bun daemon (apps/daemon) that enrols once, keeps an outbound WebSocket to a MachineRelay Durable Object, claims runs, and executes each run as a Claude Code session through @anthropic-ai/claude-agent-sdk. The same daemon on a laptop against wrangler dev is the local mode the brief asks for. Every runtime sits behind one RuntimeAdapter interface, so Claude Managed Agents (Agentum's gateway code) can arrive as a second adapter without touching the trigger, session or credential code. It is not in v1 unless Dom picks "SMB first" in open question 2. Credentials never leave the Worker. Each run gets one token for its whole life, handed to Claude Code over the SDK's control channel (never on disk, never on the command line), and a per-connector proxy URL. The Worker injects the right credential (the person the run is on behalf of, or the agent's own) on the way out. That one proxy covers all three credential cases in the brief, logs every connector call, and works for any runtime that can speak MCP over HTTP.

System diagram

Module map

The repo layers by tier (route, tRPC router, service, query functions), so each capability is a name that appears once per tier. The public API of a capability is its exports subpath in packages/services, never a barrel. Tables move from the single schema.ts into packages/db/src/schema/<module>.ts, with drizzle.config.ts listing the files (Agentum does the same). The browser imports only @repo/db/shared. Pure protocol code and state machines go in packages/protocol so the daemon and the Worker parse the same frames. Durable Object classes live in apps/web/src/server/durable/ and hold transport state only. Three rows below list two subpaths. That is one module with two consumer sets (authz is called by every service, credentials by the proxy and the claim route, api-keys and oauth-clients by the settings UI and the MCP route), and still no barrel: each subpath is one file with its own code.

Core seams

Six interfaces. They are written in M0 as code with tests, because every lane builds against them. What freezes at M0 is the part that crosses a process or network boundary: the foundation tables, the machine protocol, the run token and proxy URL, and the platform MCP tool names. The rest may still change until the M1 gate, with changes announced. Type sketches use the repo's conventions: ISO strings, string ids, plain JSON. Every service is a factory that takes a Database, the atomic write port, and narrow injected dependencies, never env.

1. Trigger to run: startRun()

Every way to make an agent do something goes through one service function. UI chat, Slack mention, inbox mention, routine tick, HTTP trigger and the MCP send_message tool all call it. It finds or creates the session, inserts a queued run, appends run.queued to events, and hands the run to the agent's RuntimeAdapter. 

// @repo/services/runs
createRunsService({ db, atomic, adapters, gateways, blobs, clock, devFakeRuntime }): RunsService
interface StartRunInput {
  agentId: string;
  // Session identity. Same key, same session, so a Slack thread or an inbox
  // thread keeps its context. "ui" keys are session ids the UI already holds.
  session: { origin: "ui" | "slack" | "inbox" | "routine" | "trigger" | "mcp"; externalKey?: string };
  input: { text: string; fileIds?: string[] };   // fileIds must belong to the principal's user and workspace
  reply?: ReplyTarget;                            // where the answer goes when the run finishes
  requestId?: string;                             // idempotency; unique index on (workspace_id, request_id)
}
type ReplyTarget =
  | { kind: "slack"; teamId: string; channel: string; threadTs: string }
  | { kind: "inbox"; threadId: string }
  | { kind: "none" };
runs.startRun(principal, input): Promise<{ runId: string; sessionId: string; status: "queued" }>
runs.waitForRun(runId, waitMs): Promise<RunSummary>   // long-poll helper for MCP and HTTP triggers

// There is no actor input. startRun derives everything from the authenticated principal:
//   principal.kind "user"    -> actor = that user;      on_behalf_of_user_id = that user
//   principal.kind "run"     -> actor = parent agent;   on_behalf_of_user_id = parent run's value (inherited, never overridable)
//                               parent_run_id = parent run; depth = parent depth + 1, refused above 3
//   principal.kind "trigger" -> actor = that trigger;   on_behalf_of_user_id = null
//   principal.kind "system"  -> only the tick calls this, for routines: actor = the routine's trigger; null
// A duplicate requestId is caught as the unique violation, the existing run is read back and returned.
// Credential resolution (seam 4) reads on_behalf_of_user_id, nothing else.

The on_behalf_of_user_id chain is what stops a person without a credential from getting one by asking agent A to ask agent B. A run descended from a human request stays that human's request however many agents it passes through. Only routines and HTTP triggers, and runs descended from them, run as the agent itself. Because the subject comes from the principal and the principal comes from the token, no caller can supply a different one. A Slack route builds a user principal with via: "slack" only after the signature check and the identity link, so a Slack message is a user's request or nothing.

A second message to a session while a run is active queues a second run. One run per agent runs at a time, enforced by the claim's conditional write (seam 3), not by the daemon. A send_message from a run that would wait on a busy ancestor (A asks B, B asks A) is refused instead of waiting for a timeout.

2. Runtime adapter

// @repo/services/runs
interface RuntimeAdapter {
  kind: "machine" | "managed" | "fake";
  // Fast. Enqueue or offer, never execute inline.
  dispatch(db, run: RunRecord, agent: AgentRecord, deps: AdapterDeps): Promise<void>;
  cancel(db, run: RunRecord): Promise<void>;
}
// Shared by every runtime. The daemon POSTs these; the managed poller calls them in-process.
ingestRunEvents(db, principal: RunPrincipal, events: RunEventInput[]): Promise<{ lastSeq: number }>
completeRun(db, principal: RunPrincipal, result: { status: "done" | "failed"; text?: string; fileIds?: string[]; error?: string; usage?: Usage; runtimeRef?: string }): Promise<void>
// Both refuse with 409 unless runs.status is "running". That is the fence against a
// late event or completion from an execution whose lease already expired.
// One exception: completeRun({ status: "aborted" }) is accepted from the machine that claimed the
// run, for a "running" run (it becomes "interrupted" with process_ended_at set) and for an
// "interrupted" run (it records process_ended_at). Both are the daemon saying "the local process
// has exited"; a repeat gets 409.

The fake adapter answers with an echo. It is registered only when devFakeRuntime is set, and agents.runtime allows fake so a seed script can create such an agent; that is how the Access and Automation lanes run their checks before a machine exists. A run whose lease expires becomes interrupted, never re-queued, because a lost heartbeat does not prove the Claude Code process stopped before it sent an email. The daemon, on a 409 from heartbeat or a 1012 close, or when it stops itself, aborts its local process and posts aborted once it has exited. The server accepts it for a running run, which becomes interrupted at once, and for an interrupted one. The UI offers Retry (a new run) only after that, or after ten minutes, so two processes never work on the same files on purpose.

3. Machine protocol (daemon and relay)

Zod schemas in packages/protocol, parsed on both sides, strict objects, capability flags in hello so a newer Worker never sends a frame an old daemon cannot read (Ariadne's rule). WebSocket carries presence and offers only. Run data goes over HTTP with the machine credential, which keeps the relay small and lets curl reproduce every step. Queued runs in D1 are the source of truth for dispatch: on hello the relay offers every queued or offered run for the machine's agents, oldest first, and a tick job re-offers anything queued or offered for more than 60 s. Offers are idempotent because the claim is the conditional write. Lease is 90 s, heartbeat every 20 s. 

// daemon -> relay (WS)
{ type: "hello", daemonVersion, capabilities: { agentSdk: "0.2.119", container: false }, agents: string[] }
{ type: "ping", at }
// relay -> daemon (WS)
{ type: "hello_ack", machineId, serverTime }
{ type: "offer", runId, agentId }       // one per queued run for an agent on this machine
{ type: "cancel", runId }
// close codes: 4401 credential rejected (stop), 1012 replaced by a newer connection
// daemon -> worker (HTTP, bearer hm_mach_...)
POST /api/machines/runs/:runId/claim     -> { run, agent, session, runToken, mcpServers, inputFileIds, instructions }
   // one conditional write, all of: runs.status IN ('queued','offered')
   //   AND agents.machine_id = this machine
   //   AND NOT EXISTS (another run for this agent with status 'running')
   //   AND NOT EXISTS (an older queued run for this session)
   //   AND runs.pending_files IS NULL
   // The run token is minted here, once, and nowhere else.
POST /api/machines/runs/:runId/events    -> { events: RunEventInput[] }      // batched every 500 ms, 409 unless running
POST /api/machines/runs/:runId/heartbeat -> {}                               // extends lease_until by 90 s, 409 unless running
POST /api/machines/runs/:runId/complete  -> { status, text, fileIds, usage, runtimeRef }   // or { status: "aborted" } for a running or interrupted run, from the claiming machine

The claim answer carries everything the daemon needs for the run, including the generated mcpServers map (seam 4), so the daemon holds no credentials and no connector list. The run token lives as long as the run, with a hard cap of 12 hours. Its validity is checked on every use against the current row: runs.status = 'running' AND lease_until > now. Nothing rotates, so Claude Code holds one token from first tool call to last. How it reaches Claude Code matters: the SDK puts mcpServers given to query() on the claude command line (--mcp-config), where any process on the box can read it from ps. The daemon therefore starts query() in streaming-input mode with no HTTP servers, calls query.setMcpServers( { ...}), which travels over the SDK's control channel on stdin, and only then sends the first user message. strictMcpConfig: true keeps settings-file servers out. The claim is bound to the machine and to the agent's execution slot: a daemon can only claim runs for agents assigned to its own machine row, and only one run per agent can be running.

4. Credential resolution and the connector proxy

Every assigned connector becomes an entry in the run's mcpServers map that points back at the Worker. The proxy resolves the credential per call, so a token refresh or a re-auth in the middle of a long run just works. 

// What the daemon passes to query.setMcpServers() for a run, in memory only (never query()'s mcpServers option, which goes on argv)
"notion": { "type": "http", "url": "https://hm.example/api/proxy/con_123", "headers": { "Authorization": "Bearer hm_run_..." } }
"harbourmaster": { "type": "http", "url": "https://hm.example/mcp", "headers": { "Authorization": "Bearer hm_run_..." } }

// @repo/services/credentials
createCredentialsService({ db, atomic, secretsKey, clock, fetch }): CredentialsService
credentials.resolve({ connectorId, agentId, onBehalfOfUserId }): Promise<
  | { ok: true; credential: DecryptedCredential; ownerKind: "user" | "agent"; version: number }
  | { ok: false; reason: "not_assigned" }                                   // the proxy answers 403
  | { ok: false; reason: "needs_auth"; ownerKind: "user" | "agent"; ownerId: string; connectPath: string }>
// connectPath is a Harbourmaster page, /connect/:connectorId?as=user or ?as=agent:<id>, never a provider URL.

The rule, per agent_connectors.credential_mode, applied to the run's on_behalf_of_user_id (seam 1), never to the direct actor:

  • user_or_agent (default). A run on behalf of a person uses that person's credential for the connector. A run on behalf of nobody (routine, HTTP trigger, and runs descended from them) uses the agent's credential. A person without a credential gets needs_auth with a Connect link. It never falls back to the agent's credential for a person, however many agents the request passed through.
  • agent. Always the agent's credential. For shared systems where the agent should have its own identity.
  • user. Only a person's credential. A routine run with this mode fails with connector.needs_auth, which is the right answer.

Credential ownership is independent of auth kind. A header credential can be pasted as yourself or as the agent, the same as an OAuth grant, so a personal API token still gives "it looks like Dom".

The proxy route, in order: verify the run token (stateless HMAC with run id, agent id, workspace id and a 12 h cap; then runs.status = 'running' AND lease_until > now, which is the real fence); load the agent_connectors row for the run's agent and the requested connector, and answer 403 when there is none (a URL missing from mcpServers is not authorisation); resolve the credential by the rule above, treating revoked as needs_auth; forward the MCP request with the real header.

Refresh. Most refreshes never race, because the proxy refreshes ahead of time when expires_at is within two minutes. When a refresh is needed, the caller first takes a lease: UPDATE credentials SET refreshing_until = now + 30 s WHERE id = ? AND version = ? AND (refreshing_until IS NULL OR refreshing_until < now). Only the row's winner calls the provider's token endpoint, once. It then writes the new secret with WHERE id = ? AND version = ? AND refreshing_until = mine AND status != 'revoked', bumping version and clearing the lease. Losers poll version for up to five seconds and use the newer secret; if nothing changed they answer the model with a retry error, not needs_auth. needs_auth is written only by the lease holder, only when the provider refused, and only through the same fenced write. A revocation or a re-authorisation bumps version and clears refreshing_until, so a stale lease holder's write fails its version check and nothing it does survives. That is what "exactly one refresh" means here: one token-endpoint call per rotation, which the stub in M3.3 counts.

The error text returned to the model carries the Connect path. Append one connector.call event per request, with the tool name and no payload. Cap forwarded responses at a wall-clock limit (open question 9), because a tool call held open through the Worker is the one path nobody has measured.

Connecting is always a signed-in act. /connect/:connectorId?as=user requires a Clerk session, creates the oauth_states row with initiator_user_id at click time, and sends the browser to the provider. The callback refuses unless the session user is the initiator, and return_to must be a same-origin path. ?as=agent:<id> is offered only on the agent's page. So a Connect path posted in a Slack thread or an inbox thread cannot bind the clicker's account to someone else's credential row, and the Slack gateway sends it as an ephemeral message to the run's on_behalf_of user anyway.

}
// isOrgMember(userId, clerkOrgId) is a Clerk Backend API call with a 60 s cache, injected
// by apps/web. It runs for api_key and oauth principals on every request, because a
// bearer token has no session and a person who left the org must lose access that minute.
// allowedOrgIds: an org not on the list never gets a workspace. Sign-up on the public domain
// is open by default in Clerk, and v1 is Dom's; Clerk's restricted sign-up mode is turned on too.
// An oauth principal's workspace comes from its approved oauth_clients row, never from input.
// @repo/services/authz
can(principal: Principal, action: string, resource: { workspaceId: string; kind: string; id?: string }): boolean
// v1 body: principal.workspaceId === resource.workspaceId. Every service method calls it.

Token prefixes: hm_key_ API key (hashed in D1, flightdex-v2 pattern), hm_mach_ machine credential (hashed, Ariadne), hm_trg_ trigger token (hashed), hm_run_ run token (stateless HMAC with the Worker secret, The Brain's bdev_ pattern, minted once at claim, 12 h cap, valid while the run is running and its lease is live), hm_enr_ enrol code (single use, 15 minutes). Clerk sessions and Clerk OAuth access tokens resolve to kind: "user". Routes that take a cookie session and mutate (file upload, OAuth start, Slack install) run behind csrf() like tRPC does today; routes meant for bearer tokens ignore cookies.

Data model

Twenty tables (a twenty-first, managed_agents, arrives with the managed runtime), all except workspaces with workspace_id TEXT NOT NULL and no default, so a forgotten scope fails at insert. Nine of them are the foundation and exist at M0: workspaces, identity_links, agents, machines, machine_enroll_tokens, sessions, runs, events, files. Each later lane adds its own tables in its first PR. Ids are ULIDs as text. Timestamps are ISO text. JSON columns are text with a zod schema in the owning module. Encrypted columns use AES-GCM with an AAD of { workspaceId, table, rowId, field }, the same binding for every secret in the system. After M0, schema changes go through one serial queue, one small PR each; lanes rebase and regenerate, and never merge two migrations/meta journals.

Multi-statement writes go through one port, atomic, exported by @repo/db. The repo's Database type covers D1 and bun:sqlite, but drizzle 0.44.7 has batch only on the D1 driver and interactive transactions only on the SQLite drivers, and D1 has no interactive transactions at all. So atomic(statements) runs db.batch on D1 and a db.transaction on bun:sqlite; the app passes the D1 one, tests pass the SQLite one, and services take { db, atomic }. Every "in one atomic write" on these pages means this call.

Auth and the three credential cases

People sign in with Clerk. The Clerk session's orgId picks the workspace; a user with no org is sent to Clerk's create-organization screen. Because the Worker sits on a public domain and Clerk sign-up is open by default, two gates sit in front of that: Clerk's restricted sign-up mode on the instance, and an injected allowedOrgIds list in the principal resolver, so an org not on the list never gets a workspace. workspaceProcedure replaces protectedProcedure and narrows ctx.principal to a user in a workspace. Machine callers send a bearer token and go through the principal resolver, which looks at the prefix.

Claude.ai and Claude Code connect to /mcp in one of two ways. An API key minted in Settings (hm_key_) for scripts and Claude Code. Clerk OAuth for Claude.ai: Harbourmaster publishes protected-resource metadata, Clerk is the authorization server, the Worker verifies the access token with idPOAuthAccessToken.verify, and a per-workspace approval gate refuses clients nobody approved, because Clerk tokens carry no audience (flightdex-v2 cycle 9 finding). Both end as Principal { kind: "user" }, so the MCP tools and the tRPC routers call the same services.

The three cases from the brief, walked through the design:

  1. Linked to Dom, so it looks like Dom in the external system. Dom opens Connectors, picks Notion, clicks Connect. The OAuth flow stores a credentials row with owner_kind = user, owner_id = Dom. Dom messages the agent from the UI or from Claude.ai; the run's actor is Dom; the proxy sends Dom's token.
  2. A colleague tasks the agent. The colleague mentions the agent in Slack. The Slack route maps the Slack user to a Clerk user through identity_links (email match on first contact, and only when that Clerk user is a member of the workspace's org and the event's team_id matches the app row). The run is on behalf of that user. If they have no Notion credential, the Slack gateway sends them an ephemeral message with the Connect path (a signed-in Harbourmaster page, so nobody else can bind their account to it), and the run records connector.needs_auth. If the colleague instead asks the agent to "ask Bruce to search Notion", Bruce's run inherits on_behalf_of_user_id from the colleague's run and hits the same needs_auth. Nothing runs as Dom, or as the agent, by accident.
  3. The agent runs on a routine or an event. The actor is the trigger and on_behalf_of_user_id is null. The proxy picks the owner_kind = agent credential, which someone connected once from the agent's Connectors tab ("Connect as this agent"). Missing credential, same needs_auth path, delivered to the reply target or shown on the agent page.

Secrets at rest: AES-GCM through Web Crypto with a non-extractable key imported from SECRETS_KEY and an AAD that binds the ciphertext to its row (flightdex-v2 secrets.ts, copied). Inbound tokens (API keys, machine credentials, trigger tokens) are hashed, never encrypted. Connector secrets never reach the daemon, Claude Code, Slack or the browser. The daemon's env for Claude Code is filtered (bruce-next buildAgentEnv), and outbound text from the daemon passes a masker that redacts the run token and the machine credential (Ariadne masker.ts).

The machine. Claude Code runs with bypassPermissions, which confines nothing to a directory, so the boundary is drawn with Unix users. The daemon runs as the user who installed it and owns ~/.harbourmaster/config.json (mode 600) with the machine credential. It spawns every Claude Code process as a separate user, hm-agent, through sudo -u hm-agent; install-service writes a sudoers drop-in that allows that one command and creates the user. Work directories belong to hm-agent. A run can therefore read every agent's files on the box and the machine's Claude login, but not the machine credential, so it cannot claim or heartbeat other runs and cannot obtain another person's run token. Run tokens exist once, in the daemon's memory and in the Claude Code process that received it over stdin, never on disk and never on the command line. Connector secrets are never on the box. strictMcpConfig and the per-run reset of work/.claude/ stop one run from planting a hook or an MCP server that fires in a later run on behalf of someone else. What a prompt-injected run can still do: act as any agent on the same machine in the same workspace with that agent's own credentials, and read their files. That is the same trust the brief gives Bruce today. One Unix user per agent is the next step and sits in Deferred.

A machine where the daemon cannot get a second user (no sudo, no root) is enrolled as single_user, and the rule changes: runs on behalf of anyone other than the person who enrolled it resolve only agent credentials. The agent page and the Slack reply both say so, so the brief's case 2 is never silently downgraded.

Decisions and rejected alternatives

Decision Why Rejected
The walking-skeleton runtime is a machine daemon running Claude Code through the Agent SDK. It is Dom's own use case (Bruce), it has the most copyable code (Ariadne relay and client, bruce-next agent core), and the same binary on a laptop against wrangler dev is the "run locally straight away" mode. It proves the hardest seam first. A Worker-hosted tool loop first: less reuse, no local-machine story, and it would need an MCP client plus tool execution built from scratch. Managed Agents first: needs a public URL in dev and the beta API's quirks on day one.
Daemon in TypeScript on Bun, not Go. Claude Code and the Agent SDK are Node packages; a Go daemon would still have to spawn them. bun build --compile gives one binary (Ariadne ships this way). Reusing Agentum's Go computer daemon as the runner: it exposes a shell and files to an agent that runs elsewhere, which is the Managed Agents story, not this one. It stays on the shelf for that milestone.
Relay is transport only. Claim, heartbeat and complete are compare-and-set rows in D1. An expired lease interrupts the run and never re-runs it. Durable Objects get evicted and alarms double-fire. trueforge lost a 45 s exec to an instance swap; Ariadne put all job state in D1 and the relay survived it. A lost heartbeat does not prove the process stopped, so an automatic re-run could send the same email twice. Run state in DO storage: simpler code, lost on eviction, untestable locally (workerd never supersedes instances). Re-queue on expiry with attempt ids on every frame: safe for retry-safe work only, and v1 has no way to know which work that is.
Managed Agents is not in v1 by default. The brief lists it, but Dom's own use is the machine runtime, and Managed Agents fix MCP servers at agent registration, so the per-run token design needs extra work there (a re-sync per run or a session-scoped token). "Do not invent the future" says keep the adapter seam and build the second adapter when someone needs it. Open question 2 lets Dom flip this. Build it last in v1 (the first draft of this plan). Build it first for SMBs: needs a tunnel in dev and the beta API's quirks on day one.
Three build lanes, not ten. One to three people will build this. Ten lanes with seven frozen contracts pay the whole coordination cost of parallel work and still collide in server.ts, context.ts and router.ts. Three lanes with pre-split wiring files is the most parallelism the staffing can use. Ten lanes (the first draft).
One run token for the life of the run, delivered over the SDK control channel. Claude Code gets its MCP headers once; nothing updates a running process's transports, so a token that expired with a 90 s lease would fail every tool call after the first lease. Validity is server-side (running and a live lease, 12 h cap), which is the real fence anyway. The SDK's --mcp-config puts query()'s mcpServers on argv, readable by every process on the box; setMcpServers() goes over stdin. Rotating tokens per heartbeat (the previous draft): breaks mid-run. Passing mcpServers to query(): leaks the token through ps.
One atomic write port in @repo/db, over db.batch on D1 and db.transaction on bun:sqlite. The repo's Database type has no batch, and D1 has no interactive transactions. Without a port, every "atomic" claim on these pages is a wish and the tests would run against a driver that cannot do it. Services typed on the D1 driver: untestable on bun:sqlite. Drizzle's D1 transaction: not interactive on D1.
Claude Code runs as a separate Unix user (hm-agent) from the daemon. With one user, a run can read the machine credential, claim other people's queued runs, and spend their run tokens through the proxy. That is case 2 of the brief broken by a cat and a curl. sudo -u is the spawn prefix the deferred container and per-agent-user work already needed. Keep one user and downgrade colleagues to agent credentials: breaks case 2 for everyone. Offer tokens over the socket: a run can open its own socket with the credential.
Run events travel daemon to Worker over HTTP POST, batched. WebSocket carries hello, ping, offer, cancel. Small relay, every step reproducible with curl, no 32 MiB frame limit to think about, and the HTTP route is an ordinary Hono route with the machine principal. Everything over the socket (Ariadne, trueforge): more frames, a bigger DO, harder to test.
Credentials resolve in the Worker and connectors are reached through a proxy URL with a run token. One code path for all three credential cases and all runtimes. Secrets never leave the Worker. Every connector call lands in the log. Refresh and re-auth happen in one place. The Agent SDK's type: "http" MCP config with headers makes it free on the daemon side (checked in sdk.d.ts 0.2.119). Hand decrypted tokens to the daemon per run: leaks secrets to the machine and to Claude Code's env. Anthropic vaults as the only store (Agentum): managed runtime only. Per-machine .mcp.json edited by hand (bruce-next): no central registry.
One append-only events table, append enforced by SQLite triggers, transcripts as a view over it. The brief wants every action in one log to learn from. One insert path is easier to keep honest than two tables. Triggers make "append-only" a database fact, not a convention (no repo analysed enforces it). Separate session_events and activity_log tables (trueforge, Agentum): two write paths, two shapes. K2 streams plus consumers (control-plane): no local emulation, beta product.
Platform MCP on @modelcontextprotocol/server 2 with createMcpHandler per request, Clerk OAuth plus API keys, client approval gate. Copied from flightdex-v2 where it is deployed and smoke-tested with both lanes, and it is on zod 4 like this repo. No Durable Object, no KV. @cloudflare/workers-oauth-provider (The Brain, Ariadne): a proper authorization server with audiences, but it wraps the whole Worker, needs KV, and pins an agents version that has moved. Worth revisiting if the Clerk-token-without-audience problem bites beyond the gate.
Slack through the Events API over HTTP, one app per agent, created from a generated manifest with pasted tokens. Mentions and DMs only in v1. The manifest API is an optional follow-up. HTTP mode needs no always-on process. Four repos have the paste flow; none has used the manifest API, and the brief's "few clicks" can be measured on the paste flow before deciding whether the API path is worth building. Per-agent apps give @Bruce in Slack. New Slack apps are agent-view only since June 2026, and Ariadne's manifest already has features.agent_view. Channel watch is deferred because each watched message would be a Claude Code run. Socket Mode on the daemon (bruce-next): ties Slack to a machine being up and needs an app-level token no manifest can create. Manifest paste (every repo analysed): works, kept as the fallback, but it is five copy steps. One bot per workspace with channel routing: fewer apps, but the agent is not a Slack user.
Workspace equals Clerk organization from day one, workspace_id NOT NULL everywhere. Agentum rebuilt for tenancy in cycle 8, flightdex-v2 scoped 130 call sites by hand, Ariadne decided it on day one and never looked back. Cheap now, expensive later, and the brief says not to paint into a corner. Single tenant with a later retrofit. Personal workspaces for users without an org (adds a second path through every auth check).
Routines run from the Worker cron minute tick over a triggers table. No DO per workspace to re-arm, no alarm to lose. One atomic write inserts the run (with request_id = trigger:id:occurrence) and advances next_run_at, so a crash on either side loses nothing; an overlapping tick hits the unique index, reads the existing run back and moves on. A crash after the write leaves a queued run that the sweep offers. Cron math copied from bruce-next. Scheduler DO with one alarm per workspace (Agentum, trueforge): precise to the second, more moving parts than a minute tick needs.
Chat UI polls run events in v1. Message-level updates every 1.5 s are fine for a first iteration and need no second DO. WebSocket fan-out per session (Ariadne RunRoom): deferred, listed.
Module layout: slice by name inside the existing tiers, tables in packages/db/src/schema/<module>.ts, protocol in packages/protocol, framework-free MCP tools in packages/mcp. Fits the repo's layering and lint rules. The global "one folder per capability with an index barrel" rule loses to the repo's noBarrelFile and the browser-bundle rule; the intent survives as one exports subpath per capability. Recorded here so it is not re-argued. One workspace package per capability: closer to "copy the folder to move it", but untested with drizzle.config.ts and the Vite plugin, and the schema still has to be one migration history.
No pi-durable, no Trueforge fork, no OpenClaw dependency. pi-durable is Node-only and "changes without notice". Trueforge cost a 35-conflict merge per upstream sync. OpenClaw is a single-operator design with four renames in a year. All three are good to read and bad to depend on. Building on any of them as the runtime.
