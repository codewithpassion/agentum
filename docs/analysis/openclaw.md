# OpenClaw analysis (plus bruce-hermes)

Analysed 16 Oct 2026 from a read-only look at `/home/roboto/devel/openclaw` (package version 2026.2.25, about 4,650 TypeScript files) and `/home/roboto/devel/bruce-hermes`. Nothing was built or run. Everything below comes from reading docs and source, not from running the system.

## 1. Purpose and License

**Purpose.** OpenClaw is a personal AI assistant that runs as one long-lived "Gateway" daemon on the user's own machine. The Gateway owns every messaging connection (WhatsApp, Telegram, Slack, Discord, Signal, iMessage, Teams, Matrix and about 25 more), runs an agent loop per conversation, and exposes a WebSocket API to a CLI, a web UI and companion apps. It is built for one trusted operator, not for SMB teams. Its value to Harbourmaster is the shape of its abstractions, not its code.

**License.** MIT, copyright 2025 Peter Steinberger (`/home/roboto/devel/openclaw/LICENSE`). Copying code is allowed, in whole or in part, including commercially. The only duty is to keep the copyright notice and the MIT permission text in every copy or substantial portion. There is no patent grant and no warranty. Two things to check before any copy:

- The agent runtime is the third-party `@mariozechner/pi-agent-core`, `pi-ai`, `pi-coding-agent` (v0.55.0). Those packages carry their own license, which I did not verify. Copying OpenClaw code that imports them drags that dependency along.
- `vendor/a2ui/` is Apache-2.0 (its own LICENSE file). Skills under `skills/` and `extensions/*` may have their own notices. Check per file.

For Harbourmaster the practical answer is: borrow the patterns, copy small leaf files (see section 4) with the MIT header, and do not copy the core runtime.

## 2. Stack and deployment

- TypeScript (ESM), Node 22+, pnpm workspace (`.`, `ui`, `packages/*`, `extensions/*`). Bun is supported for dev and scripts. Vitest for tests, Oxlint/Oxfmt for lint.
- Protocol types: TypeBox schemas generate JSON Schema, which generates Swift models for the macOS/iOS apps (`docs/concepts/architecture.md`).
- Agent runtime: Pi (`pi-agent-core`) embedded in process, wrapped by `src/agents/pi-embedded-runner/`. Also a CLI-backend mode (`src/agents/cli-runner.ts`, `claude-cli-runner.ts`) that shells out to Claude Code or Codex CLIs.
- Slack via `@slack/bolt`, scheduling via `croner`, browser via `playwright-core`, sockets via `ws`, config validated with `zod` v4.
- Deployment: `npm i -g openclaw`, then `openclaw gateway` as a launchd or systemd service on a Mac, Linux box or VPS. Dockerfile, docker-compose, Podman scripts, `fly.toml` and `render.yaml` exist. Remote access is Tailscale or SSH tunnel to `127.0.0.1:18789`. Tool execution can optionally run in Docker sandboxes (`Dockerfile.sandbox*`).
- State is files, not a database: `~/.openclaw/openclaw.json` (JSON5 config), `~/.openclaw/agents/<agentId>/{agent,sessions}/`, `~/.openclaw/cron/jobs.json`, `~/.openclaw/credentials/`, `~/.openclaw/media/`. One Gateway per host, one trusted operator per Gateway.
- Not Cloudflare-shaped. It assumes a persistent process, a writable filesystem, child processes and Docker. A port to Workers would need a Durable Object per agent or session in place of the process and the files.

## 5. Brief coverage

**Creating and running agents.** Partly. Agents are defined in config (`agents.list[]`: `id`, `workspace`, `agentDir`, `model`, `sandbox`, `tools`) and created by `openclaw agents add <name>`, which scaffolds a workspace with `SOUL.md`, `AGENTS.md`, `USER.md`. Many agents run in one Gateway, each isolated by directory. Sandbox mode (`off`, `non-main`, `all`) and scope (`session`, `agent`, `shared`) choose whether tools run on the host or in Docker. There is a `cli-runner` that drives an external CLI (Claude Code, Codex) as the agent brain, and "nodes" that extend a Gateway onto other devices. Missing for Harbourmaster: any UI to create an agent (there is a CLI wizard and a Control UI, but the model is config-file editing), any choice of runtime such as Cloudflare agent or Claude managed agents, and Podman vs native per agent (Docker only, and only for tools).

**Talking to agents.** Good on sessions, absent on the inbox. Sessions are stored as JSONL with an index, and the `sessions_list` / `sessions_history` / `sessions_send` tools let one agent read or message another agent's sessions. Subagents report back to the requester. WebChat shows one agent's main session across channels. Not present: an MCP server that lets Claude message an agent (OpenClaw exposes an OpenAI-compatible HTTP API and a tool-invoke HTTP endpoint instead, `docs/gateway/openai-http-api.md`, `tools-invoke-http-api.md`), and a forum-style agent inbox.

**MCP connectors and credentials.** Weak, by design. VISION.md says MCP goes through the external `mcporter` CLI (`skills/mcporter/SKILL.md`) so servers can change without a Gateway restart. There is no central connector registry, no connector-to-agent assignment, no per-user OAuth for MCP servers, and no vault. Credentials are config values and plaintext JSON (`auth-profiles.json`, `~/.openclaw/credentials/`), per agent. Skills inject secrets with `skills.entries.*.env` / `apiKey` into the host process. None of the brief's three credential cases (user, requesting colleague, agent) exists, because the trust model is one operator. What to take: per-agent profile lists with ordering and failure cooldown, and the Slack `userToken` read-only-by-default rule (a user-bound token that is read-only unless explicitly allowed).

**Slack, triggers and gateways.** The strongest area. Slack is a full channel with DMs, channels, threads, mention gating, slash commands, reactions as status, media, streaming replies, and a scope manifest. Routing by `teamId`, `accountId` and peer picks the agent. Triggers: inbound messages, webhooks (`/hooks/wake`, `/hooks/agent`), cron with delivery to a channel, Gmail Pub/Sub (`docs/automation/gmail-pubsub.md`), and hooks on internal events. There is a heartbeat mechanism (periodic agent wake with a checklist, `docs/gateway/heartbeat.md`, `docs/automation/cron-vs-heartbeat.md`) that fits "monitor and be proactive". Missing: guided Slack app creation. Setup is a manual walk through `docs/channels/slack.md` with a pasted manifest.

**Files.** Inbound only, and local. Chat attachments are fetched, size-capped, MIME-sniffed and placed in a media store, then copied into the agent's sandbox workspace. Outbound uses `outbound-attachment.ts` and per-channel upload. No Google Drive, OneDrive or Samba connection, and no "file landed, trigger agent" source (the closest is Gmail Pub/Sub). Those would be new work.

**Logging and knowledge.** Partial. Transcripts are append-only JSONL and cron has a run log (`src/cron/run-log.ts`). The Gateway writes rolling JSON-lines logs under `/tmp/openclaw/` (`docs/logging.md`) and emits OpenTelemetry via `extensions/diagnostics-otel`. This is operational logging, not an audit log meant for learning patterns. Knowledge is per-agent markdown memory files (`MEMORY.md`, `memory/*.md`) with hybrid BM25 and vector search over sqlite or LanceDB (`docs/concepts/memory.md`), plus a pre-compaction "write to memory now" turn. There is no shared multi-agent wiki. The markdown-file approach is compatible with the "file structure with file commands" idea.

**Auth and permissions.** Different problem. Gateway auth is a shared token or password, with Tailscale and trusted-proxy modes (`docs/gateway/authentication.md`, `trusted-proxy-auth.md`). Devices are approved once and get a token. Senders are controlled by DM policy and allowlists. SECURITY.md states the model plainly: authenticated callers are trusted operators, one gateway is not a multi-tenant boundary, plugins are trusted code. So there are no users, orgs or roles to borrow. What does transfer: layered tool policy, sandbox vs policy vs elevated vocabulary, pairing, deny-by-default approval fallback, and the security audit idea. With Clerk, Harbourmaster's user and org identity replaces what OpenClaw calls "operator".

## 6. Gotchas and lessons

- **Single-operator trust model.** Anything that reads across sessions (`sessions.list`, `chat.history`, the `sessions_*` tools) assumes one trusted person. Do not copy those tools as they are into a multi-user product. Scope them by Clerk user and org, and decide early which agents may read which sessions.
- **Config-file-as-database.** Agents, bindings, channel accounts, cron jobs and plugin settings live in a JSON5 file that is read at start and rewritten on change (`docs/automation/cron-jobs.md` warns that manual edits are only safe when the Gateway is stopped). This works for one user and fights a hosted UI. Use D1 tables.
- **Shared DM session by default.** `dmScope: "main"` makes every DM share one context, and the docs have to warn about leaks. Harbourmaster should isolate per sender by default.
- **Process-bound design.** Socket Mode, Baileys sessions, in-memory lane queues, file locks (`src/plugin-sdk/file-lock.ts`), timers and child processes all assume one long-lived host. Each of these needs a different mechanism on Workers (DOs, alarms, queues).
- **Size and sprawl.** `src/agents` has 341 files and `src/gateway` 183, many of them provider-specific model quirks (Bedrock, Chutes, Doubao, MiniMax, Ollama). CHANGELOG.md is about 400 KB. The channel contract has more than 20 optional adapters. Copy none of that. The project's own AGENTS.md aims for files under about 700 lines and still has several at 20-45 KB.
- **Test names encode bug history.** Files like `service.issue-13992-regression.test.ts` and `isolated-agent.skips-delivery-without-whatsapp-recipient-besteffortdeliver-true.test.ts` show where cron delivery and timers were hard to get right: duplicate timers, daily skips, restart catch-up, `every` next-run drift, stagger. Read `src/cron/service/timer.ts` (27 KB) and the regression tests before designing routines.
- **Delivery vs execution status.** OpenClaw had to split "the job ran" from "the result was delivered" (`lastRunStatus` vs `lastDeliveryStatus`). Design that split in from the start.
- **Prompt injection is declared out of scope** in SECURITY.md unless it bypasses a policy boundary. Harbourmaster will handle other people's data, so it needs the external-content wrapping and a real approval path, not just documentation.
- **Secrets in plaintext JSON.** `auth-profiles.json`, pairing stores and exec-approvals socket tokens are plain files protected by file permissions. Not acceptable for a hosted multi-user product.
- **MCP outsourced to a CLI.** It keeps core small but means no connector management, no auth re-trigger and no per-agent assignment. Harbourmaster's central connector registry has no precedent here.
- **Fast churn and renames.** The project went Warelay, Clawdbot, Moltbot, OpenClaw. Legacy aliases are still in config handling (`CLAWDBOT_LIVE_TEST`, "legacy" notes in cron types). Pinning to it would be risky, which supports borrowing patterns over taking a dependency.
- **Docs claim "one Gateway per host"** for WhatsApp session reasons. That is a Baileys constraint, not a general design rule.

## 7. Maturity

- Actively developed, young and fast moving. I found no usage numbers, so I cannot say how widely it is deployed. Version scheme is date based (2026.2.25). Roughly 4,650 TypeScript files, a 400 KB changelog, stable/beta/dev release channels, companion apps for macOS, iOS and Android, a docs site in several languages, a public skill registry (ClawHub), a security policy and threat model (`docs/security/`, `SECURITY.md`).
- Tests are extensive and colocated (Vitest, coverage floor of 70%), with e2e, live and Docker suites. Several test files exceed 20 KB, so coverage is deep in the hot paths (cron, routing, Slack).
- Docs are good where it matters to us (routing, sessions, queue, cron, Slack). `docs/concepts/architecture.md` says "Last updated: 2026-01-22", so some pages lag the code.
- The project keeps core lean on purpose (VISION.md): new channels, memory backends and skills are meant to be plugins or ClawHub packages.
- I did not run it, so I cannot say how it behaves in practice. Treat any "works well" impression as coming from the docs and test coverage only.

## 8. bruce-hermes

**What it is.** Dom's own repo at `/home/roboto/devel/bruce-hermes`, with a root README, a git history of five commits, and `bruce-reborn/` as the one app. It merges "Bruce" (TypeScript, Anthropic Agent SDK, Bun) with ideas ported from Hermes Agent (Nous Research, Python, MIT). `reference/bruce/` and `reference/hermes-agent/` are read-only snapshots for cross-checking. `bruce-reborn/PLAN.md` is a phased handoff plan. The latest commits say phases 2 to 6 are done (gateway kernel, Signal, memory, cron enhancements, wiring), and the README still says "Phase 1 status", so the README is stale. Total about 94 TypeScript files outside `reference/`. I did not run it.

**Shape.** A single long-running Bun service (`service/gateway.ts`) with channels as listeners: Mattermost, Slack, Discord, WhatsApp, Signal. Layout:

- `service/channels/types.ts`: a small `Channel` interface (`start`, `stop`, `deliver`, optional `listChannels`) plus `InboundMessage` and `OutboundMessage`. The comment says a channel is "a dumb pipe", and typing indicators, quick acks, file download and message splitting live inside each channel.
- `service/gateway/`: `kernel.ts`, `pairing.ts`, `delivery.ts`, `mirror.ts`, `session_context.ts`, `channel_directory.ts`.
- `service/lib/agent_handler.ts` (20 KB), `session_store.ts` (sqlite, `sessions.db`), `transcript.ts`.
- `service/scheduler/` (cron, store, templates), `service/tasks/`, `service/agentfield/` (an agent client).
- `.claude/skills/` (about 25 skills such as `manage-schedules`, `transcribe-remote`, `upload-to-drive`) and `execution/` (deterministic Bun scripts that the skills call).
- `CLAUDE.md` describes a 3-layer model: skills say what to do, the agent orchestrates, TypeScript scripts do the work.

**Worth borrowing for Harbourmaster.**

- The `Channel` interface in `service/channels/types.ts`. It is about 40 lines and already implemented five times, so it is proven. It is smaller and easier to implement than OpenClaw's `ChannelPlugin`. Start here, and add OpenClaw adapter ideas (threading, mentions, security) only when a second gateway needs them. Dom wrote this interface in Bruce, so copying it raises no license question. Not everything in `bruce-reborn` is that clean. The files ported from Hermes (`pairing.ts`, `kernel.ts`, `delivery.ts`, `mirror.ts`, `memory_manager.ts`, `insights.ts`, `title_generator.ts`) derive from MIT code and need the Hermes copyright notice kept.
- `service/gateway/pairing.ts`: an 8-character code from a 32-character alphabet without confusable characters, 1 hour expiry, 3 pending per platform, a per-user rate limit, lockout after 5 failed approvals, atomic file writes. It is the same design as OpenClaw's pairing, written in Bun and ported from Hermes. Swap the file store for D1.
- `service/scheduler/types.ts` (`ScheduledJob`, `JobRun`, `deliveryTargets` such as `slack:C123`, `origin`, `local`, plus `naturalLanguage` input kept next to the cron expression). Simpler than OpenClaw's cron model. The `deliveryTargets` string form is a handy way to say where output goes.
- `gateway/mirror.ts` (one conversation spanning platforms) and `delivery.ts`. Compare with OpenClaw's `identityLinks` and "last" channel before reusing.
- The skills-plus-scripts split in `bruce-reborn/CLAUDE.md` and the "self-anneal" rule (fix the script, then update `SKILL.md`). It is a working pattern for agents that improve their own skills, which ties to the learn-from-the-log idea in the brief.
- `memory_manager.ts`, `insights.ts`, `title_generator.ts` are small ports from Hermes. They are candidates for the knowledge and logging section, but they are only 2 to 5 KB each and I did not read their internals.

**Not worth borrowing.** Local `sessions.db`, `.env` files and JSON stores (`channel_directory.json`, `active_threads.json`) assume one host. A local `service/.env` exists on disk. It is gitignored, so it is not in the repo, but it is not part of what should be copied. The single-process model has the same Workers problem as OpenClaw.
