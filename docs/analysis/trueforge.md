# Trueforge analysis

Repo: `/home/roboto/devel/trueforge` (remote `cwp` = `codewithpassion/trueforge`, a fork of `truefoundry/trueforge`, MIT). Analysed 16 Oct 2026. Read-only.

Key point for the architect: this is a fork. Most of what Harbourmaster could reuse is Dom's own work on top of the upstream harness (Workers port, remote computers, Slack, Cloudflare sandbox, remote desktop). The turn loop, MCP client and UI packages are upstream code that Dom merged rather than wrote. He authored 358 of the 1075 commits. Both are marked below as [up] (upstream TrueFoundry) and [dom] (Dom's fork commits, tracked in `PROGRESS.md` Cycles 17 to 41).

## 1. Purpose

Trueforge is an open-source "agent harness": the runtime that runs the model loop, MCP tools, skills, a code sandbox, approvals, context compaction and session storage. It is exposed as a chat UI, an HTTP API plus generated TypeScript/Python SDK, and an embeddable UI package. Dom's fork (`dom/main`) turns it into something close to Harbourmaster's shape: saved agents, Slack as a channel, schedules, agents that run on machines Dom owns (a Go daemon that dials out), and a full deployment on Cloudflare Workers with Clerk login. It is the closest existing match to the brief, except for agent-to-agent messaging, MCP-server mode and credential vaults, which it lacks.

## 2. Stack and deployment

- Languages. TypeScript (Node >= 22.14, pnpm 11 workspace, tsup builds, Jest and Vitest). Go for the machine daemon (`packages/trueforge-computer`). Python only for sandbox helper scripts and the generated SDK (`python/trueforge_sdk`). Not Bun: the repo uses pnpm and Node tooling (the deploy guide only uses `bunx wrangler`).
- Server. Hono with `@hono/zod-openapi`, one OpenAPI document (`/api/v1/openapi.json`, Swagger at `/api/v1/docs`). Kysely over SQLite, Postgres or D1. LLM calls via the Vercel AI SDK `ai@7` (`trueforge-core/src/core/llm/VercelAILLM.ts`): anthropic, openai, google, openai-compatible.
- Three runtimes chosen by `TRUEFORGE_RUNTIME` (`packages/trueforge/src/config.ts`, a discriminated union): standalone Node + SQLite, distributed Node + Postgres + Redis, and **workers** (Cloudflare). Dom's deployment is Workers: `packages/trueforge/wrangler.jsonc`, name `trueforge`, custom domain `trueforge.rockyshoreslabs.io`.
- Cloudflare bindings (wrangler.jsonc): D1 `DB`, R2 `FILES` (session files), Durable Objects `SESSION_DO`, `SCHEDULER_DO`, `COMPUTER_DO` (with a Container, `standard-2`, max 5), `REMOTE_COMPUTER_DO`, `RATE_LIMIT_DO`, static `ASSETS`, cron `*/5 * * * *` to re-arm the scheduler alarm, `cpu_ms` 300000 (needs the Paid plan).
- Auth. OIDC (`openid-client` v6, `jose`) with login cookies. Deployed with Clerk as the issuer (`OIDC_ISSUER_URL` is a Clerk accounts.dev URL). Admin is matched by email (`OIDC_ADMIN_ROLE_VALUE`, `OIDC_USER_ROLE_CLAIM=email`), with an `OIDC_ALLOWED_EMAILS` allowlist. Standalone mode has no login at all. A TrueFoundry-gateway authenticator also exists (`src/truefoundry/`).
- Tenancy. `tenant_id` is a column on every table, but `identity.ts` hard-codes `'default'`. Single tenant in practice.
- DB. D1 migrations `packages/trueforge/migrations/d1/0001..0009` (generated from the Kysely SQLite migrations by `pnpm d1:schema:dump`). Documents are JSONB-in-BLOB columns (`manifest`), STRICT tables.
- Other deploy targets. Docker Compose, Helm chart (`charts/trueforge`), Railway, `npx @truefoundry/trueforge` local mode.
- Frontend. React + Vite (`packages/frontend`), built on `assistant-ui`. The reusable UI is `@truefoundry/trueforge-ui` plus `@truefoundry/trueforge-assistant-ui-runtime`.

## 5. Brief coverage

### Creating and running agents

- Solved: Saved agents with a spec (model, instructions, MCP servers, skills, sandbox, web search) and a builder UI. Run in three places: Node server, Cloudflare Workers `SessionDO`, and "Run on" a remote computer (Settings, then Computers). Cloudflare sandbox container per session. The whole thing is hostable on Cloudflare or runnable locally (`npx @truefoundry/trueforge`, SQLite).
- Partly: Always-on machine: the Go daemon runs commands as one OS user in one directory. `computer_agent_access` is an allowlist table keyed `(computer_id, agent_id)`, so several agents may be allowed on one computer, but they all share the daemon's user, `workdir` and filesystem. There are no per-agent directories or accounts, and `run_as_user` is only what the daemon reports in `hello` (`RemoteComputerDO.ts:1187`), not something the server sets. The daemon runs in Docker (`Dockerfile`, hardened example in the README), natively (systemd unit), or as a desktop image. Podman is not supported by the daemon (it appears only as an unrun Agentum prototype in `docs/remote-computers-plan.md`). Native versus container is a choice made on the machine, not in the UI.
- Partly: Claude-Desktop-like local frontend: local mode plus the chat UI is that, but the agent loop is the server's. No Claude Code or Agent SDK runtime, and no pluggable "runtime" concept. The only agent runtime is the trueforge harness itself.
- Nothing: Claude managed agents as a target. Other cloud agent services.
- Sub-agents exist (`create_sub_agent` in `DynamicSubAgents.ts`) but only as threads that clone the parent's spec, not calls to other saved agents.

### Talking to agents

- Solved: Sessions and turns persist with full event logs (`session_event` table), listable and viewable (`/api/v1/sessions`, `docs/sessions.mdx`). Chat UI and Slack threads both talk to agents.
- Nothing: Connecting Claude to the platform via MCP: there is no MCP server in the repo (`grep modelcontextprotocol/sdk/server` finds only an error class import). The platform is an MCP client only. The OpenAPI REST API and generated SDK are the only programmatic surface.
- Nothing: Agent-to-agent calls and a forum-like inbox. `docs/agent-calling-plan.md` (a `call_agent` tool with a per-agent allowlist and linked sessions) and `docs/a2a-plan.md` (serve A2A 1.0 JSON-RPC, add a service credential) are written but both say "Nothing in this plan is implemented", and `grep call_agent|a2a` in the source returns nothing. The plans are good input for the inbox design.
- Nothing: Agents asking another agent for an extract of an old session.

### MCP connectors and credentials

- Solved: One central registry (`mcp_server` table, Settings, Connectors), assigned per agent. Header auth (static headers) and OAuth with dynamic client registration, per user, with refresh and a re-auth link surfaced in chat (`resolveInvokeHeaders` in `McpServerWithAuthStore.ts`). Token key is `(oauth_server_id, user_id)` (`oauth_token` table).
- Partly: Credential cases from the brief: (1) linked to a specific user, yes, via per-user OAuth tokens. (2) colleague tasks the agent and it acts as the colleague: no. Slack and schedule turns run as the integration's or schedule's `created_by_subject`, and per-sender identity is a stated non-goal in `integrations-per-agent-plan.md`. (3) agent-own credentials for routines: only in the sense that static header auth is shared across users, and routines act as the schedule creator.
- Nothing: More than one OAuth setup per connector (one `oauth_server` and `oauth_client` blob per server row). No non-DCR OAuth (pre-registered client id and secret). No vaults: secrets (`bot_token`, `signing_secret`, MCP header values, OAuth tokens) are stored as plain JSON in `manifest` and `token` BLOB columns and are redacted only when read through the API (`secretRedaction.ts`). There is no encryption at rest, no secret references, no hand-out of a vault to an agent. The sandbox keeps "secrets in the harness", meaning the agent code never sees tokens; Code Mode calls MCP through the harness.

### Slack, triggers, gateways

- Solved: Tag the bot in a channel thread (`app_mention`) or DM it. The Slack thread maps to a session by `external_id` (`slackConversationKey`: team, channel, thread ts). Replies post in the thread. Approvals and agent questions arrive as Block Kit buttons. Schedule results can be posted to a channel by rule. A generated manifest guides setup.
- Solved: Routines: cron schedules with timezone, run-now, per-run sessions.
- Partly: Fewer clicks: the user still creates a Slack app from a pasted manifest and copies two secrets back. No OAuth install flow, no management-token automation.
- Nothing: Monitor all messages in a channel and act proactively (`events.ts`: "Only mentions are answered in channels"). Bearer-authenticated external trigger endpoint: the A2A plan records that no service credential exists for machines (`withAuth` takes only OIDC cookie or bearer). Only one deployment-wide `TRUEFORGE_API_KEY` on Node for the schedule execution route. File-landed triggers. Other gateways.
- The adapter port (`ChannelAdapter`, `InboundEvent`, `Delivery`) is written to take a second channel, but only `slack` is registered (`IntegrationTypeSchema = z.enum(['slack'])`).

### Files

- Partly: Session files in R2 or on disk (tool-result screenshots, offloaded large results, sandbox download endpoint). Files move between the agent and a remote machine in 256 KB chunks over the relay (`FILE_CHUNK_BYTES`).
- Nothing: Slack file upload: `attachment_urls` are collected but "recorded but not fetched" (`events.ts`), and `router.ts` never reads them, so a files-only message is ignored. No Google Drive, OneDrive, Samba gateway, no triggers on file arrival. (A remote computer with a mounted drive would give agents the Samba case through the daemon, but nothing builds that.)

### Logging and knowledge

- Partly: Each turn's events are stored (`session_event`, keyed by `(session_id, turn_id, event_id)`), plus per-session metrics (cost, duration, turns; `session-metrics`), `integration_event` (inbound dedupe and replay), and `computer_audit` (per-op audit rows for exec, file and desktop). An `AgentTracing` interface exists with a no-op default. Nothing enforces append-only at the database level, and there is no cross-agent action log or query API for pattern learning.
- Nothing: Shared wiki or knowledge base, "just bash" file tree. Skills (git-backed `SKILL.md` packs loaded on demand in the sandbox) are the nearest thing: the agent reads instructions from a repo, but cannot write back to it as shared memory.

### Auth and permissions

- Solved, and it matches the brief: OIDC login with Clerk as issuer in the live deployment (`wrangler.jsonc`), single admin by email, email allowlist. Authorization is deliberately minimal: `TrueForgeAuthorizer` lets anyone read and use any agent, and only the creator manage or delete (`auth/authorizer.ts`). There is an `Authorizer` interface (`listAgentAccess`, `canAccessAgent`, `getPermissions`) and an `/api/internal/list-permissions` endpoint, so fine-grained rules can drop in later. Computers use an explicit agent allowlist (`resolveComputer.ts`).
- Gap: Auth is OIDC cookie plus bearer only. No service tokens for agents or external callers, no org or role model, single tenant.

## 6. Gotchas and lessons

From `PROGRESS.md` unless noted.

- Fork upkeep is expensive. Cycle 31 merged 74 upstream commits with 35 conflicts. Five files (`config.ts`, `main.ts`, `apis/turns.ts`, `apis/sessions.ts`, `apis/schedules.ts`) were resolved to the fork's side and the upstream behaviour was deferred. Upstream also deleted an npm dependency Dom was patching (moved in-tree). Lesson for Harbourmaster: copy files out of Trueforge rather than tracking it as upstream.
- The Workers port needed seams. Node-only code in core (`undici`, `node:dns` SSRF guard, Postgres drivers, `require`) broke the Workers bundle, so the code uses deep imports only (never the core barrel) and a `workers:check` script fails the build when a banned module appears. Upstream barrel imports break the bundle.
- Durable Objects are not reliable holders of long work. Cycle 32: a turn held by a `SessionDO` alarm died when the platform replaced the instance during a 45 s remote `exec`. The fix probes the object's own storage every 5 s and cancels turns as `abandoned`. Workerd never supersedes instances, so this cannot be tested locally. Related: `alarm()` holds up to 14 minutes, so a second invocation must not hold the same turns.
- Frame limits. Cloudflare closes the whole WebSocket at 32 MiB per frame, so the relay caps frames at 4 MiB and chunks files at 256 KiB. Heartbeats are bare `ping`/`pong` text frames answered by `setWebSocketAutoResponse` so the DO is not woken.
- Optional features must not break the basic one. Cycle 30: a remote machine without the Python `pydantic` package could run nothing, because skill mounting ran unconditionally. The fix has the client report `capabilities.skills` itself. Rule: gate on what the machine proves it can do.
- Test security checks through the real runtime. Cycle 40: an Origin/CSRF check passed unit tests (injected deps) and failed every write under `wrangler dev`, which rewrites the Origin header. Cycle 39: one bad image in a tool result could brick a session; fixed with header sniffing, size limits and a request byte budget.
- Stale builds. After an SDK regeneration, rebuild the SDK `dist` before `workers:deploy`, or the deploy ships the old SDK.
- Wire-contract discipline. Remote protocol v1 is frozen. New ops arrive as capability-gated additions with defaulted fields, because stored capability documents are re-parsed on every read. Adding a required field to a persisted schema breaks old rows.
- Migration ordering. Kysely refuses a DB whose executed migration names are not a prefix of the sorted list. Dom renamed two migrations to sort after upstream's; any dev DB that ran the old names must be recreated. D1 uses its own numbered files and is unaffected.
- Slack is unproven live. Phases I2.4, I3, I4 and P3 (live workspace tests) are all blocked on "a real Slack app". An existing Slack app must be re-created from the regenerated manifest to get interactivity. Per-agent integrations mean one Slack app per agent, and two agents in one workspace need two apps.
- Live tests still owed. The Phase 9 production live test (Google login, enrol a machine with `--desktop`, takeover) is "owner-only" and not recorded as done.
- Agent worktrees (Claude Code Agent tool) started on `origin/main`, not `dom/main`; eslint scanned `.claude/worktrees`; a usage-limit cut-off left uncommitted work. Operational, but relevant if Harbourmaster is also built with parallel agents.
- Local mode has no auth and the README says never expose it.

### Docs versus code

- README says the sandbox is "Daytona today". The code has Daytona, TFY, a local provider (`LocalSandboxProvider.ts`) and the Cloudflare Computer provider. `docs/roadmap.mdx` still lists the local sandbox as future work.
- `docs/schedules.mdx` offers Hourly, Daily and Weekly; the API schema takes any 5-field cron with a timezone (`schemas/schedule.ts`). The restriction is in the UI only.
- `require_approval` on a computer is stored and shown, but nothing asks a person yet. The schema text says so ("the gate itself arrives in a later release") and `desktopTools.ts` withholds input tools when it is set. Treat it as a stub.
- The plan numbering collides: `agent-calling-plan.md` and `a2a-plan.md` call themselves "Phase 9" and "Phase 10", while the shipped remote desktop was also "Phase 9" in `PROGRESS.md`.
- `docs/cloudflare-workers-port-plan.md` says Phase 7 (sandbox on Workers) is "not started" in its header; the sandbox plan and Cycles 17 to 23 show it shipped and deployed. The header is stale.
- The port plan says Workers runs with "code execution disabled"; the live `wrangler.jsonc` sets `TRUEFORGE_SANDBOX_BACKEND=cloudflare-computer`.
