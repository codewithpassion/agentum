# Analysis: flightdex-v2

Repo: `/home/roboto/devel/flightdex-v2`. Analysed 2026-10-16. Read-only. Companion to [flightdex.md](flightdex.md), which covers the older v1 and explains why v1 is not the one to lift from.

## 1. Purpose

Flightdex v2 is a multi-workspace board and CRM tool for Harbour Edge. It mirrors a Linear team (issues, projects, comments, attachments) and a Twenty CRM (customers, contacts, notes, segments) into Cloudflare D1, serves a fast board and customer UI from that mirror, and writes changes back to Linear and Twenty. It also exposes the same operations to agents through an MCP server at `/mcp`.

It is still not an agent platform: it has no agent runtime, no machines, no sessions. For Harbourmaster it is a worked, tested, deployed example of the "MCP connectors and credentials" and "triggers and gateways" plumbing: encrypted per-tenant and per-member credentials, an MCP server behind two auth paths with an OAuth client approval gate, signed inbound webhooks, cron scheduling across tenants, and tenant isolation. The direction is inbound (agents call Flightdex), the opposite of Harbourmaster's outbound need (agents call many connectors), but the credential and webhook code transfers.

## 2. Stack and deployment

- Runtime and tooling: TypeScript, Bun workspaces, Turborepo, Biome via Ultracite, husky. Same skeleton as v1 (see flightdex.md).
- Web: TanStack Start, React 19, shadcn/ui, Hono as the Worker `fetch` handler, tRPC 11 plus TanStack Query. Board uses drag-and-drop (`features/board/`, `use-move-issue.ts`, `board-cache.ts`).
- Backend: Cloudflare Worker `flightdex`, custom domain `flightdex2.rockyshoreslabs.io` (`apps/web/wrangler.jsonc`). Bindings: D1 `DB` (database `flightdex`), R2 `FILES` (attachments), cron triggers `*/5 * * * *` and `7,17,27,37,47,57 16 * * *`. Vars `APP_TIMEZONE`, `CONTROL_PLANE_URL`. `observability.invocation_logs` is off on purpose, because the Twenty webhook URL carries a path token and invocation logs record URLs.
- DB: D1 with Drizzle (`packages/core/src/db/schema.ts`, 15 tables, migrations `0000` to `0009` in `packages/core/migrations/`). One database, `workspace_id` on every row.
- Auth: Clerk for sign-in. Authorisation is workspace membership by verified primary email (`workspace_members`), read from D1 on every request. `ALLOWED_EMAILS` now means "who may create workspaces". There are no roles: `grep role|admin|owner` in `services/workspaces.ts` finds nothing, so every member can invite, remove and replace credentials (the PRD lists this as an open decision).
- MCP: `@modelcontextprotocol/server` 2.0.0 plus `createMcpHandler` from `agents/mcp/server` (Cloudflare Agents SDK package, used only as a request handler, no Durable Object). Stateless, one server instance per request.
- External: Linear GraphQL, Twenty REST and GraphQL metadata, the control plane tRPC summary (`CONTROL_PLANE_URL`, `CONTROL_PLANE_TOKEN`).
- Secrets: `WORKSPACE_SECRETS_KEY` (AES key), `CLERK_*`, optional `CLERK_ISSUER_URL`, `PUBLIC_BASE_URL`, `ALLOWED_EMAILS`, legacy `LINEAR_*`/`TWENTY_*` (kept only until the adopt script clears the legacy workspace flag, and deleted in production on 2026-09-21 per PROGRESS cycle 11).
- Docs vs code: `README.md` is the stock scaffold and says nothing. The real docs are `docs/PRD.md`, `docs/mcp-prd.md`, `docs/multi-workspace-prd.md`, `apps/web/README.md` (291 lines, the deploy and migration runbook) and `PROGRESS.md`. Code and docs agree on every point I checked (tool counts, header names, AAD format, cron slots). The PRD says 26 MCP tools, and the code has 26 (counted from the `name:` entries in `packages/mcp/src/tools/*.ts`: 8 read, 18 write).

## 5. Brief coverage

- **Creating and running agents**: nothing. No agent entity, runtime selection, machine registry, container option or sessions. The workspace switcher, members page and connections wizard are UI patterns for "create a tenant and connect things", not for agents.
- **Talking to agents**: partly, in the other direction. Claude can call Flightdex through MCP (OAuth or API key) and read or change the board, customers, notes and comments. There is no agent-to-agent inbox, no stored agent sessions and no message to an agent. Comments on issues and CRM notes are the closest thing to a forum, and they live in Linear and Twenty.
- **MCP connectors and credentials**: partly solved, and this is the strongest match.
  - Solved: encrypted credential storage with AAD binding (`crypto/secrets.ts`); shared per-tenant credentials and per-member credentials in one resolution path (`createWorkspaceContext` with `acting`); a settings UI for keys and approved OAuth apps; credentials never returned by the API (summaries say "configured" only); stored key unreadable gives "enter it again", not a crash.
  - The three credential cases map directly: user-bound (member's own Linear key via `actAsMember`), colleague-tasks-agent (the acting member comes from the verified token, not from input), and agent/routine (`acting` omitted: cron, webhooks and provisioning use the workspace key).
  - Not solved: OAuth to third-party systems. Both Linear and Twenty use pasted API keys. The member's own Linear key is a pasted personal API key because no Linear OAuth app exists (PROGRESS cycle 11). There is no token refresh, no re-triggered auth, no multiple auth methods per connector (header, OAuth), no central connector registry assignable to many agents, no key rotation code (only the `v1:` prefix), and no vault object separate from the row that owns it.
- **Slack, triggers and gateways**: partly. Inbound signed webhooks with per-tenant tokens, dedupe and fast ack are done and verified live (cycle 6: UI updated 4.5 to 9.2 s after a Linear or Twenty edit). Cron fan-out exists. The connect wizard creates a remote webhook for you. Missing: Slack itself, routines defined per agent, a generic bearer-auth "trigger an action" endpoint (API keys exist and could back one), and file-landed triggers.
- **Files**: partly, and only attachments. R2 upload and download per tenant with membership checks and key-to-tenant binding (`files-routes.ts`, `services/attachments.ts`). No Slack upload, Google Drive, Samba or file-triggered agents.
- **Logging and knowledge**: weakly. Structured JSON log lines go to Workers logs. `sync_state` and `webhook_events` record sync outcomes and deliveries. Nothing is an append-only action log a human can query, and there is no wiki.
- **Auth and permissions**: mostly solved for a first iteration, and it goes beyond what the brief asks. Clerk sign-in, membership by verified email in D1 on every request, NOT_FOUND for non-members, API keys with read or write access, OAuth clients with read or write approval, workspace-scoped everything, and an isolation test suite. There are no roles (every member can do everything), which matches "keep permissioning to a minimum" but means the later fine-grained step has no hook yet except `access: "read" | "write"` on keys and clients.

## 6. Gotchas and lessons

All from `PROGRESS.md` cycles 6 to 11 and the PRDs, spot-checked against code where noted.

- **Clerk OAuth tokens have no audience and no app-specific scope** (cycle 9). A valid token only proves "this user consented to some app on the Clerk instance". With dynamic client registration on, one consent click for "profile, email" would have given a phishing client full write and delete. The fix is the per-client approval gate in `oauth-clients.ts`. Verified in code: `authenticateBearer` refuses with `client_not_approved` unless `resolveOAuthClient` says approved. Harbourmaster uses Clerk, so it inherits this problem if it exposes MCP over Clerk OAuth.
- **`@clerk/backend` 3.16.8 `authenticateRequest` ignores the revoked and expired flags** for OAuth tokens, and the real verify response has no `type` field and gives `expiration` in seconds although the typings say milliseconds. `clerk-oauth.ts` calls `idPOAuthAccessToken.verify` directly and normalises. Look at a real response before checking a field.
- **Auth outage must not look like a bad token.** 429, 5xx and network errors answer 503 with `Retry-After`, because a 401 makes MCP clients discard the token and redo consent. A 401 or 403 from Clerk means our own secret key was refused and logs `mcp.config` loudly (verified in `clerk-oauth.ts` `classifyFailure`).
- **Per-call OAuth verification cost about 290 ms** against 50 to 75 ms with an own key. A 60 s cache of Clerk's answer (never the approval) brought the median to 65 ms. Failures are not cached, so a fake `oat_` token costs a Clerk call per request. A Cloudflare rate limit rule on `/mcp` is the stated mitigation and was not added.
- **Approve by client id, never by name.** The app's name is self-chosen, strings land in an agent's prompt, and names are stripped of control characters and capped. The 403 text quotes the client id.
- **MCP SDK v2 on Workers**: the handler factory never sees `env`, so build the handler per request. `allowedHostnames` must be set explicitly or every request is rejected (fails closed). Set `listChanged: false` and `maxSubscriptions: 0` with a handler per request. A thrown Error's message reaches the client verbatim, so wrap every tool and let only `CoreError` text through. Set `destructiveHint` explicitly on write tools, because the spec reads a missing one as true. Partial success must name the created record or an agent retry creates a duplicate. `today` defaulted to UTC and was a day off every Sydney morning. Tool inputs need descriptions. Claude Code uses `http://localhost:PORT/callback`, not 127.0.0.1.
- **Webhooks**: Linear's `Linear-Delivery` header is unsigned, so dedupe on a hash of the signed body. Content-Length cannot be trusted, so stream with a cap. Twenty v2.40 signs only when the webhook has a secret (HMAC of `${timestamp}:${body}`). Do not use the URL path token as the HMAC key. Workers invocation logs record URLs, so a token in the path leaks into logs unless `invocation_logs` is off (set off in `wrangler.jsonc`). Whether real Twenty payloads carry the sender id was unconfirmed at cycle 10 and then settled on 2026-09-21 (cycle 11: real v2.40 payloads pass the sender check).
- **Cron limits**: D1 allows 1000 queries per invocation and a worst-case pull costs about 650, hence one tenant per run. Choose the next tenant by oldest attempt, not oldest success, or a failing tenant starves the rest (`schedule.ts`). `wrangler versions upload` does not carry cron triggers: run `wrangler triggers deploy` after.
- **Multi-tenancy retrofits are expensive.** Drizzle has no central tenant filter: about 130 call sites plus raw SQL were scoped by hand. The dangerous leaks were in sync, not reads: a pull for A would have deleted B's segments and notes. The isolation suite sat behind an env flag, so CI skipped it until a review caught it. Decide tenant scoping on day one, and make `workspace_id` NOT NULL with no default so a forgotten scope fails at insert.
- **Per-member key leak found in review (cycle 11)**: member rows are keyed by `(workspace_id, email)`, and when another Clerk user verified the same address, the stored Linear key followed the email. Fixed by adding the Clerk user id to the AAD and clearing the `linear_*` columns when the row changes hands. Verified in `member-linear.ts` (`memberKeyField`).
- **Drizzle errors carry bound parameters (ciphertext, hashes).** Credential writes replace DB errors rather than wrapping them (`unsaved` in `member-linear.ts`).
- **A user-supplied URL is a server-side fetch** (the Twenty base URL): https public hosts only, no IP literals, no redirects, fixed error messages. Documented hole: the remote workspace id comes from whatever server answers, so a member with a fake server can claim another instance's id.
- **A Linear workspace API key cannot attribute writes to another user** (`createAsUser` is OAuth-app only), which is why members paste their own keys. Options considered: map by email only, one OAuth app acting as app, each member connects their own. Dom chose the last. For Harbourmaster a real OAuth app per connector is the better long-term path.
- **Migrations**: drizzle-kit emits `ADD COLUMN ... NOT NULL` without a default, which SQLite rejects, so migration 0007 was hand-assembled with table rebuilds, with a permanent test comparing migrated `PRAGMA table_info` to the snapshot. The deploy order matters when the old Worker cannot write to the new schema: build, `versions upload`, migrate, `versions deploy @100%`, `triggers deploy`. `wrangler d1 migrations apply DB --remote` failed with code 7403 using the binding name here, and worked with the database name.
- **Dev and prod share live Linear and Twenty**, and neither client can delete a webhook. Webhook provisioning from a local run would have re-pointed production, so it is forced to `--remote` or `--skip-webhooks`.
- **Browser agents**: sign-in tokens in a URL get blocked by the claude-in-chrome permission classifier, and `agent-browser open` echoes the URL including the token. Consent for Clerk OAuth happens on the Account Portal origin, so the dev-login session does not carry over.
- **Secrets on the command line**: use `wrangler secret bulk` from a mode-600 file and shred it. The vite build writes `dist/server/.dev.vars` with local secrets (verified not uploaded).
- **Open items recorded**: no real OAuth flow to third-party systems; production Clerk is a development instance on a production domain (cycle 6, may have changed since); `get_board` is unlimited (about 200 KB at 300 cards); the OAuth approval decision awaited the owner's confirmation as of cycle 9; HTML has no script CSP.

## 7. Maturity

- Last commit: 2026-10-11 ("Merge the control plane ops tile (HEI-130)"), 76 commits. Cycle log runs 2026-08-19 (bootstrap) to 2026-09-21. Working tree has one untracked file, `session-replay.html` (10 MB).
