## Refinements (2026-10-27)

Checked against main at c5ba505. Where these differ from the scope above, they win.

- depends_on keeps every V5 task and adds V4.21, so the V4 and V5 staging checks don't overlap. V3.14 comes in through V4.21.
- The controller can do these with wrangler: deploy (`staging:deploy` applies the remote migrations), set `MAIL_DOMAIN=rockyshoreslabs.io` and `MAIL_ZONE_ID` on staging, and list or delete routing rules. Routing and sending are already on for `rockyshoreslabs.io`, so no DNS change is needed.
- Only Dom can do this: create a Cloudflare API token with Zone, Email Routing Rules, Edit on `rockyshoreslabs.io`. Wrangler can't create tokens. The controller then sets it with `wrangler secret put CF_EMAIL_ROUTING_TOKEN --env staging`. Without it, provisioning fails, so stop at that step and report blocked on Dom. If V5.2 chose Option B, also deploy the inbox Worker to staging first.
- Staging has no minute tick (crons run on production only). Approval expiry and `provisionPending` don't run there. Provision through the profile's Retry, and leave expiry to the unit tests.
- Unknown addresses: with per-address rules, Cloudflare rejects mail to an unknown address at SMTP time, and Gmail shows the bounce. The Worker never sees it. "Bounced mail shows on its task" means an outbound mail that bounces: approve a send to an address that doesn't exist and check the task's band.
- Gmail legs: use Dom's Gmail through a Gmail connector if the controller session has one. Otherwise run everything else and leave the Gmail steps for Dom, logged as pending.
- Sign in with `agent-login --env staging --email` of a user on the production Clerk instance.
