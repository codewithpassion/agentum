One run as a receipt of steps, following `docs/v2/design/hm-unified/project/Task.dc.html`. It updates live from V1's session stream and leaves slots for the thread (V2.12), the Files panel (V4) and the live computer (V6).

## Scope
- New route `apps/web/src/routes/_app/tasks.$runId.tsx`: breadcrumb "Desk › Task", title, status pill, Stop task (`runs.cancel`), and a facts row (agent, started by, runs on, cost so far).
- New `apps/web/src/components/task/`: `Receipt` renders `buildReceipt` steps with agent tiles, in/out key chips, the green link with its count between steps, and the paused step highlighted with V1's approval or question card inline. `ActionLog` renders `toActionLog` with kind tags.
- Live: subscribe to V1's per-session stream, filter to this run, and rebuild the receipt and log from the event list on each event. Don't refetch the whole run.
- The session's other runs show as "Earlier in this thread" links.
- Placeholder slots: "Files" (V4) and "Computer" (V6), each a titled empty card saying it comes later, and a "Thread" slot that V2.12 fills.

## Refinements (2026-10-26)

Checked against main at 4da1878. Where these differ from the scope above, they win.

- Dom's answer: a task is one run. A follow-up starts a new run and the view moves to it; the session's other runs show as "Earlier in this thread".
- The route file is V2.10's stub `routes/_app/tasks.$runId.tsx`; fill it.
- Live: the stream is `GET /api/sessions/:sessionId/stream` (`apps/web/src/server/routes/session-stream.ts`), resumed with `?after=<event id>`. Open it after the last event `tasks.get` returned, so it replays only what was missed. Build the transport once here as a hook (for example `components/task/use-session-events.ts`) from `components/agent/chat/use-session-stream.ts`: EventSource, `parseFrame`, the `MAX_FAILURES` rule and the fallback when the stream is refused (`readyState === EventSource.CLOSED`, V1.6's must-fix). The fallback refetches `tasks.get` every 10 s, not every 1.5 s. V2.12 reuses the hook, so one page holds one EventSource.
- The stream carries only `STREAM_EVENT_TYPES`, so connector failures reach the action log on reload only.
- Request cards come from `components/requests/` (moved in V2.10). A `request` frame or `request.*` event updates the paused step, and `settledFromEvent` settles the card.
- Stop task: `runs.cancel` also accepts a `waiting` run.
