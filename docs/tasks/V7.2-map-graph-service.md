The data behind the map's Runs mode. It holds no UI judgement, so it is built and tested on its own.

## Scope
- `packages/services/src/map.ts`: `graph(principal, { days: 7 })` returns `MapGraph`. Nodes come from triggers (http, routine, email and Slack channels from earlier milestones), agents (with tool ports from their connectors, computer, browser and skills) and outputs (Slack channels, library folders the agent writes, the Q&A board, outbound email).
- Wires and 7-day counts come from `events`: `trigger.fired` gives trigger to agent, V3's hand-offs give agent to agent, `slack.message_sent` gives agent to Slack, `library.write` gives agent to folder, and `qa.asked`/`qa.answered` give agent to Q&A. A wire with zero events in 7 days is idle.
- An agent is `waiting` when it has an open V1 pending request. The node carries the request summary for the inspector.
- Stored `map_positions` are merged in, and a node without one gets a column layout (triggers, agents, outputs).
- tRPC `map.graph` in `apps/web/src/server/trpc/map-router.ts`, added to `router.ts`.
- Counting stays within D1 limits: grouped queries over a time-bounded index, not one query per wire.

## Check
- `packages/services/src/map.test.ts` with a `bun:sqlite` db: each wire kind and its count, the 7-day window edge, idle wires, the waiting flag, workspace isolation, and stored positions winning over the layout. `map-router.test.ts` passes.
- `bun run check && bun run test && bun run build` pass.

## Refinements (2026-10-27)

Checked against main at 24c28ad. Where these differ from the scope above, they win.

- depends_on stays V7.1. The mail, computer and browser data it reads are columns and event types from V5.1 and V6.1, which V7.1 follows, and the tests seed rows and events. It needs no V3 to V6 service.
- Read the `triggers` table directly for trigger nodes. `triggers.list` filters `kind = "http"` (`triggers.ts` around line 308) and routines filter `routine`, so neither returns `mail` rows. A mail trigger's label is its agent's `agent_mailboxes.address`. Leave out revoked triggers and `draft` or archived agents. Add one `slack` trigger node per agent Slack app (`slack_apps`).
- Wire sources, one grouped query per event type over `events_workspace_type_created_idx` (V7.1):
  - Trigger to agent: `trigger.fired` has `actor_id = triggerId` and `agent_id`, so group by those, no JSON. Slack to agent: `run.queued` whose `payload.origin` is `slack`, grouped by `agent_id`. Mail to agent: `mail.received` grouped by `agent_id`.
  - Agent to agent: there is no hand-off event. `run.queued` carries only `{ depth, origin }`. Use `runs.parent_run_id`: the `run.queued` events in the window joined to `runs` and to the parent run for the from-agent. This counts `send_message` and agent-made inbox wakes.
  - Agent to Slack: `slack.message_sent` keyed on `json_extract(payload, '$.channel')`. Agent to library: `library.write` keyed on the first segment of `payload.path`, with `agents/<slug>/` and the task folders each kept as one node. Agent to Q&A: `qa.asked` and `qa.answered`. Agent to email: `mail.sent`.
- Leave out dry runs (`runs.dry_run`), as V3.7 does for the desk.
- Agent ports: connectors from `connector_assignments`, skills from `skill_assignments`, the computer from `agents.computer_machine_id` (V6.1) with its status, and the browser unless `runtimeConfig.browser === false` (V7.4). Use grouped queries for the workspace, not `agentProfile.profile` per agent.
- Waiting: an agent with a run in status `waiting` (`runs_agent_status_idx`). Put the pending request record on the node in the shape `requests.listPending` returns, so V7.3 renders it with `RequestCard` and `viewFromRecord`.
- Build the service in `compose.ts` (`map` in `Services`) and mount `map-router.ts` in `runtime-router.ts`, not `router.ts`, whose comment says lanes never edit it.
- Same-file overlaps: `runtime-router.ts` with V3.6 and V4.11 (services lane). `compose.ts` with many V4 to V6 tasks across lanes (V4.6, V4.9 to V4.12, V4.20, V5.3, V5.7, V6.6, V6.8, V6.10 to V6.13).
