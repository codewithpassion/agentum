From M3 gate round 1 (docs/reviews/M3-1.md, must-fix 1). Any signed-in workspace member can follow a `/connect?as=agent:<id>` link from anywhere, such as one the proxy's needs-auth message passes to Slack, and bind their own account as the agent's login. Only the agent's page should start that flow.

## Scope

In `packages/services/src/connector-oauth.ts` `start`, or in the `/connect/:connectorId` route in `apps/web/src/server/routes/connectors-oauth.ts`, refuse to start a flow for `as=agent:<id>` unless the navigation came from Harbourmaster itself. Take the smaller of these two fixes:

- Require `Sec-Fetch-Site: same-origin`, or, when that header is missing, a `Referer` whose origin matches the request. Any other request is redirected to `/agents/<id>?tab=connectors` and inserts no `oauth_states` row and registers no client.
- Have a GET with `as=agent:<id>` render a confirmation page that names the agent and the connector. Only a same-origin POST from that page starts the flow.

`as=user` stays as it is, because it can only ever bind the clicker's own row. The proxy's needs-auth text and `connectPath` may keep the `/connect` path, since the redirect now lands on the agent page. Pointing the agent case at `/agents/<id>?tab=connectors` directly is also acceptable. Update the agent tab's "Connect as this agent" link if the POST variant is chosen.

## Check

In `apps/web/src/server/routes/oauth-callback.test.ts`:

- `GET /connect/:id?as=agent:<id>` from a signed-in member without same-origin fetch metadata redirects to the agent page, and `oauth_states` stays empty with no registration call at the stub.
- The same GET with `Sec-Fetch-Site: same-origin` (or the confirmation POST) redirects to the provider with a state row whose `owner_kind` is `agent`.
- `?as=user` without fetch metadata still redirects to the provider.
- The existing tests (a different initiator gets 403, an off-site `return_to` gets 400, a non-member's `?as=agent` is refused) still pass.

`bun run check && bun run test && bun run build` pass.
