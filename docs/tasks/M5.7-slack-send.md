Asked for by Dom on 19 Oct 2026. Today an agent can only answer in a Slack thread where someone mentioned or messaged it: the reply goes out through `packages/services/src/slack/gateway.ts:236` when the run ends. An agent asked from the Harbourmaster chat, a routine or a trigger has no way to post to Slack. Comms-Chief on staging hit this.

Decisions (Dom, 19 Oct 2026):
- Targets: channels the agent's bot has been added to, and DMs to linked workspace members (the `identity_links` rows for that Slack team). No arbitrary Slack users.
- No approval per message. Every send is recorded in the Log, with a cap of 30 sends per hour per agent.
- A reply in a thread the agent started routes back to the same agent and session, as a mention does.

Where the bot is: ask Slack live rather than keeping our own copy. `users.conversations` with the bot token lists the channels the bot is a member of (the app already has `channels:read` and `groups:read`), so nothing goes stale and existing apps need no manifest change. Linked people come from `identity_links`.

## Scope

- Two tools for runs on the Harbourmaster MCP server, for agents that have a Slack app installed (follow the R.1 and SK.3 tool pattern, thin calls into a service method):
  - `slack_destinations`: the channels the bot is in (name, id, private or public) and the linked people (Harbourmaster name, Slack display name), so the agent can pick a target.
  - `slack_send`: `to` is a channel name or id from that list, or a linked person; `text`; optional `thread_ts` to continue a thread the agent started. Posts with the agent's own bot token. Returns the channel, `ts` and a permalink if Slack gives one.
- A DM to a person opens the conversation with `conversations.open` (add the `im:write` scope to the manifest; say in the review file that existing apps need it added in Slack and reinstalled, and make the tool's error say so when Slack answers `missing_scope`).
- Refuse a channel the bot isn't in, an unlinked or unknown person, and an agent without a Slack app, each with a clear message that tells the agent what to do. Refuse over the cap with the time when the next send is allowed.
- Record a `slack.message_sent` event (agent, run, channel or person, ts, text length, never the text itself) and count it for the cap.
- Thread replies: when the agent starts a message, remember the thread (`channel`, `ts`) against the agent and session, so a reply in that thread from a linked person starts a run in the same session, through the existing thread-to-session mapping (`externalKey`) the mention path uses.
- Tool descriptions say what the agent can reach and that every send is logged.
- The agent's system prompt, when it has a Slack app, gets one line saying it can post with `slack_send` and list targets with `slack_destinations`.

## Check

- Service and tool tests with a fake Slack client: lists channels and linked people; sends to a channel, to a person (opens the DM), and into its own thread; refuses a channel the bot isn't in, an unlinked person, an agent without an app, and the 31st send in an hour; a reply in a started thread maps to the same session; `missing_scope` gives the reinstall message; the event never carries the text.
- `bun run check && bun run test && bun run build` pass.
- Live on staging (controller): Comms-Chief, asked in the Harbourmaster chat, posts in a channel it's in and DMs Dom; Dom's reply in that thread reaches the same session.
