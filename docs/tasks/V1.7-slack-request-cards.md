The pure half of answering from Slack: what the cards look like and how a button click is read back. V1.13 wires it to the Slack apps.

## Scope
- New `packages/services/src/slack/request-cards.ts`, no I/O:
  - `approvalCard({ agentName, summary, input, expiresAt, requestId })`: Block Kit blocks with the agent name, the summary, the scrubbed input in a code block (cut to Slack's 3 000-char text limit), the expiry in Slack's `<!date^…>` format, and three buttons, Allow once, Always allow and Deny (style danger), with `action_id` `hm_req:<requestId>:<decision>`.
  - `questionCard({ agentName, questions, expiresAt, requestId })`: one section per question; a single-choice question gets buttons (`hm_req:<requestId>:choice:<q>:<i>`), a multi-select or open question gets an "Answer" button that opens a modal (`modalView` below).
  - `modalView(request)`: a `plain_text_input` per question, plus `checkboxes` for multi-select choices; `callback_id` `hm_req_modal:<requestId>`.
  - `settledCard(request, { by, via, outcome })`: the card after any surface answered, expired or cancelled it, buttons removed ("Allowed once by Dom on the web", "Expired, nobody answered").
  - `parseInteraction(payload)`: from a `block_actions` or `view_submission` payload to `{ requestId, userId, teamId, appId, answer }` or a reason it is not ours, validated with the V1.1 answer schemas.
- Fallback text on every message for notifications.

## Check
- `packages/services/src/slack/request-cards.test.ts`: snapshot-free assertions on block types and `action_id`s; a long input is cut under the limit; parse round trips for each decision, a choice button, and a modal submission with free text and a multi-select; a foreign `action_id` is ignored.
- `bun run check && bun run test && bun run build` pass.
