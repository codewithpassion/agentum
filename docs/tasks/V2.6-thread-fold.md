The assistant-ui thread (V2.12) needs a session's events, both the stored ones and V1's live frames, as messages with parts. This task writes that fold as a pure module beside the stream frame types, so the UI task only wires it into assistant-ui's external store runtime. It follows trueforge's `convertTurnMessages.ts` and `useTrueForgeAgentMessages.ts` as patterns. Those files are Apache-2.0, so any file that adapts their code carries a "Modified from trueforge assistant-ui-runtime (Apache-2.0)" header, and the package gets a copy of the Apache 2.0 licence.

## Scope
- New `packages/protocol/src/thread.ts`, exported as `@repo/protocol/thread`, with its own neutral types (no assistant-ui import): `ThreadMessage { id, role (user | assistant), runId, createdAt, status (running | waiting | done | failed | cancelled), parts }`, where a part is text, reasoning, tool-call (name, input, result, ok, toolUseId), attachment (file id) or a V1 approval or question request.
- `foldThread(events): ThreadMessage[]`: `message.user` starts a user message, with its input file ids as attachments. Assistant text, reasoning and tool calls of one run form one assistant message. `tool.result` joins its call by `toolUseId`. Run status events set the message status.
- `applyFrame(messages, frame)`: folds one V1 live frame (token deltas included, if V1 streams them) into the list without re-folding everything, and is idempotent on a repeated event id (stream resume with Last-Event-ID).
- Attachment markers become attachment parts through `@repo/protocol/attachments`.
- Add `packages/protocol/LICENSE-APACHE-2.0` if any code is adapted rather than rewritten.

## Check
- `packages/protocol/src/thread.test.ts`: two runs in one session give user, assistant, user, assistant; a result joins its call out of order; reasoning lands before text; a waiting run gives a message with a request part; replaying a frame twice changes nothing; deltas append to the open text part.
- `bun run check && bun run test && bun run build` pass.
