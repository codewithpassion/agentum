Found by the local M1 gate run on 16 Oct 2026. One of five `bun scripts/e2e/skeleton.ts` runs died with "database is locked". The error came from the skeleton process, not the Worker.

## Scope

`scripts/dev/local.ts` (around line 110) opens the local D1 SQLite file with `bun:sqlite` and sets no busy timeout. It should set one (for example `PRAGMA busy_timeout = 5000`) on every connection it opens, so a dev or e2e script waits while the Worker holds the write lock. Scripts only; nothing ships in the Worker.

## Check

A test opens the same SQLite file twice, holds a write transaction on one connection, and shows that a write through the `local.ts` helper waits and then succeeds once the first commits. The test fails without the busy timeout. With `bun run dev` and an enrolled daemon running, `bun scripts/e2e/skeleton.ts` passes 5 times in a row.
