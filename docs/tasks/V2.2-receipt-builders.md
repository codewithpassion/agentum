The task view and the desk both turn a run's events into plain words. These pure builders do that once, so the server (desk bands) and the browser (live receipt from V1's stream) share one implementation.

## Scope
- New pure module folder `packages/services/src/tasks/` (no drizzle, no `env`, browser-safe like `cloud/environment.ts`), exported as `@repo/services/tasks/receipt`, `@repo/services/tasks/action-log`, `@repo/services/tasks/status-band`.
- `buildReceipt(run, events): ReceiptStep[]`: step 1 is where the run came from (origin: ui, slack, inbox, trigger, routine, handoff from another run). Consecutive calls of one tool fold into one step with "×n". An assistant message closes a step. A skill read is its own step ("Skill: name vN"). A pending approval or question from V1 is a `paused` step and carries its request id. In and out chips come from the top-level scalar keys of the tool input and result (at most 3 each, values truncated). `countToNext` comes from array lengths in the result or the call count.
- `toActionLog(events): ActionLogEntry[]`: `message.reasoning` becomes thought, `tool.call` tool_call, `tool.result` tool_result (error when `ok` is false), V1's approval and question events plus `run.limit_reached` become note, `run.failed` and `connector.*` failures become error.
- `statusBand(run, events, pending): StatusBand`: one sentence. Running gives the latest tool in words or "Thinking", waiting gives what it waits for, done gives the first sentence of the result text, failed gives the error.
- Strip `[ATTACHMENT:]` markers with `stripAttachmentMarkers` from `@repo/protocol/attachments`.

## Check
- `packages/services/src/tasks/*.test.ts`: a ui run with three calls of one tool folds to one step with ×3 and a count; a Slack-origin run starts with a Slack step; a paused approval step; chips cap at 3 keys; each event type maps to the right log kind; a band for each of running, waiting, done and failed; an empty run gives one origin step.
- `bun run check && bun run test && bun run build` pass.

## Refinements (2026-10-26)

Checked against main at 4da1878. Where these differ from the scope above, they win.

- Payloads the builders read: `run.queued` is `{ depth, origin }`, with `origin` the session origin (ui, slack, inbox, routine, trigger, mcp; `queuedEvents` in `runs.ts`). `message.user` is `{ fileIds, text }`. `message.assistant` and `message.reasoning` are `{ text }`. `tool.call` is `{ input, name, toolUseId }`. `tool.result` is `{ ok, output, toolUseId }` with `output` a string. `request.*` events carry `requestId`, and `request.opened` adds `display`, `expiresAt`, `kind`, `toolName`, `toolUseId` (`announce` in `requests.ts`). A handoff is `run.parentRunId`; the caller passes the parent agent's name in, since no event holds it.
- Out chips and array counts apply only when `output` parses as a JSON object or array. Otherwise there are no out chips, and `countToNext` uses the call count.
- An event with `payloadRef` set has an empty payload (the body went to R2). Render its step without chips instead of failing.
- Skill steps: cloud runs call `activate_skill` with `input.name` (`apps/web/src/server/pi-run-skills.ts`), machine runs call Claude Code's `Skill` tool (check its input key in a recorded run). No event carries a skill version, so the title is "Skill: name" without "vN". Managed runs have no skill call to match.
- Import `RunRecord`, `EventRecord` and `RequestRecord` with `import type` only. V2.11 bundles these modules for the browser, so they must not pull drizzle at runtime; the build's `drizzle` grep checks it. Add one `exports` entry per module to `packages/services/package.json`.
- `statusBand` for a done or failed run uses `run.resultText` and `run.error`, so V2.8 reads events only for live runs.
