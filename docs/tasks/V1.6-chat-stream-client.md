With the stream route from V1.4 in place, the existing chat (`apps/web/src/components/agent/tabs/chat.tsx`) stops refetching the whole transcript every 1.5 s. This is the minimum V1 needs to watch a run live. The assistant-ui chat is V2.

## Scope
- A pure reducer in `apps/web/src/components/agent/chat/stream-logic.ts`: `applyFrame(state, frame)` folds `event`, `delta`, `run` and `request` frames into the same `ChatItem` list `toChatItems` builds today. A `delta` shows as the agent's growing message and is replaced by the stored `message.assistant` event of the same run. A `truncated` event triggers one transcript refetch. Frames are parsed with `@repo/protocol/stream`.
- A hook `useSessionStream(sessionId)` in `apps/web/src/components/agent/chat/use-session-stream.ts`: loads the transcript once through `getTrpc().sessions.transcript`, then opens `EventSource('/api/sessions/:id/stream?after=<last event id>')`. The browser's own reconnect sends `Last-Event-ID`. After three failed reconnects it falls back to the old poll (`POLL_MS`), and goes back to the stream when the page regains focus.
- `chat.tsx` uses the hook. `shouldPoll` and the `setInterval` stay only as the fallback. A `waiting` run shows "Waiting for an answer" in `statusLine`.

## Check
- `stream-logic.test.ts`: event frames in order, a duplicate event id ignored, delta then final message replaces the delta, a run frame updates the status line, a truncated event asks for a refetch.
- `bun run check && bun run test && bun run build` pass, and `apps/web/dist/client` has no `drizzle`.
- Browser check (dispatcher, local dev with the fake or faux runtime): send a message, see text and tool calls appear without a 1.5 s jump, reload mid-run and see nothing duplicated.
