From M5 gate round 1 (docs/reviews/M5-1.md, must-fix 1). Slack DM sessions are open to the whole workspace, both in the UI and to any run of the agent through MCP `read_session`. Another user can ask the agent to repeat someone's DM in a channel.

## Scope

A session opened by a Slack DM is visible only to the user who sent it, the same rule `origin: "ui"` sessions follow. Channel-thread sessions stay shared. The Slack service knows the trigger (`event.trigger === "dm"`, from `channel_type: "im"`). Pass a privacy flag from the Slack service through `startRun`'s session input to the `sessions` row, for example a nullable `private` column, or a `slack_dm` origin if contract C3 may change. Make `visibleSessions` (`packages/services/src/sessions.ts:146-158`) treat that flag like `ui`: visible to `actorId`, and to a run only when the run's `onBehalfOfUserId` is that user. A schema change means `bun run generate` and committed migrations. `getRun` and `cancelRun` already reuse the rule after M2.4, so they follow. Change `sessions.test.ts:234-252` to start the shared session as a channel thread, so it still asserts what it means.

## Check

In a `sessions.test.ts` case, user u2's DM session is missing from `sessions.list` and `sessions.transcript` for user u1 and for a run on behalf of u1, and is present for u2. A channel-thread Slack session stays visible to both. A `slack-events.test.ts` case sends a DM fixture and checks that the resulting session carries the privacy marker, and that a mention fixture's session does not. An MCP `read_session` from a run on behalf of another user returns not-found for the DM session. `bun run check && bun run test && bun run build` pass.
