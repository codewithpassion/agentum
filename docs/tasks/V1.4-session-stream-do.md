Today the chat polls `sessions.transcript` every 1.5 s (`POLL_MS` in `apps/web/src/components/agent/chat/chat-logic.ts`) and refetches the whole transcript. This task adds one stream per session that every runtime feeds, modelled on trueforge's `SessionDO` with `Last-Event-ID` resume (`/home/roboto/devel/trueforge/packages/trueforge/src/workers/{SessionDO,turnEventWire,durableObjectEventSubscriptions}.ts`, patterns only).

## Scope
- New `apps/web/src/server/session-stream.ts` (DO class `SessionStream`, named by session id) with its logic in `session-stream-core.ts` so bun can test it. It holds open SSE writers in memory, fans out each published frame, sends a `ping` every 25 s, and drops a writer whose write fails. Nothing is stored: stored events live in D1, deltas are ephemeral.
- RPC `publish(frame)` for frames from `@repo/protocol/stream`, and `fetch` that opens a stream.
- Binding `SESSION_STREAM` in all three places of `apps/web/wrangler.jsonc` (top level, `env.staging`, `env.staging.previews`) and migration tag `v5` with `new_sqlite_classes: ["SessionStream"]`. Export the class from `src/server.ts`.
- Route `GET /api/sessions/:sessionId/stream` in a new `apps/web/src/server/routes/session-stream.ts`, mounted from `routes/runtime.ts` on a cookie group. Clerk session to principal, then `services.sessions` visibility (a hidden or unknown session answers 404). Resume: with `Last-Event-ID` (or `?after=`), first replay the session's stored events after that id from `services.events.query` (pages of 500, `message.*`, `tool.*`, `run.*`, `request.*`), then hand over to the DO. Subscribe to the DO before reading D1 and drop duplicates by id, so an event that lands between the two is not lost.
- Publishing: a `streamPublisher(namespace, defer?)` in `apps/web/src/server/session-stream-port.ts`. In `compose.ts`, `Infra` gains an optional `streams` port; `composeWith` registers it with `events.onAppend` and `runs.onEvent` (the runs service has its own events instance), so PiRun, ManagedPoller and machine uploads (all through `ingestRunEvents`) and the request events from V1.5 reach the stream without changes to the services. Events without a session are skipped. A payload with `payloadRef` goes out as `truncated: true`. A run status change goes out as a `run` frame for `run.*` events. A failing publish logs and never fails the append.
- The published record is the stored one, so the C.19 scrub and the run's masker have already run. Nothing raw reaches the stream from here.

## Check
- `session-stream-core.test.ts`: fan-out to two writers, a closed writer is dropped, ping cadence with a fake clock.
- `routes/session-stream.test.ts`: 401 without a session, 404 for another user's private session, replay after `Last-Event-ID` in id order then live frames, no duplicate when an event is published during the replay.
- `compose` test: an appended run event reaches a fake `streams` port with the stored (redacted) payload; an event with no session does not.
- `bun run check && bun run test && bun run build` pass, and the client bundle grep for `drizzle` stays clean.
- Live on staging (controller): `curl -N` the stream of a session with an agent cookie while a cloud run works; events arrive within a second, and a reconnect with `Last-Event-ID` replays only the missed ones.

## Refinements (26 Oct 2026, against main)

Checked against the code before V1 started. Where these differ from the scope above, they win.

- `startRun` writes `run.queued` and `message.user` with `insertStatement` (`runs.ts:500-512`), which skips `onAppend`. Publish both to the stream after `startRun`'s atomic write.
- The replay filter uses `events.query`'s `types`, which takes exact `EVENT_TYPES` values with no wildcard. List the exact message, tool, run and request event types instead of `message.*`, `tool.*`, `run.*`, `request.*`.
