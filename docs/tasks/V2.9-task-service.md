The task view needs one run with its context: agent, who started it, where it runs, cost so far, its events and its pending request. V3's "Recent tasks" card reuses the list call.

## Scope
- New `packages/services/src/tasks/service.ts` `createTasksService`, built in `compose.ts`.
- `tasks.get(principal, runId)`: the run (status, input text, timestamps, usage as cost so far), the agent (name, runtime, machine), "started by" in words (a person, Slack, inbox thread, trigger or routine name, or a handoff from another run via `parentRunId` with that run's agent), the session id for the thread, the session's other runs (id, status, input), the run's events, and V1's open request for the run.
- `tasks.list(principal, { agentId?, limit, before? })`: recent runs with title (session title or trimmed input) and `statusBand`.
- New `apps/web/src/server/trpc/tasks-router.ts` (thin), added to `runtime-router.ts`.
- Reads go through `authorize()`. A private session's run is visible only to its actor, as in `visibleSessions`.

## Check
- `packages/services/src/tasks/service.test.ts`: "started by" for each origin and for a handoff; cost from usage; the private-session rule; the agent filter and paging of `list`; two-workspace isolation.
- `apps/web/src/server/trpc/tasks-router.test.ts`: input validation and 401.
- `bun run check && bun run test && bun run build` pass.

## Refinements (2026-10-26)

Checked against main at 4da1878. Where these differ from the scope above, they win.

- Dom's answer: a task is one run. A follow-up starts a new run, and the session's other runs show as "Earlier in this thread".
- Visibility: use `visibleSessions` and `sessions.get(principal, sessionId)` from `sessions.ts` (V1.4). They already hide a ui session or private DM from other members, so no new rule is needed.
- Titles: sessions have no title column. `titlesFor` in `sessions.ts` (trigger name, inbox thread title, Slack label, else the first message) is a closure inside `createSessionsService`. Lift it with `triggerNamesOf`, `threadTitlesOf` and `slackLabelsOf` into an exported helper and call it from both services.
- `tasks.get` returns the session's `origin` and `externalKey`. V2.12 continues a ui session with `runs.start({ session: { externalKey, origin: "ui" } })`; the browser cannot start runs in other origins (`runs-router.ts`).
- Events: return the session's events, not only the run's. V2.11 filters to the run, V2.12 folds the whole session. Use the types in `STREAM_EVENT_TYPES` (`apps/web/src/server/session-stream-frames.ts`, after V2.1) so the snapshot and the stream agree, and include `request.*`, which `sessions.transcript` leaves out. `events.query` caps at 500 per call: page, or cap and say so in the result.
- Open request: `requests.listPending(principal, { sessionId })` filtered to the run, dropping expired ones as V2.8 does.
- "Started by": `run.actor`, the `run.queued` payload's `origin`, and `parentRunId`. Person names go through the `PeopleLookup` port (`infra.people`). `usage.costUsd` can be missing; return null then, not 0.
- Export the service as `./tasks/service`. V2.2's builders must never import it.
