Agent email builds on Dom's agentic-inbox-hei. Before the contract, decide how harbourmaster reaches it. This runs first in V5, and the contract V5.1 depends on it.

## Scope
- Read `/home/roboto/devel/agentic-inbox-hei` (`workers/index.ts` `receiveEmail`, `workers/durableObject/index.ts` `MailboxDO`, `workers/lib/tools.ts`, `workers/email-sender.ts`, `workers/lib/auth.ts`, `wrangler.jsonc`) and its `docs/00-current-state.md`, `01-rest-api-plan.md`, `02-cli-plan.md`.
- Option A, a module inside harbourmaster's Worker: port `MailboxDO` and the tool functions into a portable module, add an `email()` handler to `apps/web`, drop Access auth and the React Router/Kumo UI. Weigh zod 3 there against zod 4 here, one more DO class and migration tag, and the Apache-2.0 notice on ported files.
- Option B, a separate Worker reached by service binding: keep agentic-inbox-hei deployed with its UI, CLI and MCP; add a `WorkerEntrypoint` RPC surface there and a binding from harbourmaster (top level, `env.staging`, `env.staging.previews`); inbound mail calls back into harbourmaster through a reverse binding. Weigh two deploys per environment, previews, and changes in a second repo.
- For both: how one address per agent is provisioned on Email Routing (per-address rules through the Cloudflare API, or a catch-all with the address registry in D1), how sending works (`send_email` binding with Email Sending), and where mail bytes live.
- Write `docs/decisions/agent-email.md`: the decision, the `MailboxPort` method list V5.1 should define, the changes needed in agentic-inbox-hei (Option B), and what Dom must set up in Cloudflare. If the choice needs Dom, report blocked with the two options and a recommendation.
