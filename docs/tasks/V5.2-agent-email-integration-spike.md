- Cloudflare facts, read with wrangler on 27 Oct: account `a12823016aa16d0a8dd2678b258bd751`. Zone `rockyshoreslabs.io` has Email Routing on and Email Sending on (DKIM selector `cf-bounce`). Its catch-all is disabled (drop). Two literal rules, `ccau@` and `supatesta@`, forward to Dom. The staging Worker is `harbourmaster-staging`. DO `migrations` sit at the top level of `wrangler.jsonc` only (next tag `v6`). Crons run on production only, so staging has no minute tick.
- What wrangler can do: the controller's login has `email_routing (write)`, `email_sending (write)` and `zone (read)`. It can enable routing and sending and list, create and delete rules. It can't create an API token or write DNS records.
- Plan defaults to record. Staging uses `MAIL_DOMAIN=rockyshoreslabs.io`, which needs no DNS change. Previews leave `MAIL_DOMAIN` empty, and mail is off there. Dom picks the production domain before the production deploy. Provision with per-address literal rules (action `worker`), as the plan says, not the catch-all. Pointing the catch-all at a Worker would change how unknown mail to Dom's domain behaves. Without it, Cloudflare rejects unknown addresses at SMTP time, and the sender gets a bounce. Note the per-zone rule limit and what it means for the number of agents.
- The Worker's `EmailRoutingPort` needs a Cloudflare API token (Zone, Email Routing Rules, Edit, on `rockyshoreslabs.io`). Only Dom can make it. Name the secret in the decision (default `CF_EMAIL_ROUTING_TOKEN`), plus the zone id (`MAIL_ZONE_ID`, a var).
- `EmailRoutingPort` needs `findRule(address)` besides `createRule` and `deleteRule`, so provisioning can refuse an address that already has a rule (Dom's two).
- Decide whether to port `verifyDraft` (Workers AI). Plan default: no, because outside mail waits for a person anyway.
