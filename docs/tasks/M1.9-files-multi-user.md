Follow-up from M1.6 (docs/reviews/tasks/M1.6.md). On a multi-user machine `hm-agent` owns the run's work directory, so the daemon can't write input files into it or read attachments back. Today a run with input files fails there with a clear message, and attachment markers are refused with a note.

## Scope

On a multi-user machine the daemon places input files in the work directory and reads attachments out of it, through the same narrow sudo path M1.4 uses for `mkdir` and `rm`, so the files end up owned by `hm-agent` and the daemon's own config stays unreadable to it. Any sudoers change stays as narrow as M1.4's and is written by `install-service`. The single-user path does not change. Remove the "not supported yet" failure and refusal M1.6 added.

## Check

Daemon tests cover the exact sudo argv for writing an input file and reading an attachment, and show that a path outside the work directory is refused on both. The M1.6 file tests still pass. Live part, on a machine with sudo (Dom): a run with an input file reads it, and an attachment it writes shows up in the chat.
