Agents send and reply from their own address. Mail to an outside contact waits for a person by default.

## Scope
- `packages/services/src/mail/outbound.ts`: `send(principal, draft)` and `reply(principal, threadId, draft)` for a run principal. Recipients are checked with the V5.1 inside/outside rule. Inside: send through `MailboxPort` now. Outside without an "Always allow": create a V1 approval of the `mail_send` kind (from, to, subject, body preview), record the message `held`, emit `mail.held`, and return "waiting for approval" to the agent.
- The approval decision handler: Allow once or Always allow sends and marks `sent`; Deny marks `rejected`; expiry marks `expired`. Each tells the waiting run the outcome through V1's mechanism.
- A sent mail links its thread to the run's task.
- The desk counts: `mail.today(workspace)` per address, in and held.

## Check
- `packages/services/src/mail/outbound.test.ts`: inside sends at once, outside is held with an approval, allow sends, always-allow lets the next mail through, deny and expiry close it, the thread links to the task.
- `bun run check && bun run test && bun run build` pass.

## Refinements (2026-10-27)

Checked against main at c5ba505. Where these differ from the scope above, they win.

- No V3 or V4 dependency. `requests.ts` is touched by no V3 or V4 task. V3.2 only calls `setRule` and `removeRule`.
- The approval is a V1 `approval` through `requests.open`, with `toolName: "mail_send"`, `toolUseId: "mail:<messageId>"` and `toolKey: mailToolKey(address)` (V5.1). `display.input` carries `from`, `to`, `cc`, `subject` and `preview` (the first 500 characters). One request per message. Its key names the first outside recipient without an `allow` rule. On Always allow, the handler also writes `allow` rules for the message's other outside recipients.
- Held or not: `needsApproval` is true only for an `ask` rule, and mail turns that around. Query `agentToolRules` for an `allow` rule on each outside recipient's key instead.
- Changes in `requests.ts`, keyed on the `mail:` prefix of `toolUseId`. `open` skips `runs.markWaiting`, so the agent keeps going and the tool returns at once. `cancelForRun` leaves the row pending, so it outlives the run and expires after `APPROVAL_TTL_MS`. `resume` skips `runs.resumeRequest`, since no runtime waits on it (managed `resume` would kick the poller).
- Plan default, replacing "tells the waiting run": the run is not woken. The outcome shows in `mail_read` and as `mail.sent`, `mail.rejected` or `mail.expired` in the session's events. A remote MCP call can't wait an hour, and a 25-second long poll per call would hold the run in `waiting` while the model loops.
- Decision handler: an `events.onAppend` listener on `request.answered` and `request.expired` for rows with `toolName === "mail_send"`. It reads the decision from the row's `answer`.
- Inside check: `MemberDirectory` from `desk-api.ts:56` (compose passes `infra.memberDirectory`) with the workspace's `clerkOrgId`, plus the same workspace's `agent_mailboxes`. Without a directory, members count as outside.
- V3.2's `askBefore` reads `agentToolRules`. Make it skip `mail:` keys (one filter in `agent-profile.ts`).
- Expiry runs from the minute tick (`tick/runtime.ts:16`), and that runs on production only. The unit test covers expiry. Staging can't.
- Same-file overlaps in the services lane: `agent-profile.ts` (V3.2, V4.3).
