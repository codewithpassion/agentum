From M1 gate round 1 (docs/reviews/M1-1.md, must-fix 1). When the daemon stops on its own (SIGTERM, a 1012 close, a restart), the server answers its `aborted` completion with 409 because the run is still `running`, and the daemon treats the 409 as done. The run stays `running` until the lease ends, then turns `interrupted` with no `process_ended_at`, so the chat disables Send and Retry for 10 minutes.

## Scope

In `packages/services/src/runs.ts` `completeRun`, when `status` is `aborted`, the run is `running` and the caller passed `authorizeRunWrite`, do one conditional write (`WHERE id = ? AND status = 'running'`). It sets `status = 'interrupted'`, `finished_at`, `process_ended_at` and `error = "Aborted by the machine"`, and then appends `run.interrupted`. An aborted call on an `interrupted` run keeps today's behaviour, and a repeat on either path still gets 409. Remove the wrong comment at `apps/daemon/src/run.ts:134`, or make it true. Update the C4 line in `docs/architecture/index.html` (around 1538) and the matching sentence around 1485 so that they say `aborted` is accepted for a running run from the machine that claimed it, and for an interrupted run. The daemon code stays as it is.

## Check

- A service test: claim a run as machine A, then `complete { status: "aborted" }` makes it `interrupted` with `process_ended_at` set and a `run.interrupted` event. A second aborted call gets 409. The same call from machine B gets 403.
- `runs-machine.test.ts`: after an aborted completion of a running run, the run token is refused by the proxy resolver, and the agent's next queued run can be claimed at once.
- Live: start a run that runs `sleep 60`, send SIGTERM to the daemon, and within a few seconds the row is `interrupted` with `process_ended_at` set, and the chat's Retry and Send are enabled.
