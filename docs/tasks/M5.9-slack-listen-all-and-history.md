Asked for by Dom on 19 Oct 2026, for agents such as an archivist that should see every message in their channels and decide for themselves whether to answer. M5.7 subscribes the app to `message.channels` and `message.groups` and lets through only replies in threads the agent started. This task builds on that.

Decisions (Dom, 19 Oct 2026):
- A setting per Slack app on the agent's Slack tab: "Mentions only" (default, today's behaviour) or "All messages in its channels".
- In "all messages" mode, channel messages are stored and handed to the agent in batches: at most one run per channel every 5 minutes, carrying every message since the last batch. Mentions and DMs still start a run at once, as now.
- The agent answers only if it decides to. A batch run may end with no reply, and nothing is posted then.
- Messages are stored by Harbourmaster, so they can be searched.
- Slack's `search.messages` needs a user token, so bots can't use it. History comes from `conversations.history` and `conversations.replies` (the app has `channels:history` and `groups:history`), and full-text search runs over our stored copy.

## Scope

- Setting: a `listen_mode` column on `slack_apps` (`mentions` or `all`, default `mentions`), a service method and tRPC procedure to change it (people only), and a control on the Slack tab that explains the cost in one sentence.
- Store: a `slack_messages` table (workspace, app, channel, ts, thread_ts, Slack user id, linked Harbourmaster user if any, text, created_at), written for every channel message in "all" mode and for every message that starts a run in either mode. Skip bot messages, including the agent's own. Edits and deletes (`message_changed`, `message_deleted`) update or remove the row. Message bodies are workspace data: never log the text.
- Batching: in "all" mode, a channel message that isn't a mention or a reply in an agent-started thread goes to the store and schedules a batch for that channel, unless one is already scheduled within 5 minutes (use a Durable Object alarm or the existing cron tick, whichever the codebase already uses for similar delayed work). The batch run's message lists the new messages (author, time, text, thread) and says the agent may reply in the channel or a thread with `slack_send`, or do nothing. The batch run has no automatic reply: what the agent writes at the end isn't posted. Mentions keep their automatic reply.
- Tools for runs (agents with a Slack app), in the M5.7 tool module:
  - `slack_history`: one channel or one thread over a time range, from Slack live (`conversations.history` and `conversations.replies`), paged, capped at 200 messages per call. Only channels the bot is in.
  - `slack_search`: full-text search over the stored messages of this app's channels, with optional channel, person and time filters, capped results. Say in the tool description that it covers only messages stored since "all messages" was turned on, and mentions.
- System prompt: in "all" mode, one line saying the agent sees channel messages in batches and may stay silent.
- Retention: delete stored messages older than 90 days in the existing purge job, and say so on the Slack tab.

## Check

- Service tests: "mentions" mode ignores plain channel messages as before; "all" mode stores them and schedules one batch per channel per 5 minutes; a mention in "all" mode starts an immediate run and is not batched again; a batch run posts nothing on its own; edits and deletes update the store; bot messages are skipped; the history tool refuses a channel the bot isn't in; search filters by channel, person and time; rows older than 90 days are purged.
- `bun run check && bun run test && bun run build` pass.
- Live on staging (controller): switch Comms-Chief to "all messages", post three plain messages in its channel, and see one batch run within about 5 minutes; ask it in the Harbourmaster chat to search for a word from those messages and to summarise the last hour of the channel.
