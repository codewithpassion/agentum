Found by V1.15's staging check on 26 Oct 2026. An agent runs one run at a time. A run queued behind a run in the `waiting` state is failed "Never claimed" one hour after it was created (the M4.4 cut-off, `NEVER_CLAIMED_ERROR` in `packages/services/src/runs.ts`). An approval also waits one hour. So a Slack message sent to an agent while it waits on an approval is lost when nobody answers within the hour. Staging example: run 01M5VA5X4NF4Y7YPQRZ62G9A13 failed at 06:16:49 UTC behind a waiting run.

## Scope

- A run that is queued only because an earlier run of the same agent is `waiting` (or running) must not hit the never-claimed cut-off. The cut-off still applies when no runtime ever picks the run up (machine offline, managed poller dead).
- Pick the smallest rule that does this, for example measuring the cut-off from when the agent was last free rather than from creation. Write the rule in the task's review file.
- Unit tests in `packages/services` cover: queued behind a waiting run for more than an hour is not failed; queued with a free agent and no claim for an hour is still failed.
