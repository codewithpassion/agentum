The agent's mail tools, available to every runtime through the platform MCP.

## Scope
- New `packages/mcp/src/tools/mail.ts`: `mail_list` (threads of the calling agent's mailbox), `mail_read` (one thread), `mail_send`, `mail_reply`, using the V5.1 port signatures and input schemas.
- A held send returns a clear "waiting for approval, you will be told the outcome" text, not an error.
- Register the tools only for run principals of agents with an active mailbox.

## Check
- `packages/mcp/src/tools/mail.test.ts` with fake ports: list and read, send sent, send held, reply to a thread, refused for a principal without a mailbox.
- `bun run check && bun run test && bun run build` pass.

## Refinements (2026-10-27)

Checked against main at c5ba505. Where these differ from the scope above, they win.

- No V3 or V4 dependency. V3.9's dry-run gate keys on annotations, so it covers these tools whatever the order.
- This task now holds the mail part of `McpPorts` (moved from V5.1): an optional `mail?:` group (`list`, `read`, `send`, `reply`), so the app compiles until V5.7 adds adapters. The four input schemas go in the new `packages/mcp/src/tools/mail.ts`.
- Registration: a `mail?: boolean` field in `ServerOptions` (`server.ts`), beside `readOnly` and V3.9's dry-run option. `harbourmasterTools` adds `mailTools(ports)` when `mail` is true and `ports.mail` is set. The route decides (V5.7).
- Annotations: `READ_ONLY` for `mail_list` and `mail_read`, a `WRITE_*` set for `mail_send` and `mail_reply` (`tools/define.ts`).
- Held send text: the mail is held for a person, the outcome shows in `mail_read`, and the agent should not send it again. The run is not paused (V5.5).
- Same-file overlaps in the mcp lane: `server.ts` (V3.9), `tools/define.ts` and `tools.test.ts` (V3.9, V4.13).
