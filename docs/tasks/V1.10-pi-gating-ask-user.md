Cloud runs execute tools inside the `PiRun` Durable Object. An approval or a question can take hours, and the object can be evicted in that time, so the wait must survive a restart the way C.0 to C.10 made tool calls survive one.

## Scope
- New `apps/web/src/server/pi-run-gate.ts` (logic) and its install in `PiRun`'s constructor next to `repeatGuardExtension()`: an extension whose `wraps` decorate every tool (or a `beforeTool` hook if a wrap can't cover MCP tools installed later; settle this first, see the pi-durable README "Extensions" and "Calling tools from tools").
  - Before a call runs: `toolKey({ runtime: "cloud", name, server })` with the installed server keys, then `requests.needsApproval`. No rule: the tool runs as today, with no extra latency beyond one D1 read (cache the agent's rules for the run).
  - With a rule: `requests.open` (idempotent on Pi's tool call id), then wait for the outcome. Allowed: run the inner tool as a nested call (`api.executeTool` with a fixed `key`), so after a restart a finished inner call is not repeated and an unsafe one follows its own replay policy. Denied, expired or cancelled: return `outcomeText` as an error result without running the tool.
  - The waiting gate is replay-safe: after an eviction it re-runs, finds its request by tool call id, and waits again or proceeds.
- `ask_user` Pi tool from `ASK_USER_TOOL` (V1.3), installed for every cloud run, also replay-safe: opens a `question` request and returns `outcomeText`. Add one sentence to the cloud system prompt saying when to use it.
- Waking: `PiRun.requestAnswered(runId, requestId)` RPC resolves the in-memory waiter; `durableRunnerPort` in `pi-run-port.ts` implements `answered` with it. Without a live waiter (after an eviction), the lease alarm (`RunLeaseAlarm`) also checks open requests each beat, so an answer is picked up within one beat even if the RPC was missed.
- The lease keeps beating while the run is `waiting` (V1.2 made heartbeats accept it).
- Dev only: a faux prompt in `pi-run-faux.ts` that calls `ask_user` and one that calls a gated tool, for local tests and the durability suite.

## Check
- `pi-run-gate.test.ts` with a fake requests service: no rule runs the tool at once; a rule opens one request and runs the tool after allow; deny and expiry return the texts and the inner tool never runs; a re-run of the gate after a simulated restart reuses the request and does not run a finished inner call twice.
- `pi-run-core.test.ts`: the run goes `running -> waiting -> running -> done` with `run.waiting` and `run.resumed` events.
- `bun run e2e:pi-durability` gains a case: kill the dev server while a run waits for an answer, restart, answer, and the run ends `done` with the tool run once.
- `bun run check && bun run test && bun run build` pass.
- Live on staging (controller): an isolate agent with "Ask me before" on `bash` waits on a `bash` call; Allow once runs it; a second call asks again; Always allow stops the asking.

## Refinements (26 Oct 2026, against main)

Checked against the code before V1 started. Where these differ from the scope above, they win.

- PiRun status checks that only accept `running` must treat `waiting` the same: the claim in `pi-run.ts:254` (else a restarted waiting run gets `conflict`), the completion retry in `pi-run-core.ts:409`, and `pi-run-start.ts`.
- Pass the original MCP `server` and tool name to the gate. Don't parse them back out of Pi's tool name: `piToolName` replaces characters and truncates, and `uniqueName` may add `_N` (V1.3's tool keys).
