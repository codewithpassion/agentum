One service owns every question and approval, whatever runtime raised it and whatever surface answers it. The first answer wins, an unanswered request expires, and the run moves between `running` and `waiting` as requests open and close.

## Scope
- New `packages/services/src/requests.ts` (factory `createRequestsService({ atomic, clock, db, events, runs, secrets })`, helpers in `packages/services/src/requests/`), added to `composeWith` and `Services` in `apps/web/src/server/compose.ts` (that one registration only):
  - `needsApproval(principal, { runId, toolKey })`: reads `agent_tool_rules` for the run's agent; true only for mode `ask`.
  - `open(principal, { runId, kind, toolUseId, toolName, toolKey?, input | questions })`: system or the claiming machine only (same rule as `authorizeRunWrite`). Idempotent on `(run_id, tool_use_id)`: a repeat returns the existing row and its outcome if it already has one. For an approval, `display.input` is the input after `redactToolPayload` (C.19, `packages/services/src/events/scrub.ts`) and the run's masker (`secrets.maskerFor`), capped per V1.1; `display.summary` from `approvalSummary`. Sets `expires_at` from `APPROVAL_TTL_MS` or `QUESTION_TTL_MS`. Writes the row, then appends `request.opened` with `append` (not `insertStatement`, so stream and Slack listeners see it), then calls `runs.markWaiting`.
  - `answer(principal, { requestId, answer, via })`: a user who can see the run's session (`visibleSessions`). Compare-and-set `WHERE status = 'pending'`: the first answer wins and a later one gets `conflict` "Already answered". `always_allow` also upserts the rule to `allow` and appends `tool_rule.changed`. Appends `request.answered` (decision or answers, answered by, via; free-text answers go through `redactText`). When no other request of the run is pending, calls `runs.markRunning`, then the runtime's wake-up (below).
  - `outcome(principal, requestId)` and `waitForOutcome(principal, requestId, { waitMs })`: the poll the daemon uses, same pattern as `waitForRun` (`WAIT_POLL_MS`, capped at 25 s).
  - `expireDue(principal)`: system only; pending rows past `expires_at` become `expired` with `request.expired`, then the same resume and wake-up as an answer. Safe to run twice.
  - `cancelForRun(run)`: on `run.finished`, `run.failed`, `run.cancelled`, `run.interrupted` (register with `runs.onEvent`), pending rows become `cancelled` with `request.cancelled`.
  - `listPending(principal, { sessionId? })` and `listRules` / `setRule` / `removeRule` (per agent, `tool_rule.changed` on each change).
- Wake-up port: `RuntimeAdapter` in `packages/services/src/runs/types.ts` gains optional `resume(run, request)`. The cloud adapter (`cloud/runtime.ts`) calls a new optional `CloudRunnerPort.answered(runId, sessionId, requestId)`; the managed adapter (`managed/runtime.ts`) calls `poller.kick(runId)`; the machine adapter does nothing (the daemon long-polls). The app-side ports are V1.9 and V1.10.
- Machine claim: `claimRunForMachine` (`packages/services/src/runs/machine-claim.ts`) takes a `requestsForDaemon` option like `libraryForDaemon` and then adds the agent's ask keys as `toolRules`.
- tRPC `apps/web/src/server/trpc/requests-router.ts`: `pending({ sessionId? })`, `answer({ requestId, decision | answers, note? })` with `via: "web"`, `rules.list({ agentId })`, `rules.set({ agentId, toolKey, mode })`, `rules.remove(...)`. Registered in `router.ts`.

## Check
- `packages/services/src/requests.test.ts`: open is idempotent and puts the run in `waiting`; two runs of the same tool use id stay separate; the display holds `[redacted]` for an `sk-` token and `[secret NAME]` for a granted secret's value; first answer wins against a second (conflict) from another surface; `always_allow` writes the rule and the next `needsApproval` is false; two pending requests keep the run waiting until both close; expiry turns a pending row `expired` and resumes the run, twice in a row changes nothing; cancel on run end; a user who can't see the session gets not found; the adapter's `resume` is called once per close.
- `requests-router.test.ts`: input validation and that each procedure is one service call.
- `bun run check && bun run test && bun run build` pass.

## Refinements (26 Oct 2026, against main)

Checked against the code before V1 started. Where these differ from the scope above, they win.

- Register the router as `requests` in `runtime-router.ts`, not `router.ts` (lanes don't edit `router.ts`).
- `claimRunForMachine` (`runs.ts`) and `claimForMachine` (`runs/machine-claim.ts`) both take `requestsForDaemon`.
- `authorizeRunWrite` and `WAIT_POLL_MS` are private to `runs.ts`. Repeat the `authorizeRunWrite` rule (system, or the machine in `claimed_by`) in the requests service rather than importing it.
- Add `./requests` to the `exports` of `packages/services/package.json`.
