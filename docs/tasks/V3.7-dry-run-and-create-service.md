Before "Create agent", the person runs the draft on a sample and nothing is saved or sent. "Create agent" then turns the draft into a working agent with its tools, skills, schedule and address in one step.

## Scope
- `agentBuilder.saveDraft(principal, { draftAgentId?, draft })`: creates or updates the `draft` agent row (V3.4 `createDraft`) from the reconciled draft.
- `agentBuilder.dryRun(principal, { draftAgentId, sample })`: starts a run through `runs.startRun` with `dry_run = true`, a `dry_run` session origin, and the cloud isolate runtime whatever the draft's runtime is (the model maps to `CLOUD_DEFAULT_MODEL` when the draft's model is not a cloud model). Returns the run id. The page follows it on V1's stream and renders it with `buildReceipt`.
- Dry runs never appear on the desk, in sessions, in Slack or in recent tasks (filter on `dry_run` in V2.8 and V2.9's queries).
- `agentBuilder.create(principal, { draftAgentId, draft })`: in one `atomic` write where the services allow, else in order with a clear partial-failure error: activate the draft, assign connectors and skills, set `handsTo`, create the routine (approved, since a person made it), and reserve the address. Refuse while gaps remain, except the address, which falls back to `suggestAddress`.
- `agentBuilder.discard(principal, draftAgentId)`.
- Add the procedures to `agent-builder-router.ts`.

## Check

## Refinements (2026-10-26)

Checked against main at ae74008. Where these differ from the scope above, they win.

- Starting a dry run: do not add `dryRun` to `startRunInputSchema`, because `runs-router.ts` builds the browser schema from it. Pass it in-process, for example `startRun(principal, input, { dryRun: true })`. `prepareStart` then accepts a `draft` agent, picks the cloud adapter whatever `agent.runtime` is, and the insert sets `dry_run`.
- The model swap goes in `cloud/runtime.ts`, which reads the agent row itself. When `run.dryRun` is set and the model is not in `CLOUD_MODELS`, use `CLOUD_DEFAULT_MODEL`.
- Session: origin `dry_run` with `private: true`. `visibleSessions` then hides it from other members, and the builder still reads it through `sessions.get`, which the stream route authorizes with (`session-stream.ts:202`). Do not filter dry runs in `visibleSessions` or `sessions.get`, or V3.13 loses its stream.
- Filter `dry_run` out of the lists: the desk's run lanes (`desk.ts`), `tasks.list` (`tasks/service.ts`), and the session list and search (`sessions.ts`). Dry runs open no requests (V3.8 skips `ask_user` too), so Needs you and the Slack DM cards are unaffected.
- `saveDraft` writes through V3.4's `createDraft` and `agents.update`. The page keeps the full draft (gaps, didList, sample) in its state. The row holds the fields only.
- `create`: each service writes its own events and none takes an outer `atomic`, so go in order. Call `activate` first, because `connectors.assign` (`loadActiveAgent`), skill assignment and `routines.create` refuse a non-active agent. Then assignments, `handsTo`, the routine and the address. On a failure, report what was done and what was not. Rules go into `instructions` (V3.1). `mail` starts create nothing (V3.5).
