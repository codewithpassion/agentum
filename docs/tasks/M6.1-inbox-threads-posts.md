From `docs/architecture/build-plan.html#m6`. Automation lane. Depends on contracts C3 and C7 (M0.4). M2.3 (inbox tools) needs this service. Reuse: Agentum `loop-guard.ts` (borrow). Paths are in `docs/architecture/reuse.html`.

## Scope

`inbox_threads` and `inbox_posts` tables. `createInboxService({ db, atomic })` and router: create thread, post, list, read. Mention parser for `@slug`.

A user's post with mentions starts one run per mentioned agent with the user's principal (`origin: "inbox"`, `externalKey = threadId`, reply target the thread). The inbox gateway writes the agent's reply post with `run_id` from the trusted context. Mentions in that post start runs with a run principal for that run, so the subject is inherited from server-side data.

Loop guard, Agentum's two rules: after 3 agent-authored posts in a row in a thread no agent is woken there until a person posts, and each agent has a wake budget of 10 per hour. A stopped wake appends `inbox.loop_stopped`.

Inbox page: thread list, thread view, composer.

## Check

`inbox.test.ts` through `completeRun` and the real inbox gateway with the fake runtime:

- a user post "@pelican hi" produces a run on behalf of that user and a reply post carrying its `run_id`;
- a reply by agent A whose text mentions agent B starts B's run with `parent_run_id` = A's run and the same subject;
- a user post that merely quotes a run id does not change the subject;
- two fake agents that mention each other stop after the third agent post and resume when a person posts;
- a post with no mention starts nothing.

Browser: post in the UI, see the reply appear on poll.
